02

작업 개념도

native 하네스는 건드리지 않는다. 우리가 소유하는 것은 그 바깥의 다섯 가지 — 상태, 권한, 예산, 근거, 종료다.

deliberate 모드의 실제 순서

네 모드 중 가장 비싼 경로. 핵심 장치는 가운데 세로선 하나다 — 초안이 전부 확보되기 전에는 누구도 남의 답을 볼 수 없다. 이것이 없으면 "독립 교차검토"는 그냥 한 모델의 의견이 나머지로 번지는 과정이다.

공통 입력에 오류가 두 건 있었다

blind 검토에 제공한 "확인된 사실" 중 두 개가 틀렸다. "ACP는 과금 정보를 포함하지 않는다"는 과장이었고(스키마에 세션 누적 Cost가 있다), "Paseo는 AGPL-3.0"은 검색 스니펫을 확인 없이 옮긴 것이었다 — 실제로는 Apache-2.0이다. 둘 다 GitHub API와 원문으로 직접 확인했어야 했다.

P0의 "같은 버전으로 제공한다"는 같은 오류를 함께 받는다는 뜻이기도 하다. 한 참여자가 첫 번째를 잡았고 두 번째는 아무도 잡지 못했다 — 물어보지 않은 것은 검토되지 않는다.

같은 이유로 herdr는 아예 목록에 없었다. 40.2k★ Apache-2.0 Rust 런타임이고, 세션 생존·재접속·pane 상태라는 이 프로젝트의 D16 영역을 정면으로 다룬다. 빠진 선택지는 반례가 나올 수 없다.

같은 결론이 같은 근거를 뜻하지 않는다. 의존 범위 질문에서 양쪽 다 "전체 채택 보류"에 도달했으나, 한쪽은 원칙에서 추상적으로, 다른 쪽은 실제 코드의 강등 경로를 읽고 논증했다. 합의는 관측값이고 근거는 한쪽에만 있었다.

04

다음 대화에서 결정할 것

아래는 설계가 갈리는 지점이다. 지금 답을 고르지 않아도 되지만, 골라야 구현이 시작된다. 각 항목에 현재 기울어진 쪽을 표시했다.

Q1

어댑터 전송을 무엇으로 할 것인가

저장소는 CLI별 맞춤 adapter를 설계했다. 그 사이 ACP가 사실상 표준이 됐다.

ACP 우선 + exec 폴백세 도구 중 ACP 지원을 V04-01에서 확인하고, 지원하는 것부터 붙인다. 미지원은 codex exec·claude -p·agy 헤드리스로 감싼다.
전부 직접 exec의존성이 없고 동작이 투명하다. 대신 세 도구의 출력 형식 변화를 계속 따라가야 한다.
Q2

Orca를 흡수할 것인가, 참고만 할 것인가

MIT라 법적 제약은 없다. 문제는 의존의 크기다.

패턴만 가져온다worktree 격리 방식과 어댑터 목록을 참고하되 코드는 직접 쓴다. 우리 고유 기여(2·5층)가 남의 실행 모델에 묶이지 않는다.
Orca 위에 얹는다배선을 통째로 절약한다. 대신 상태·예산의 단일 소유자 원칙(D16)을 남의 스케줄러와 협상해야 한다.
Q3

첫 실행 언어와 런타임

현재 검사기는 Python이다. 처음에는 "전송을 쓰려면 TypeScript가 필요하다"고 적었으나 ACP에 공식 Python 라이브러리가 있어 그 전제는 성립하지 않는다. 선택 근거가 바뀌었다.

Python 코어 유지, TS는 화면 경계만상태·예산·정책 엔진을 두 언어로 쪼개지 않는다. 기존 74개 검사와 계약을 그대로 잇는다. UI가 필요해지면 그때 경계를 하나 둔다.
TypeScript 단일유지보수자가 TS에 훨씬 능숙하거나 배포에서 Python 동봉이 반복 장애가 되면 이쪽이 낫다. 지금 코드량이 작아 이식 비용도 작다.
Q4

첫 화면이 보여줄 것

앱의 정체성이 여기서 갈린다. 병렬 실행기인가, 판단 구조인가. 교차검토에서 양쪽 다 claim ledger를 권했으나 양쪽 모두 근거가 없었다. D12에 따라 미해결로 남긴다 — 합의는 검증이 아니다.

세션 그리드실행 중인 에이전트를 나란히 보여준다. 기존 도구 전부가 이 모양이다. 주 용도가 판단 검토가 아니라 장시간 작업 감시라면 이쪽이 맞다.
claim ledger어느 판단이 어떤 근거에 의존하고 무엇이 미해결인지를 앞에 둔다. 차별화에는 성공해도 사용자가 시간만 더 쓰고 오류를 더 잘 찾지 못하면 실패다.

판정은 Q8 화면 비교 실험 이후다. 선호도가 아니라 잘못된 확신, 중요한 반례 발견, 판단에 걸린 시간을 본다.

결정 전에 먼저 할 일

위 네 가지는 전부 V04-01 인벤토리 결과에 따라 답이 바뀐다. 실제 설치 버전, 로그인 방식, 사용 가능한 상급 모델, ACP 지원 여부, 권한·취소 기능을 비밀 값 없이 기록하는 것이 먼저다. 문서만 보고 configured = true로 만들지 않는다.

그 다음이 V04-03 — 두 native 경로의 읽기 전용 독립 답변 비교. 세 모델 토론·자동 수정·학습 router·장기 DB를 동시에 붙이지 않는다.

이 문서가 주장하지 않는 것. 여기 그려진 구조 중 실행되는 것은 §01의 초록 항목뿐이다. 다이어그램은 설계의 그림이지 동작의 증거가 아니다. 라이선스·star 수·topics는 2026-09-22 GitHub API로 확인했고, 각 프로젝트의 실제 코드 품질·보안·전체 동작은 검사하지 않았다. F25–F27은 문서·코드·로컬 재현으로 확인했으나 실제 CLI를 설치해 실행한 결과가 아니다. 교차검토를 한 번 돌렸다는 것이 이 방식이 단독보다 낫다는 증거도 아니다 — 대조군 없이 한 번 실행했을 뿐이다. 협업이 단독보다 나은지는 여전히 측정되지 않았다.
