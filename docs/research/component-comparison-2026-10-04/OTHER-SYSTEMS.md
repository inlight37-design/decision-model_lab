# 대응 프로젝트도 내부 책임으로 나누기

고정 SHA·읽은 줄은 [근거 문서](EVIDENCE.md)와 [출처 맵](source-map.json)에 있다. 아래 설명은 선택한 코드 경로에 대한 것이다. 다른 경로에서 같은 기능이 없다고 단정하지 않는다. 이번에 추가로 읽지 않은 Hermes 전체 UI·자동화·연동 분야는 [앞선 기능 목록](../feature-catalog-2026-10-04/HERMES.md)의 문서 근거를 따른다.

## Hermes Agent

### 세션 원문 검색 — HM-SEARCH

`session_search_tool.py`는 검색을 discover/scroll/read/browse로 나눈다. FTS5로 먼저 관련 세션을 찾고, 필요한 위치를 펼쳐 읽는다. 검색 자체에는 모델 호출이 필요 없다고 명시한다. 숨겨진 세션 종류, cron 결과 순서, lineage 중복, 읽는 내용의 길이 같은 조건을 두어 “과거 모든 내용을 한 번에 prompt에 넣기”와 다른 흐름을 만든다. 이번 검토는 1–95행의 계약·설정이 중심이며 모든 SQL을 실행한 것은 아니다.

**우리 적용:** 작업/실행 목록에서 질문·결과·검토 내용을 검색하고, 결과 한 줄의 근거 위치를 눌러 원문을 연다. 검색 결과 열람과 다음 실행 첨부를 별도 행동으로 둔다. 최근 실행만으로 기억을 채우는 한계를 줄이고, 사용자가 과거 자료를 직접 고를 수 있다.

### 개인/에이전트 기억 snapshot — HM-MEMORY

`MEMORY.md`와 `USER.md`를 세션 시작 시 고정한 문맥으로 읽고, 중간 파일 변경은 현재 prompt를 바꾸지 않는 계약이다. memory 도구는 add/replace/remove/batch를 지원한다. 우리 실행 입력 hash와 잘 맞는 발상이다.

읽은 `_gate_or_stage`는 허용/차단/승인 대기 흐름을 나누며, 교체·삭제를 승인 대기로 보낼 때 당시 일치한 항목을 고정한다. 승인 시 다시 부분 문자열 검색해서 다른 항목에 적용하는 문제를 피하려는 설계다. 다만 gate 모듈 import 실패 시 허용하는 분기도 있으므로 모든 경로의 강제 승인 보장으로 소개하지 않는다.

**우리 적용:** 기억 편집 창에서 `expected_version` 또는 이전 본문 hash를 함께 보내고, 사용자가 읽은 뒤 다른 세션이 바꿨으면 다시 검토하게 한다. 실행 도중 메모를 수정해도 이미 고정한 입력은 변하지 않는다.

### 절차 재사용과 점진적 펼치기 — HM-SKILLS

`skills_list`는 이름·설명 등 목록을, `skill_view`는 본문·태그·관련 파일을 제공한다. 설치된 플러그인 스킬, 플랫폼, 비활성 상태, 파일 경계가 별도 고려 대상이다. 긴 절차를 항상 넣지 않고 필요한 순간 읽는 편의가 핵심이다.

`agent/curator.py`에서 읽은 수명 분류 경로는 사용 시각으로 active/stale/archive를 나누고 pin 또는 cron 참조 대상을 보호한다. 아직 본 적 없는 seed와 한 번도 쓰지 않은 항목에 유예를 둔다. 이 부분은 결정적 분류이고, 다른 LLM consolidation 경로의 품질을 검증한 것은 아니다.

**우리 적용:** 역할/자료/출력 형식을 묶은 작업 양식, 스킬 설명 카드, 선택한 스킬의 고정 내용, 사용 기록에 따른 정리 제안. 오래 안 썼다는 이유로 자동 삭제하지 않고 pin·참조 중인 양식을 보존한다. 스킬의 shell 전처리·도구 실행은 별도 기능으로 명시해야 한다.

## codex-peek

### MAP 검색 — PK-RETRIEVAL

`map-retrieval.js`는 경로·backtick 식별자·인용 구절 등 검색 seed를 추출하고, 결정적 lexical 점수와 tie-break를 사용한다. 경로 구분자와 NFC 정규화, URL 제외, seed 상한 같은 작은 처리들이 코드 질문에서 유용하다. 임베딩 의미 검색이라고 부르면 안 된다.

**우리 적용:** 파일명·에러 코드·결정 ID를 정확히 찾는 채널을 자연어 유사도와 구별한다. “이 경로가 같아서”, “이 식별자가 일치해서” 같은 선택 이유를 표시한다. 현재 `app/memory.py`는 질문의 단어/한국어 2-gram을 비교하므로 이 채널은 별도 개선 후보가 된다.

### 근거와 최신성 — PK-FRESHNESS, PK-RETRIEVAL

`map-freshness.js`의 계약은 기준 결정(`basisDecisionId`)을 가진 authoritative baseline과 단순 캐시 evidence를 구별한다. `map-reader.js` 입구는 잠금 아래 기준/정규 내용을 snapshot으로 읽고, 해시 계산을 밖에서 하며 변동 시 제한적으로 재시도한다. 읽기 경로가 기준 결정을 새로 작성하지 않는 분리가 핵심이다.

`map-provenance.js`는 DECISIONS의 원자적 기록에서 “왜?” 검색을 별도로 수행한다. 코드 seed와 결정의 제목/keywords를 찾는 방식은 다르다. 조회 사용 로그와 실제 첨부 원장도 같은 것이 아니다.

**우리 적용:** 검색 인덱스에 원문 hash/추출기 버전을 묶고, 현재 자료와 달라졌으면 stale을 표시한다. “기준으로 채택한 결정”과 “검색 중 발견한 관련 기록”을 다르게 보여준다. 검색한 뒤 실행에 붙이지 않은 자료가 입력 원장에 들어가지 않도록 한다.

### 검증 완료와 멈춤 조건 — PK-VERIFY

`verify-guard.js`의 선택 경로는 변경 흔적, proof 상태·종료 코드·비어 있지 않은 결과·세션·시각을 본다. 재시도 상한으로 Stop 훅 루프가 무한히 반복되는 것을 막으려는 구조도 있다. proof가 사실 정확도를 보장한다는 뜻은 아니다.

**우리 적용:** 실행 완료 화면에 “결과 도착”, “필요 검토 완료”, “미해결 항목 남음”을 구별한다. 외부 Stop 훅을 설치하는 대신 현재 controller의 종료·검토·처분 상태를 재사용한다. 우리의 whole-tree 종료 확인과 blind 초안 계약은 그대로 유지할 기준이다.

## WorkTrail

### 작업 기록과 연구/모델 계층 분리 — WT-RECORD

`casebook/core/worktrail.py`는 자체 DB의 케이스/작업 기록 엔진이며 해당 파일에서 LLM을 import하지 않는다. `recording.py`는 외부에서 온 note/evidence와 참조를 기록하고 pending→finalized 같은 상태 변화를 다룬다. 기록을 남기는 행위 자체에 모델 호출을 붙이지 않아도 된다.

**우리 적용:** 결과를 또 요약시키기 전에 질문, 사용자 결정, 검토 처분, 다음 행동을 구조화해 남긴다. 현재 원장에 이미 있는 사실은 다시 생성하지 않고 projection으로 보여준다.

### 상태 문장과 원문 검색의 분리 — WT-STATE, WT-SEARCH

`state.py`는 decision/constraint/ruledout, scope와 evidence, 사용자/에이전트 권한 출처, supersedes를 가진 추가 기록에서 현재 상태를 만든다. focus/open/next와 next owner를 별도 선언으로 다룬다. 읽은 설명상 hypothesis와 brief는 current-state의 권위가 아니다. 모든 기록에 사용자 승인 절차가 있다는 뜻은 아니다.

`search.py`의 FTS5 검색은 evidence 원문·snippet·출처를 반환하고 기본적으로 보관 케이스를 제외하며 소유 범위를 결합한다. `prior.py`는 설치 전 대화에서 사용자 메시지를 찾아 보존하는 경로다. 거기서 결정·목표·thread를 임의 추론해 만들지 않고 원본 경로와 외부 ID를 둔다.

**우리 적용:** 긴 실행 결과에서 현재 결정을 자동 사실로 만들지 않는다. 사용자가 확인한 결정/제약과 모델의 제안은 분리한다. 검색 결과에는 “사용자 원문”, “모델 답변”, “검토 처분” 출처를 표시한다. 작업 복귀 화면에는 `현재 결정 / 남은 문제 / 다음 행동 / 담당`을 보여줄 수 있다.

### thread·작업공간 연결 — WT-STATE

`threads.py`는 함수 목록 수준에서 repo/worktree 식별, 연결, checkpoint와 전환 경로를 확인했다. 전체 구현을 검토하지 않았으므로 동시성·이식성·재시작 정합성은 미확인이다. 우리 GitHub 카드 운영은 이미 일부 채택한 방식이므로 새 task DB를 병렬로 만드는 것보다 카드/실행과 연결된 화면부터 시작하는 편이 중복이 적다.

### 재사용 조건

루트 라이선스는 **FSL-1.1-ALv2**다. MIT 프로젝트처럼 코드 파일을 바로 가져올 후보로 분류하지 않는다. 개념·사용 흐름을 참고해 우리 계약으로 독자 설계하고, 코드를 실제 재사용할 때는 대상 버전의 허용 범위와 전환 조건을 별도 검토한다. 이번 산출물에는 upstream 제품 코드를 복사하지 않았다.

## 그 밖의 후보를 잃지 않기

tmux의 화면 분리·재연결·이벤트 아이디어는 [기존 코드 분석](../tmux-2026-09-23/README.md)에, Beads/Backlog/GasTown 및 협업 제품의 기능은 [다른 프로젝트 목록](../feature-catalog-2026-10-04/OTHER-PROJECTS.md)에 있다. 이번 깊이 분석과 동일하게 모든 프로젝트의 코드를 검토했다고 확장 해석하지 않는다. 이후 사용자 불편이 해당 분야에 생기면 같은 양식으로 `입력→상태→실행→실패→화면→우리 접점`을 채울 수 있다.
