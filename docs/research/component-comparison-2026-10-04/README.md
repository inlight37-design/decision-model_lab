# 외부 프로젝트 부품 분석과 같은 기능 비교

2026-10-04 · codex · 클라우드 소스 검토 · [카드 #158](https://github.com/inlight37-design/decision-model_lab/issues/158)

사용자 요청은 AnchorMind 같은 오래 다듬어진 프로젝트를 기능 이름만 훑지 않고, 내부 구성과 동작을 나누어 비슷한 기능끼리 비교한 뒤 우리 프로젝트에 넣기 쉽게 남기는 것이다. 이 기록은 [넓은 기능 후보 목록](../feature-catalog-2026-10-04/README.md)의 **코드 수준 후속 분석**이다. 프로젝트의 개발 기간·인지도 자체를 성숙도의 증거로 쓰지 않았다. 이번에 확인한 근거는 고정한 소스의 책임 분리, 실패 처리, 상태 계약과 일부 순수 함수 실행이다.

## 어떤 장점을 가져오면 좋은가

- **AnchorMind:** 작은 기억에 출처·수명·관계·검토 상태를 붙이고, 저장 이후 인덱싱·정리·관리를 별도 부품으로 운영하는 방식. 우리에게는 선택 이유, 기억 관리 화면, 교체 이력, 검색 평가가 먼저 유용하다.
- **Hermes:** 이전 대화를 단계적으로 찾아 읽기, 세션 시작 시 기억 고정, 스킬을 목록→본문→관련 파일 순서로 펼치기. 반복 설명과 입력 준비를 줄이는 편의에 강점이 있다.
- **codex-peek:** 지도·검색 결과가 어느 원문과 기준 결정에서 왔는지 추적하고, 낡았는지 표시하는 방식. “왜 이 자료가 붙었지?”와 “최신 자료인가?”를 함께 해결할 후보다.
- **WorkTrail:** 대화와 별도로 결정·제약·제외한 선택·다음 행동을 기록하는 방식. 긴 원문을 읽지 않고 작업에 복귀하는 데 유용하다.

따라서 다음에 고르기 좋은 조합은 **기억 선택 설명 + 이전 실행 검색 + 결정/다음 행동 요약 + 교체 이력**이다. 외부 기억 서버를 설치하기 전에도 현재 SQLite·원장·화면 위에서 만들 수 있다. 임베딩·그래프·자동 회고·연동도 [적용 설계](ADOPTION.md)에 남겼으며, 지금 구현 범위로 확정하지 않았다.

## 분석 범위

AnchorMind `cdcdfaab9d1b9a64fa5f6af23354ac730c24c9fb`의 추적 파일 1,313개를 분류하고, `lib/` JavaScript 357개에 정적 탐색 정보를 만들었다. 그중 선택한 파일 50개의 핵심 경로 또는 인터페이스를 검토했다. **전체 파일 분류는 모든 줄을 읽거나 모든 기능을 실행했다는 뜻이 아니다.** TSV의 `inventory-only`, `interface-inventory`, `selected-source`와 읽은 범위를 구별한다. 다른 프로젝트는 선정한 대응 경로를 읽었으며 전 파일 감사를 주장하지 않는다.

새로운 경계 시험 12개는 고정 upstream의 순수 함수를 실제로 호출했다. DB·Redis·브라우저 UI·외부 모델·운영 서버 통합은 실행하지 않았다. 검색 품질이나 사용자 생산성 개선은 아직 측정하지 않았다. 사용자 PC의 CLI 상태도 이번 접근 범위가 아니다.

기존 AnchorMind v6.0.0 검토를 수정하지 않고 v6.1.0의 별도 기록을 추가했다. 이전의 수동 기억 우선 제안은 현재 사용자 결정인 **일반 팀원·상위 역할 자동 기억, 격리 팀원 제외**에 맞춰 해석한다. 우리 앱의 현재 동작과 새 제안은 아래 비교표에서 분리한다.
