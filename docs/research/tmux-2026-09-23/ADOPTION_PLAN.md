## 2. A — 재접속을 새 실행으로 취급하지 않는 화면

현재 서버의 run/participant/attempt 상태를 화면이 임의로 바꾸지 않는 원칙을 유지한다. 화면은 다음만 별도로 관리한다.

```text
ui_connection: connected | reconnecting | disconnected
selected_run_id: 원장에 이미 존재하는 실행 식별자
last_successful_refresh: 화면이 마지막으로 상태를 확인한 시점
request_in_flight: 중복 조회를 억제하는 화면 내부 값
```

이 값은 **예시이며 새 영속 스키마가 아니다**. `ui_connection=disconnected`를 participant의 UNKNOWN과 합치지 않는다. 화면을 못 본다는 것과 실행 종료를 확인하지 못했다는 것은 다른 사실이다.

최소 구현 후보는 현재 async refresh의 in-flight 제한, 이전 응답보다 오래된 응답을 버리는 규칙, 연결 복구 후 기존 run 재조회다. 요청 번호는 한 브라우저의 응답 순서만 다룬다. 여러 화면·재시작까지 다룰 server revision과는 다르다. 현재 snapshot만으로 충분하면 새로운 version field를 급히 도입하지 않아도 된다. [P05, TM-01·05]

사용자가 실행 생성 버튼을 눌렀으나 응답을 못 받은 경우, 자동으로 같은 POST를 다시 보내면 중복 호출 가능성이 있다. **재시도를 도입할 때**는 controller가 저장한 `command_id`와 요청 내용 binding으로 같은 사용자 명령을 식별한다. 새 명령인지 확인할 수 없으면 사용자에게 기존 실행을 확인하게 하고 조용히 재전송하지 않는다. 이것은 tmux의 명령 번호를 가져온 기능이 아니라 우리 쪽의 별도 영속 계약이다.

## 3. B — 공통 진입점과 적용 설정

현재 `Controller`의 명령 함수, `ExecutionSpec`, runner의 결과, SQLite 사건 기록을 재사용한다. N2가 N1을 호출하도록 하는 기존 계획을 유지한다. 관측 도구 전용 성공 판정, tmux 전용 예산 원장, UI 전용 정족수 판정을 만들지 않는다. [P01–P04]

### 명령·시도·사건의 서로 다른 용도

| 식별자 | 용도 | 같게 만들면 안 되는 것 |
|---|---|---|
| run_id | 고정 질문과 참여자 구성의 실행 | 브라우저 탭/선택 위치 |
| participant_id | 그 실행의 참여자 | provider 표시 이름만으로 식별 |
| attempt_id | 한 번 시작한 실행 | 같은 pane을 다시 쓰는 실행, 같은 질문의 새 호출 |
| command_id | 도입 시 동일 사용자 명령의 재전송 방지 | 새 예산을 쓰는 재시도 |
| journal seq | 원장 사건의 순서 | 모든 화면에 그대로 공개해도 되는 순번 |
| backend instance / generation | 외부 지속 세션을 도입할 경우의 연결 수명 | 프로세스 ID나 pane ID 단독의 영속 유일성 |

현재 run/participant/attempt는 이미 있다. command_id·generation을 당장 모두 구현하라는 뜻이 아니다. 네트워크 명령 재전송이나 지속형 외부 transport가 필요해질 때 그 경계에 맞게 추가한다. [P02·P03, TM-03·04]

적용 설정 화면에는 요청 모델, CLI 버전의 관측 시점, 입력 전달 방식, 권한·마운트 profile 식별자, auth/transport/context/permission 관측 상태, 실행 허가·거절의 고정 코드를 표시하는 것이 유용하다. 환경변수 값, 인증 파일 내용, 사용자 경로 전체, 질문 본문을 일반 진단 로그에 넣지 않는다. 내부 검증용 manifest와 공개용 projection도 구분한다. 필요한 설정이 누락되면 추측으로 실행하지 않는 기존 원칙을 유지한다. [P01·P06, TM-09]

## 4. C/D — 필요한 상태만 보고 느린 화면은 분리한다

먼저 현재 polling을 유지하면서 목록과 선택 실행 상세를 나누는 비용을 측정한다. 상태가 바뀌지 않았을 때 같은 DOM을 전부 다시 만들지 않는 방식, 완료 실행의 상세를 필요할 때 가져오는 방식, 현재 선택과 입력을 보존하는 방식이 후보이다. **실제 데이터량·성능 저하를 아직 측정하지 않았으므로, 어느 방법이 더 빠르다는 수치는 제시하지 않는다.** [P05]

추후 사건 push가 필요하면 다음 계약을 먼저 정한다.

- **공개용 상태와 원장 사건을 분리한다.** 봉인된 진단·길이·토큰·빈도를 새 경로로 노출하지 않는다. 숨긴 사건을 건너뛴 seq의 간격까지 보여 줄지는 별도 검토한다.
- **snapshot과 cursor를 일관되게 발급한다.** snapshot 직후 발생한 변화를 빠뜨리지 않으며, 연결 중복/끊김 뒤에는 gap을 인지하고 재조회한다. raw journal을 브라우저가 재생해 자체 판정을 만들게 하지 않는다.
- **느린 화면의 큐만 제한한다.** 화면용 갱신은 최신 안전 상태로 합치거나 재동기화를 요구할 수 있다. CLI stdout/stderr 수집과 최종 결과·예산 사건은 화면 소비 속도 때문에 멈추거나 사라져서는 안 된다.
- **기존 인증을 약화하지 않는다.** 브라우저 EventSource의 편의 때문에 Bearer token을 query string에 넣지 않는다. 인증 헤더를 지원하는 fetch 기반 스트림 또는 검토된 다른 인증 방식을 선택한다. Origin·권한·재연결 처리도 같은 API 경계에서 검증한다.

이 항목들은 제안이며 현재 SSE endpoint가 있거나 보안 검증을 마쳤다는 뜻이 아니다. tmux control mode의 구독/흐름 제어에서 역할 분리만 참고하고 protocol 문법을 복사하지 않는다. [T03·T11, P03–P07]

화면 기능은 '사용자 답 대기', '종료 미확인', '구성 축소 승인 대기', '최종 실패'로 이동하는 탐색부터다. 공개 전 비교 pane에는 답을 아예 넘기지 않는다. 공개 후 두 답을 나란히 고정하는 기능은 가능하지만, 패널 고정이나 닫기가 실행 명단·정족수·예산을 바꾸지 않도록 한다. Q4의 최종 첫 화면 결정은 별도로 남긴다. [P01·P05·P07]

## 5. E/F — tmux를 직접 쓰기 전에 확인할 것

### E: 개발자의 전용 controller 터미널

이것은 선택적인 운영 편의이며 프로젝트 runtime 의존성 추가가 아니다. 먼저 tmux가 실제로 필요한지, 이미 사용하는 실행 도구로 terminal 분리 요구가 충족되는지를 확인한다.

사용한다면 설치된 binary 버전과 실제 붙는 server 버전을 각각 확인하고, 기본 socket 대신 식별 가능한 전용 socket을 사용한다. 기존 개인 tmux server를 재사용하면서 새 client의 환경만 깨끗하면 충분하다고 가정하지 않는다. config의 hook·외부 명령·환경 상속·clipboard와 debug 로그 정책을 검토한다. controller가 출력한 fragment token과 질문이 scrollback에 남을 수 있으므로 전용 server의 접근을 controller 접근과 같은 신뢰 수준으로 둔다. [T04·T10·T12·T13]

운영 시험에서는 **자기가 만든 전용 server만** 생성·종료한다. 다른 사용 작업이 있는 기본 server에 `kill-server`를 보내거나, hook에 자동 respawn을 추가하지 않는다. 창 detach, tmux server 종료, controller 종료, WSL 종료를 서로 다른 사건으로 확인한다. 재부팅 뒤 복구와 모델 내부 상태 복원은 별도 문제다.

이번 문서는 설치 명령이나 사용자 환경 변경을 수행하지 않았다. 실제 WSL에서의 승인은 별도이며, 합성 가짜 CLI와 임시 원장으로 먼저 확인한다.

### F: 실제 PTY transport가 필요한 경우

기존 `native exec + pipe`가 충족하지 못하는 구체적인 CLI 요구가 확인될 때만 시작한다. 성공 JSON이 있는 CLI에 tmux를 넣는 것 자체는 필요성의 근거가 아니다.

외부 server socket에 작업을 위탁하는 topology는 사용하지 않는다. 실험 후보는 tmux server까지 같은 attempt 격리에 넣은 구성이다. 이 경우에도 PTY의 echo/줄바꿈/EOF, terminal 제어 데이터, stderr의 독립 채널, 원문 보존, 취소·자손 종료, server restart와 pane 재사용의 binding을 새로 검증한다. 프로세스 실패를 화면 문자열로 추측하지 않는다. [T03·T10–T14, P06]

우리 컨테이너나 사용자 PC에서 이런 구성을 실행한 것은 아니다. 현재 권고는 **보류**이며, 새 backend나 parser를 이번 PR에 추가하지 않는다.

| TP18 | 개발 문서의 기능을 안정 버전에 요청 | 지원 미확인을 성공으로 처리하지 않고 버전/기능 거절을 명시. 3.8 Events를 3.7c 기본 기능으로 요구하지 않음 | E/F |

기존 A1 시험을 이 표로 대체하지 않는다. 테스트 파일을 작성할 때는 실제 구현 변경에 해당하는 항목만 추가하고, 나머지는 계획으로 남긴다. 가짜 CLI·합성 표식·임시 원장·자기가 생성한 프로세스만 사용한다. 토큰·인증 원문·실제 질문을 시험 산출물에 넣지 않는다.

## 7. 개선을 주장하기 전에 측정할 것

UI 개선은 조회 빈도, 응답 바이트, controller/브라우저 CPU·메모리, 선택 실행의 올바른 상태가 다시 보이기까지의 시간을 전후 비교한다. 비교할 run 수·결과 크기·네트워크 지연은 먼저 고정한다. '상태 표시를 위해 추가 모델 호출이 없는가'와 '재접속 때문에 invocation이 늘지 않는가'는 별도로 기록한다.

운영 tmux는 terminal detach 뒤 controller 생존과 재접속만 먼저 확인한다. controller/WSL/호스트 종료 뒤의 복구는 다른 시험 결과로 분리한다. tmux로 토큰이 줄었다거나 모델 품질이 올랐다고 결론 내리지 않는다. 그런 효과는 이 조사에서 측정하지 않았다.

이 작업의 완료 기준은 기능 수가 아니라 **기존 실행 계약을 바꾸지 않고 필요한 사용성을 얻는가**다. 측정 이득이 없거나 PTY/추가 server 때문에 경계가 복잡해지면 아이디어만 남기고 tmux 통합은 하지 않는다.
