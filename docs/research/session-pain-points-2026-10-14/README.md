# 여러 AI 세션으로 일할 때의 불편과 이 앱의 해법 (2026-10-14)

사용자는 다른 프로젝트에서 Claude 데스크톱 세션 여러 개, Codex, 웹의 Gemini·ChatGPT, 이 PC의 GPU와 빌린 클라우드 GPU를 함께 돌리며 일한다. 그 작업에서 되풀이된 불편을 모아 달라고 했고(2026-10-14), 그 기록을 이 앱에 어떻게 적용하면 편해질지 생각해 달라고 했다. 이 문서는 그 답이다. **구현 기록이 아니다.** 앱 코드와 참여자 계획은 바꾸지 않았다.

- 작성: claude 세션, 주 PC `DESKTOP-T0UDE01`의 Windows 쪽(Claude 데스크톱 앱). 모델 호출 없음. WSL과 CLI는 이번에 보지 않았다.
- 입력: 다른 프로젝트에 있는 불편 기록(2026-10-14 작성, 문제 P1–P22와 상황판 요구). 그 기록에는 사용자의 대화 원문과 그 프로젝트의 작업 내용이 들어 있어 **공개 저장소인 이곳에는 옮기지 않았다.** 여기서는 문제를 일반화해 적고 번호만 맞췄다. 그 기록에서 옮긴 횟수·시간은 출처 등급으로 "전달"이다.
- 참고: 이 저장소에 이미 모아 둔 외부 하네스 조사(§5), 이번에 직접 읽은 Claude Code 공식 문서와 외부 도구(§6), [캐시 유지 조사](CACHE.md).

## 결론 먼저

1. **불편은 세 가지 구조에서 나왔다.** (가) 상태가 대화와 사람이 쓰는 문서에만 있다. (나) 세션 사이 연락이 사람 입력에 묶인 채팅 통로를 지난다. (다) 시계와 자원을 맡은 주인이 없어, 코디네이터 AI 세션 하나가 받기·전달·검증·일정을 다 한다.
2. **Claude Code에 이미 들어온 공식 기능으로 일부를 먼저 풀 수 있다(0단계).** 세션 사이 메시지(쉬는 세션은 새 차례로 깨운다)와 "끝나면 한 번 알려 달라"는 구독, 백그라운드 세션과 그 상태 목록(JSON, "권한 대기 중"까지 나온다), 사용량 한도가 풀리면 하던 일을 자동으로 이어 하기, 상태 줄의 5시간·주간 사용량 %다. 세션 간 메시지는 [2026-09-25 조사](../multi-ai-workflow-2026-09-25/README.md)에 인계 수단으로만 올라 있었고, 나머지는 이 저장소의 조사에 없던 것들이다. 이 앱을 고치기 전에 다른 프로젝트에서 먼저 시험해 볼 만하다(§4, §6.1).
3. **이 앱은 그것들을 원장으로 묶는 자리다.** 이 앱은 이미 반대 방향으로 만들어져 있다: 원장(SQLite)이 정본이고 화면은 그 계산 결과다. 앱이 공식 CLI를 직접 불러 사람 입력 횟수에 묶이지 않는다. 상태를 보여 주려고 모델을 부르지 않고, 모르면 "모름"이라고 쓴다. 빠진 것은 이 앱 밖의 일을 보는 눈, 결정·승인·메시지·자원을 담을 기록, 그리고 시계다. 그래서 ① 읽기만 하는 상황판(결정 없이 시작 가능) → ② 결정·승인·메시지·자원 기록과 주기 대조(사용자 결정 A) → ③ 앱이 일꾼 세션을 직접 부르고 미리 승인한 범위 안에서 이어 돌리는 부재 모드(사용자 결정 B) 순서로 넓히기를 권한다. 격리 실행(봉인·정족수)은 어느 단계에서도 건드리지 않는다.
4. **코디네이터 AI가 하던 일의 대부분은 코드가 할 일이다.** 대조, 자원의 빈 시간 계산, 시각 기록, 전달 확인은 규칙대로 계산하면 된다. 모델은 판단과 결정 요청 문안에만 쓴다. 이렇게 나누면 세션 간 메시지 한도(P1)와 코디네이터 과부하(P18)가 함께 줄어든다.
5. **캐시 유지 도구는 설치하지 않기를 권한다.** 만든 사람들 스스로 구독(Pro/Max)에서는 쓰지 말라고 적었고, 공식 문서도 쉬는 세션에 예약 작업이나 메시지가 들어올 때마다 대화 전체를 보낸다고 적었다. 구독 사용량 안에서 메인 대화는 이미 1시간 캐시를 쓰고, 오래 쉰 큰 세션은 요약으로 다시 여는 기능이 있다. 자세한 것은 [캐시 유지 조사](CACHE.md).
6. **이 앱에 대한 발견 하나.** Claude Code는 `-p` 실행에도 세션 간 메시지를 받는 통로를 연다(공식 문서). 이 앱의 Claude 참여자는 도구가 없어 밖으로 보내지는 못하지만, 격리 밖의 다른 세션이 실행 중인 참여자에게 글을 넣을 수 있는지는 확인하지 않았다(§6.3). 인계 4절의 참여자 표면에 올렸다.

## 2. 문제별 해법

"단계"는 0(Claude Code 기능을 그대로 쓰기, 이 앱 밖), ①(상황판), ②(기록·대조), ③(일꾼 세션·부재 모드)다. "있는 것"은 이 앱에 지금 구현된 것, "가져올 것"은 이 저장소의 조사(§5)나 이번에 읽은 출처(§6)에서 온 해법이다. 답을 못 찾은 부분은 §8에 모았다.

## 3. 상황판 (1단계)

### 3.1 원칙

- 읽기만 한다. 실행·승인은 따로 버튼과 기록으로 한다(2단계).
- 칸마다 출처와 갱신 시각을 붙인다. 볼 수 없는 값은 "모름"이다. "없음"·"놀고 있음"·"끝남"으로 바꿔 적지 않는다 — 이 앱의 "종료 미확정은 성공이 아니다"와 같은 원칙이다.
- 맨 위에는 사용자가 할 일을 둔다(P8 양식).
- 상태를 보여 주려고 모델을 부르지 않는다(인계 2절 5).
- 대화 기록은 본문을 읽지 않고 시각·크기·사용량 칸만 센다. 인증 파일은 열지 않는다. 읽을 경로는 설정 파일 목록으로 고정한다(결정 C).

### 3.3 데이터 모양과 이 앱 안의 자리

- 관측 한 줄은 `source`(어디서), `subject`(무엇), `state`(시작 요청·동작 확인·성공·실패·모름), `observed_at`, `fresh_until`(이 시각이 지나면 "오래됨"), `evidence`(파일 경로·명령·URL), `detail`이다.
- 수집기는 출처마다 하나다. 출처가 없거나 느리거나 형식이 깨지면 "모름"과 이유를 낸다. 한 수집기의 실패가 다른 칸을 막지 않는다.
- 자리는 새 읽기 모듈(예: `app/observe/`)과 화면 탭 하나다. 기존 토큰 API, 공개 조회(PublicQueries), island-ui 부품을 다시 쓴다. **1단계에서는 원장 schema를 바꾸지 않는다.** 관측은 화면이 부를 때 모으고 메모리에만 둔다 — 지금의 Codex 한도 조회와 같은 방식이다. 기록이 필요해지는 2단계에서 schema를 올린다. 창을 닫은 뒤에도 모으려면 OP02(지속 실행)가 필요하다.
- 이 PC의 특징: 앱 서버는 WSL에서, 다른 작업과 데스크톱 세션은 Windows에서 돈다. WSL에서 `/mnt/c`의 파일과 `nvidia-smi`는 읽힐 가능성이 높지만, Windows에서 `127.0.0.1`로 열린 HTTP 서버는 WSL 기본 네트워크(NAT)에서 바로 닿지 않을 수 있다 — 확인 필요. Claude Code 공식 문서도 "WSL 2 안의 세션과 Windows 네이티브 세션은 서로 메시지를 보낼 수 없다"고 적었다. 그래서 Windows 쪽 시작 스크립트(`app\start.ps1`)가 Windows용 수집기를 함께 띄우는 안이 유력하다.
- 보는 곳은 두 군데다. 이 앱의 창(전체 표)과, 사용자가 늘 보는 Claude 화면이다. Claude Code의 상태 줄이나 mod(화면에 띠·패널을 붙이는 확장)로 요약 한 줄("정하실 것 2 · 미전달 1 · GPU 빈 시간 40분 · Claude 주 41%")을 띄우면 묻지 않아도 보인다. 그 줄은 이 앱이 만든 요약 파일을 읽기만 한다. 데스크톱 앱에서 상태 줄·mod가 그대로 도는지는 확인하지 않았다.

### 3.4 첫 조각의 완료 조건

- 수집기마다 출처 없음·시간 초과·형식 깨짐에서 "모름"과 이유를 내는 시험.
- 대화 기록 본문과 인증 파일을 읽지 않는다는 시험(읽는 경로 목록 고정).
- 모델 호출 없음, 원장 쓰기 없음.
- 실제 PC에서 한 번 열어 각 칸의 출처와 갱신 시각이 맞는지 관측해 기록한다.

시계도 따로 필요하다. 다른 프로젝트의 외부 검토는 "규칙 문장은 타이머를 만들지 않는다"고 지적했다. 지금 쓸 수 있는 실제 시계는 Claude Code의 `/loop`(세션이 열려 있고 쉬고 있을 때만), 데스크톱 앱의 예약 작업(기기가 켜져 있으면), 클라우드 루틴이다. 다만 공식 문서대로 **예약 작업은 돌 때마다 대화 전체를 보낸다.** 그래서 이 앱 쪽 시계는 모델 없이 대조만 하는 코드로 두고(2단계), 해석이 필요할 때만 상한 있는 모델 호출을 붙인다. 감시·반복·예약·작업판이 서로 다른 기능이라는 구분은 [Hermes 기능 목록](../feature-catalog-2026-10-04/HERMES.md)의 H36 설명을 따른다.

**다른 프로젝트에서 바로 해 볼 수 있는 것(0단계).** 그 프로젝트의 설정을 바꾸는 일이라 그 프로젝트의 세션에서 사용자와 함께 정한다.

1. 코디네이터가 일꾼 세션에 일을 맡길 때 `notify_when_idle`로 "끝나면 알려 달라"를 같이 건다(같은 기기, 12시간 안). 끝난 결과가 묻히는 문제(P2)를 사람 규칙 없이 줄인다.
2. 데스크톱 앱의 보내기 도구 대신 `SendMessage`로 보내 보고, "10번 뒤 막힘"이 같은지 본다. 막히면 어느 장치가 막는지 오류 문구를 남긴다.
3. 받는 세션에서 글이 사라지는지 본다. 공식 규칙으로는 **권한을 건너뛰는 세션과 묻는 세션이 섞이면** 기본값이 글을 보류하고, 데스크톱 앱은 승인 창을 못 띄워 5분 뒤 버린다. 세션들의 권한 모드를 한 부류로 맞추거나 받는 쪽에 `crossSessionInbound: "accept"`를 정한다. 모두 받기로 두면 자기 세션끼리의 글이 보류 없이 들어간다 — 대신 쉬는 세션마다 새 차례가 열려 사용량이 든다.
4. 오래 걸리는 일꾼은 백그라운드 세션으로 띄우고, `claude agents --json`으로 "권한 대기 중"인 세션을 찾는다.

[2026-09-25 조사](../multi-ai-workflow-2026-09-25/README.md) §8은 agent teams를 "실험 기능이고 Claude만 쓰며 대화형에서만 돈다"는 이유로 맞지 않는다고 봤다. 지금 공식 문서도 대화형에서만 팀원이 생긴다고 적어 그 판단은 그대로다. 그 조사는 세션 간 메시지를 인계 수단으로만 비교했다(대화 기록이 넘어가지 않음). 이번 불편(연락, 끝난 결과 전달, 기다리는 세션 찾기)에는 그 기능과 백그라운드 세션이 직접 답이 된다.

- **판단:** 제3자 도구를 들이기보다 공식 기능(세션 간 메시지, 상태 줄 `rate_limits`를 파일로 남기는 작은 스크립트, 백그라운드 세션 목록)과 이 앱의 상황판으로 가는 쪽이 규칙과 덜 부딪힌다.

### 6.3 이 앱의 참여자와 세션 간 메시지

공식 문서는 세션 간 메시지가 2.1.224부터 "켤 것 없이 켜져 있다"고, `claude -p` 세션도 대화형처럼 수신 소켓을 연다고(bare 모드만 예외) 적었다. 이 앱의 Claude 참여자는 `-p`에 `--restricted --safe-mode`, `--permission-mode dontAsk`, `--tools ""` 또는 `Read`로 돈다([adapters](../../../core/adapters.py)).

- **밖으로 보내기:** 참여자에게는 도구가 없어 `SendMessage`를 부를 수 없다. 봉인한 초안을 다른 세션에 보낼 길은 보이지 않는다.
- **안으로 받기:** 확인하지 않았다. `dontAsk`는 "묻는 쪽" 부류라, 받는 쪽 설정이 없으면 묻는 부류의 세션이 보낸 글은 그대로 전달된다(권한을 건너뛰는 세션이 보낸 글은 보류됐다가 5분 뒤 버려진다). `--restricted`는 관리 설정과 `--settings`만 읽으므로 사용자 설정에 거절을 적어도 참여자에게는 닿지 않는다.
- **격리와의 관계:** [격리](../../../core/isolation.py)는 HOME과 /tmp를 빈 tmpfs로 두고 /run을 연결하지 않는다. 그러나 그 CLI 자신의 설정·인증 폴더는 쓰기로 연결한다. 소켓이나 세션 목록이 그 폴더 아래에 생기면 격리 밖의 세션이 실행 중인 참여자를 찾아 글을 넣을 수 있다. 문서는 소켓을 둘 수 없는 폴더일 때 `/tmp/cc-socks-<uid>`로 옮긴다고만 적었고, 기본 위치와 세션 목록이 어디에 생기는지는 찾지 못했다.
- **할 일:** 다음 재관측(인계 4절 2) 때 격리 안의 참여자가 소켓을 여는지, 그 경로가 격리 밖에서 닿는지 본다. 닿으면 `--settings`로 `crossSessionInbound: "refuse"`를 주는 안을 시험한다. 공식 문서대로라면 이때도 소켓은 열린 채 글만 버린다. 참여자 계획이 바뀌므로 그 계획으로 다시 관측한다. 파일 하나·설정 하나로 문맥 독립을 증명했다고 쓰지 않는다.

## 8. 아직 답을 못 찾은 것

- 관측한 "사람 입력 뒤 약 10번에서 막힘"이 어느 장치의 제한인지. Claude Code 문서에는 몰아 보내기 거절과 반복 제한만 있고 이 규칙은 없다. 데스크톱 앱 쪽 제한일 수 있다(§4의 0단계 2번).
- 데스크톱 앱 세션이 승인 대기 중인지 밖에서 알 방법. 백그라운드 세션은 `waitingFor`로 알 수 있지만, 데스크톱 앱 세션에 같은 목록이 있는지는 찾지 못했다.
- 데스크톱 앱에서 상태 줄 명령과 mod가 도는지. 돌지 않으면 Claude 한도 %는 터미널 세션이나 실제 호출의 보고로만 읽는다.
- 같은 세션을 데스크톱 앱과 CLI(`--resume`)가 번갈아 써도 안전한지.
- GPU를 사람이 먼저 쓰는 규칙과 기계가 빈 시간을 채우는 규칙이 부딪힐 때의 양보 순서.
- CPU 온도를 읽는 도구(Windows).
- 웹 AI(Gemini·ChatGPT)의 답을 화면 조작 없이 모으는 공식 통로.
- 대화 속에서 정한 것을 누가 결정 기록으로 옮기나. 모델이 제안하고 사람이 확인하는 방식이면, 그 확인이 다시 사람의 일(P6)이 된다.

## 9. 읽은 범위와 확인하지 않은 것

- **비공개 입력:** 다른 프로젝트의 불편 기록 전체(2026-10-14). 원문 인용과 그 프로젝트의 작업 내용은 옮기지 않았다.
- **이 저장소:** [인계](../../../NEXT-SESSION.md), [기능 안내](../../FEATURES.md), [참고 지도](../../REFERENCE-MAP.md), [현재 구조](../../../app/ARCHITECTURE.md), [협업 규칙](../../COLLABORATION.md), 운영 분석의 README·ADOPTION, 기능 후보 목록 README, 여러 AI 작업 조사 §1·§8, mixdog·Concord 검토, `app/account_quota.py`의 머리말, `core/adapters.py`의 Claude 참여자 명령 조립.
- **공식 문서(2026-10-14 읽음):** 위 §6.1 표의 링크와 [캐시 유지 조사](CACHE.md)의 출처. 긴 페이지는 필요한 절만 읽었다. 공식 문서 조사를 처음 훑은 것은 조사 에이전트였고, 이 문서에 쓴 내용은 작성 세션이 같은 페이지에서 다시 확인했다.
- **외부 도구:** §6.2의 저장소들. 조사 에이전트가 README·문서·일부 코드를 읽었고, 작성 세션이 라이선스·날짜와 표에 쓴 주장을 다시 확인했다. 표에 넣지 않은 비슷한 도구(dot-agent-deck 등)는 조사 에이전트만 읽었다.
- **확인하지 않은 것:** 어떤 도구도 설치·실행하지 않았다. WSL에서 Windows HTTP 서버에 닿는지, `nvidia-smi`가 WSL에서 도는지, 참여자의 수신 소켓, Windows 쪽 Claude Code 판을 보지 않았다. 다른 프로젝트의 횟수·시간은 그 기록을 옮긴 것이다(전달).
