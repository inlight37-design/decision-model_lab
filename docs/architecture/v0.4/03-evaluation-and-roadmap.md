# 평가 설계·사용 예시·구현 순서

[개요](README.md) · [아키텍처](02-frontier-architecture.md) · [출처](sources.json).

**실험 계획이며 결과 보고서가 아니다.** 현재 사용자 구독으로 수행한 모델 비교, 품질 향상률, 사용량 절감률은 없다. 기존 v0.2 합성 계약은 그대로 유지한다.

## 1. 반드시 답해야 할 질문

상급 모델을 세 개 호출해서 좋아졌다면, 그 이유가 다른 회사의 모델을 섞었기 때문인지, 단순히 세 배 가까운 추론 기회를 주었기 때문인지, 더 좋은 검색/검증 도구를 주었기 때문인지 구분해야 한다. 최종 합성이 원래 맞던 답변을 잃어버리는지도 봐야 한다. 근거 F07–F12/F20, 결정 D17.

제품으로 유용한지와 모델 결합 자체의 인과 효과도 구분한다. Native Codex·Claude Code·Antigravity를 비교하면 모델뿐 아니라 system prompt·도구·memory·cache·권한·숨은 내부 호출이 함께 달라진다. 이것은 **실용적인 end-to-end 비교**이며 동일 harness의 모델-only 비교라고 부르지 않는다.

## 2. 비교군: 토론 효과와 이종 모델 효과를 분리

| ID | 조건 | 확인할 질문 |
|---|---|---|
| Q0 | 현재 사용자의 상급 native 단독 | 현재 방식보다 실제로 도움이 되는가 |
| Q1 | 같은 상급 모델 단독 + 늘어난 추론/수정 예산 | 단순 추가 compute보다 나은가 |
| Q2 | 같은 상급 모델의 독립 3회 생성 + 같은 합성 절차 | 모델 다양성 없이도 얻는 ensemble 이득은 얼마인가 |
| Q3 | 세 회사 상급 모델 독립 생성 + 합성, 토론 없음 | 이종 구성의 후보 다양성이 이득인가 |
| Q4 | Q3 + 한 라운드 교차검토 | 토론이 독립 답변 비교보다 실제로 이득인가 |
| Q5 | A 생성 → B 검토; 별도 B 생성 → A 검토 | 역할 방향과 두 모델만의 구성이 더 적합한가 |
| Q6 | 유망한 조건 + 명시적 claim/evidence gate | 근거 확인이 추가 비용 대비 오류를 줄이는가 |
| Q7 | 독립 답변 + 주장 대조표만 제공, **최종 합성 없음** | 합성이 이득인가 손실인가. 사람이 원문을 직접 보면 소수 정답을 더 잘 찾는가 |

Q7은 F26 이후 추가했다. 합성 단계를 **없앤** 조건이 없으면 합성 손실을 관측할 기준선이 없다. 합성 호출이 실패하거나 한도가 부족할 때도 이미 모인 원문과 반례를 정형 보고서로 낼 수 있어야 하며, 그것을 완성된 합성 결과로 표시하지 않는다.

각 조건에 가능한 한 같은 질문·제약·좋은 평가 기준·source pack·도구를 제공한다. 교차검토 조건에만 더 정교한 지시문을 넣어 단순 모델을 불리하게 만들지 않는다. 전체 조합을 한꺼번에 실행하지 않고 Q0/Q1과 두 모델 Q5 또는 Q3의 소규모 변형부터 시작한다.

동일한 **달러·token·지연·구독 한도**를 동시에 완벽하게 맞출 수 있다고 가정하지 않는다. 공급자별 reasoning token 포함 관계나 비공개 내부 호출도 다를 수 있다. 고정된 외부 호출/시간 한도의 비교와 관측된 자원에 대한 품질–비용 곡선을 함께 본다. 모델별 effort 명칭이 같다는 이유로 같은 compute라고 부르지 않는다. F03/F15, 기존 v0.3 D07/D08.

## 3. 작업군과 정답의 의미

| 작업군 | 확인 가능한 결과 | 과장하면 안 되는 것 |
|---|---|---|
| Bounded code patch | frozen base/candidate, 숨긴 회귀 테스트, 재현 명령, diff scope | 공개 테스트 통과가 전체 코드 정확성 증명 |
| 수학·알고리즘 | 조건·반례·독립 계산·가능한 proof checker | 몇 개 숫자 대입을 일반 증명으로 취급 |
| 최신 자료 조사 | 해당 날짜의 1차 원문, claim별 지지 여부, 누락·인용 정확성 | URL 존재를 인용 내용 확인으로 취급 |
| 아키텍처 선택 | 사전에 정한 제약·대안·리스크·검증 가능한 작은 실험 | 선호가 다른 판단을 하나의 객관 정답으로 채점 |
| 설계/보안 리뷰 | 실제 재현된 결함, 거짓 경보, 발견 못 한 결함 | reviewer의 자신감이나 비판 수를 품질로 집계 |

민감하거나 외부 부작용이 있는 실행은 이 초기 연구 범위 밖에 둔다. 실제 사용자 데이터를 쓰는 경우 provider별 전송 허용·비식별화·저장 정책을 먼저 확인한다. 공개 자료와 합성 문제로 배선을 검증하는 것이 먼저다.

## 4. 점수표는 합의율보다 오류와 근거 중심

| 지표 | 정의/기록 방법 |
|---|---|
| 최종 수용률 | 사전에 고정한 작업별 acceptance 통과율. 실패·timeout·quorum 부족을 분모에서 빼지 않음 |
| Oracle candidate coverage | 독립 후보 중 하나라도 정답인 비율. 최종 산출물 성능이 아니라 후보 선택의 상한 참고치 |
| Synthesis loss | 독립 후보에는 맞는 답이 있는데 최종 답은 틀린 경우. 후보→합성 손실을 직접 집계 |
| **Extraction loss** | 초안 원문에는 있었으나 **claim으로 등록되지 않은** 중요한 조건·반례의 수. 원장 안의 처리율과 별개로 측정한다 |
| Correct→wrong / wrong→correct | 토론 전후 같은 참여자의 판정 전이. 개선과 오염을 따로 보고 |
| 근거 적합성 | 주장–출처가 실제로 대응하는지, 현재 버전인지, 반례를 누락했는지 |
| Unsupported additions | 합성에서 새로 생긴 확인되지 않은 핵심 주장 수/비율 |
| Review utility | 검증된 결함 발견, 거짓 경보, 불필요한 수정, 놓친 결함 |
| Disagreement retention | 해결하지 못한 중요한 소수 반례/조건 차이를 최종 결과가 보존했는지 |
| 비용과 시간 | 전체 cash, provider별 quota, token, wall time, 사람 검토/수정 시간, 실패 비용 |

정답이 없는 설계 task에 oracle coverage/correct→wrong를 억지로 계산하지 않는다. 대신 고정 rubric으로 조건 충족·반례·대안 비교를 평가한다. 가능하면 모델/조건을 가린 사람 검토와 독립 평가자를 사용하며, 사람 평가자 간 불일치도 보존한다. LLM judge만 있다면 결과를 그 judge에 의존하는 proxy로 표시하고 동일 계열 자기 선호와 위치 편향을 별도 검사한다. F20.

자신감 숫자를 수집하더라도 먼저 hold-out label에 대해 calibration을 평가한다. calibration이 없으면 가중 투표·자동 승인 기준으로 쓰지 않는다. Agreement는 진단 항목일 수 있으나 accuracy의 대체물이 아니다.

### 주관적 채점과 코드 리뷰의 다른 검증 기준

F22의 strict/lenient 채점 결과를 근거로, 주관적 rubric 평가는 **중립 단독 judge**와 **같은 중립 rubric의 다중 judge**부터 비교한다. 비판적 역할을 넣으면 역할 교환 조건도 두고 사람 reference와의 오차·순위 일치도를 본다. 합의율 상승만으로 채택하지 않는다. 초기 독립 초안 보존과 이후 채점 중 점수 공개/가림은 서로 다른 변수다.

코드 리뷰에는 F24를 참고해 각 finding에 `artifact_digest`, 코드 위치, 재현 조건, 관측 증거, 작업 범위 관련성을 붙이는 실험을 추가한다. 코드로 확인한 반론과 아직 확인하지 못한 우려를 구분하고, 우려는 검사할 가설로 남긴다. 검토 중 diff를 고정하고 범위 밖 우려만으로 writer가 수정을 늘리지 않게 한다. 구체적 반증 검토를 금지한다는 뜻은 아니다. 기존 0/1 round 상한을 유지하며, reviewer 수보다 검증된 결함·거짓 경보·불필요 수정과 비용을 비교한다. 이것은 향후 실험 지침이며 현재 checker가 이 필드를 검사하는 것은 아니다.

## 5. 공정성과 통계

첫 20–30개 과제는 배선·계측·실패 분류를 확인하기 위한 pilot 제안이다. 통계적으로 충분한 표본이라고 주장하지 않는다. 쉬운/어려운 문제, 검증 가능한/설계 판단 문제를 구분하고 일부를 반복해 실행 변동을 본다. 평가 세트로 프롬프트를 계속 조정하지 않고 tuning과 hold-out을 나눈다.

같은 문제의 조건 간 paired 차이를 사용하고 실행 순서를 섞는다. 반복 실행들을 독립 문제인 것처럼 부풀리지 않는다. 신뢰구간을 계산할 때 문제 단위 cluster/bootstrap 등 의존성을 반영하며, 이후 표본 크기는 관측 분산과 검출하려는 개선 폭에 근거해 정한다. 작은 pilot에서 p-value 하나로 채택 여부를 결정하지 않는다.

F15의 infrastructure 보고는 특정 실험에서 환경 차이만으로 6 percentage-point 차이가 생겼다고 설명한다. 따라서 CPU/RAM의 보장 할당량과 hard kill limit을 각각 기록하고, 네트워크·timeout·tool 권한·repo snapshot·cache warm/cold·실행 순서도 manifest에 기록한다. 서비스 장애와 quota 제한은 모델 추론 실패와 구분하되 사용자 관점 가용성 비용에서는 빠뜨리지 않는다.

권장 ablation은 서로 다른 vendor(Q2↔Q3), 토론(Q3↔Q4), 동일/다른 합성자, 이름 공개/익명화, 답변 제시 순서, 자기 평가 제외, 공통/독립 source 검색, 풀이 방법 다양성이다. 여러 요인을 동시에 바꿨다면 그 한계를 결과에 적는다.

F23을 참고해 실험 manifest에 참여자/역할·모델/effort, 통신 연결과 순서, 교환하는 내용, history/memory 접근, round/중단 조건, 최종 결정 주체와 합성 규칙을 명시한다. 서로 다른 프로토콜을 모두 같은 “debate” 조건으로 묶지 않는다. rubric·prompt를 결과 확인 후 바꾸면 새 revision으로 남기고 새 hold-out에서 평가한다. 같은 세트에서 조정한 뒤의 점수는 탐색 결과로 표시한다.

## 6. 회계와 성능 판정

회계 원칙은 [v0.3 비용 설계](../v0.3/04-decisions-and-evaluation.md)를 계승한다. 부모 계획·worker·reviewer·합성자·형식 복구·실패·도구·사람 수정까지 범위를 표시한다. 누계 session usage와 turn delta를 섞어 두 번 더하지 않는다. 관측 불가 quota는 null/unknown이며 공짜가 아니다.

월 구독료, 실제 추가 API/credit 청구, API 등가 추정치를 분리한다. '추가 현금 0'이어도 구독 한도와 지연이 증가할 수 있다. 반대로 총지출이 늘어도 수용 결과당 비용이 줄 수 있다. 품질이 다른 결과를 단순 건당 token으로 비교하지 않는다. 부분 계측이면 전체 절감률을 발표하지 않는다.

채택 기준은 특정 개선율을 미리 만들어 쓰는 대신 작업군별로 정한다. 예를 들어 복잡한 설계 검토에서는 검증된 중요 오류 감소가 추가 시간보다 가치 있는지, 반복 코드 작업에서는 단독 기준선과 동등한 수용률에서 quota/사람 수정 시간이 줄었는지를 본다. 결과는 quality–cash–quota–latency의 trade-off로 제시한다. 상급 모델 협업이 항상 경제적이거나 항상 더 정확하다는 보장은 없다.

### 모델별 캐시 회계 보강

[E28 공식 API 문서](https://developers.openai.com/api/docs/guides/prompt-caching)를 기준으로 모델/version, 가격 확인일, ordinary input·cache read·cache write를 나눈다. **2026-09-22의 GPT-5.6+ API 예시**는 write 1.25배·read 0.1배다. 같은 prefix를 한 번 쓰고 한 번 완전히 재사용하면 일반 input 비용 단위로 1.35, 두 번 비캐시 처리하면 2다. 출력·도구·추가 요청 비용을 제외한 설명이며 구독 quota 공식이 아니다. 이 배수를 모든 provider나 예전 모델에 공통 적용하지 않는다.

cold start / 같은 모델 warm 재사용 / 모델 전환 / 만료 또는 prefix 변경을 따로 측정한다. 캐시를 채우기 위한 요청도 포함하며, 실제 `cached_tokens`와 지원되는 `cache_write_tokens`를 수집한다. 공급자별 합계에 read/write가 이미 포함되는지 확인해 중복 합산을 막는다. CLI가 이를 노출하지 않으면 unknown으로 두고 API 등가 추정과 실제 추가 청구를 분리한다. 캐시가 늘었어도 총비용·수용률·지연이 개선됐는지 확인한다.

## 7. 적용해 볼 구체적인 사용법 — 모두 제안 예시

아래는 이 저장소에서 실행한 사례가 아니라 첫 workload를 설계하기 위한 recipe다.

| 상황 | 권장 첫 실험 | 주고받을 핵심 artifact | 성공/중단 조건 |
|---|---|---|---|
| 이 프로젝트의 취소/재개 설계 | A/B가 독립 failure timeline 작성, C가 반례 비교 | 상태 전이, 프로세스 생존 조건, lease/재실행 시나리오 | 중복 실행·종료 불명 상황이 계약과 테스트에 반영됨 |
| race condition 수정 | A 원인/patch, B 독립 재현·코드 review | frozen diff, interleaving, 실패하는 테스트 | 기존/추가 테스트 통과, 수정 범위 준수. 재현 못 하면 미검증 표시 |
| 새 라이브러리 도입 | A/B 독립 공식 문서 조사 후 비교 | 버전·라이선스·권한·API/구독 경로 표 | 상충하는 문서의 날짜/버전 해결, 미확인은 남김 |
| 어려운 수학/알고리즘 | 서로 다른 방법의 독립 풀이 → 반례 검토 | 조건, 계산, 증명 요약, 반례/체커 | 결론보다 성립 조건 확인. 대입 시험만으로 일반 정답 선언 금지 |
| 설계 대안 A/B/C 선택 | 3인 independent → trade-off 합성 | 요구사항·가정·비교 기준·작은 prototype 제안 | 목표가 다르면 조건부 권고. 억지 단일 순위 금지 |
| 긴 기술 자료 교차검증 | 각 모델의 claim/citation ledger → 원문 확인 | 문서 revision, 해당 절/줄, 지지/반박 주장 | 원문을 확인한 주장과 추론을 분리 |
| 구현 품질 점검 | 설계 합의 후 한 writer, 다른 상급 reviewer | 계획, diff, test evidence, unresolved | 서로 같은 파일을 덮지 않음. reviewer 제안도 검증 후 반영 |
| 저비용 경로로 전환 가능성 | frontier 결과를 reference로 경제형 single과 비교 | 동일 task/acceptance/입력, 비용·실패 로그 | 저가가 충분한 task만 낮춤. frontier 협업 전체를 저가로 대체하지 않음 |

'여러 상급 모델에게 처음부터 똑같이 질문'하는 것은 Q3의 적절한 시작점이다. 이후에만 다른 접근법·critic 역할을 부여해 개선을 측정한다. 처음부터 수많은 페르소나, debate 라운드, router, 자동 학습을 동시에 넣지 않는다.

## 8. 구현 ticket과 완료 조건

### V04-01 — 런타임/구독 inventory (아직 미실시)

설치된 도구의 실제 version/help, native 로그인 방식, 사용할 수 있는 모델, 지원 permission/output/resume/cancel 기능을 비밀 값 없이 기록한다. agy와 Gemini CLI를 별도 adapter로 다룬다. API/extra-credit fallback, 부모 환경 변수의 funding 영향도 확인한다. 완료 조건은 timestamp가 있는 capability manifest와 실행 불가 이유의 명시다. 설치·설정 변경을 자동으로 함께 하지 않는다.

**구독 인증 경로의 정책 리스크도 함께 기록한다.** 이 저장소 전체가 '구독 우선, API 선택'을 전제하는데, 그 전제는 공급자가 구독 기반 비대화형 접근을 계속 허용한다는 가정에 의존한다. 이미 F18은 Claude SDK 구독 정책의 변경이 **공지되었다가 보류된** 상태를 기록하고 있다. 즉 이 경로는 이미 한 번 흔들렸다. 따라서 adapter별로 다음을 manifest에 남긴다: 구독 기반 비대화형 사용에 대한 공식 지원 문구와 그 문서의 revision, 과거 정책 변경·유예 이력, 경로가 닫혔을 때의 대안(유료 API 전환 / 해당 provider 제외 / 기능 축소)과 그 선택의 비용.

외부 조사 중 'Gemini CLI의 소비자 인증 경로가 2026-06-18자로 종료되어 Code Assist 또는 유료 API로만 이용 가능하다'는 서술을 검색 결과 수준에서 접했다. **원문을 확인하지 않았으므로 근거 원장에 등록하지 않았고 F/D 번호를 부여하지 않았다.** agy는 Gemini CLI와 다른 도구이므로 직접 적용되지도 않는다. 이것은 검증할 단서이지 확인된 사실이 아니며, V04-01에서 각 provider의 공식 문서로 직접 확인한다. 확인되면 그때 원장에 등록하고 필요하면 새 결정을 만든다.

**완료 조건에 '실행 전 차단'을 포함한다.** 필수 제한이 적용되지 않는 실행 경로는 프로세스를 시작한 뒤 경고하는 것으로 충분하지 않다. F26이 보여주듯 실행 부품은 구조화 경로가 거절되면 스스로 다른 실행 방식으로 내려갈 수 있고, 그 방식에서는 권한 인자가 아예 전달되지 않을 수 있다. 따라서 manifest에 다음을 기록한다: 각 adapter에서 권한·출력 형식·세션 인자가 **실제로 적용됐는지 실행 전에 확인할 수 있는 방법**, 확인할 수 없을 때의 차단 지점, 강등 경로의 존재 여부.

**blind를 얻으려다 구독을 벗어나지 않는지 확인한다.** F25는 문맥 오염을 줄이는 플래그가 동시에 OAuth 자격증명을 읽지 않게 만드는 사례다. 각 adapter에서 '깨끗한 초기 문맥'과 '구독 인증 유지'를 **동시에** 만족하는 조합이 존재하는지 확인하고, 없으면 그 provider에서 blind 초안의 한계를 명시한다. 둘 중 하나를 조용히 포기하지 않는다.

**격리 수단을 실제로 시험한다.** F27에 따라 worktree 분리만으로는 동료의 미공개 산출물 읽기를 막지 못한다. 논의자에게 무엇을 읽지 못하게 할 것인지 — 보호 대상 원본, 동료의 미공개 초안, 공유 저장소 상태 — 를 각각 정의하고, 답변에 나타나지 않았다는 사실이 아니라 **접근이 차단됐다는 관측**으로 판정한다.

### V04-02 — 오프라인 프로토콜 검사 (이번 뼈대 작업)

합성 기록에서 중복 참여자, quorum 부족, 초기 peer 노출, 과도한 round/call, 무승인 funding, dangling artifact/check 참조, 근거 없는 합의의 검증 승격, unresolved 누락을 잡는 최소 검사를 만든다. 정상·거절 fixture를 시험한다. 이것은 실제 sandbox/auth나 진실 판정의 구현이 아니다. [검증 범위](VALIDATION.md)를 따른다.

### V04-03 — 두 provider의 읽기 전용 independent pilot

V04-01과 권한 검사가 통과한 두 native 경로만 연결한다. 같은 입력의 독립 artifact를 수집하고 개별 결과와 수동/제한 합성을 비교한다. 처음부터 세 제품·장기 DB·MCP UI·Jev를 함께 연결하지 않는다. 완료 조건은 입력/출력 digest, 실제 두 참여자, 미확인 항목, 사용량 범위, 권한 거절 처리, 종료/취소 관측이다.

### V04-04 — 세 상급 모델 + bounded cross-review

Q3와 Q4를 동일한 task에서 비교하고 처음 맞던 답변의 손실과 추가 비용을 측정한다. 모델 부족 때 silent degradation이 없어야 한다. 호출·deadline·재시도 상한, 검토 coverage, 합성에서 생긴 새 주장과 미합의 보존을 검사한다. 개선이 없으면 cross_check만 남기거나 task군을 좁힌다.

### V04-05 — `build_review` 연결

기존 v0.2 bounded_patch에 협업 계획/검토 artifact를 선택적으로 연결한다. 구현 writer는 하나이며 read-only reviewer와 독립 test runner를 구분한다. acceptance는 원래 작업의 권한 범위를 유지한다. 자동 main merge는 초기 완료 조건이 아니다. F24의 코드 근거/미검증 우려 구분과 scope 검사를 pilot에 포함하되, 논문의 개선율이나 더 긴 review loop를 기본값으로 복제하지 않는다.

### V04-06 — routing/Jev는 그 다음

실제 작업 기록에서 어떤 task에 협업이 유리했는지 확인한 뒤 규칙→shadow 분류→제한적 routing 순서로 간다. 작은 모델이 중요 작업의 협업을 생략하거나 강한 검증자를 몰래 교체할 수 없다. 새 gateway/framework는 transport·funding·권한·usage conformance가 증명될 때만 채택한다.

## 9. 프로토콜 검사와 실제 운영 검사의 경계

오프라인 검사는 **기록에 모순이 없는지** 확인할 수 있다. 기록된 읽기 전용 설정이 OS에서 실제 강제됐는지, 인용이 주장을 정말 뒷받침하는지, provider가 사용량을 완전히 보고했는지는 알아내지 못한다. '테스트 N개 통과'를 'N개 연구 주장 검증'으로 읽지 않는다.

실제 운영 전 추가로 필요한 것은 권한 escape/soft-denial, timeout과 자식 프로세스 잔존, event 유실/누계, 동시 task/session 충돌, stale artifact, 명시 resume, redaction/data-egress, native memory 오염, provider별 과금 경로 검사다. 의도적으로 실제 quota를 대량 소진하지 말고 기록된 event fixture와 mock으로 오류를 재현한 뒤 최소 실제 호출로 확인한다.
