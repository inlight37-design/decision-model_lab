# 04. 평가 계획과 비용 모델

> 2026-09-21 / **실험 설계**. 이 문서에는 사용자 프로젝트에서 측정한 절감률이 없다. 공급자 발표 수치, 산술 예제, 앞으로 측정할 지표를 분리한다.

## 1. 최적화 목표를 먼저 고정한다

일차 목표는 ‘토큰이 가장 적은 실행’이 아니라 **동의한 품질·안전 수준을 유지하며 수용 가능한 결과를 얻는 총비용 최소화**다. 토큰을 아끼다가 중요한 설계 오류를 만들거나 사람이 반복 수정하게 되면 목적에 맞지 않는다.

시간 단축, frontier 사용량 감소, USD 절감, 구독 quota 보존, 로컬 메모리 사용은 서로 다른 목적이다. 한 지표가 좋아졌다고 다른 지표도 좋아졌다고 표시하지 않는다.

## 2. 반드시 별도로 기록할 지표

| 축 | 지표 | 해석 |
|---|---|---|
| 작업 품질 | 수용 성공률, 회귀 오류, 요구사항 누락, 사후 재작업 | 테스트 PASS만으로 모든 품질을 대표하지 않음 |
| 운영 신뢰성 | 잘못된 ACCEPTED, 중복 외부 동작, stale 결과 수용, 복구 성공 | 잘못된 자동 승인 등은 별도 실패 기준 |
| frontier 사용 | 모델별 입력·출력·추론 보고량, 호출 수 | 서로 다른 tokenizer·usage 의미를 구분 |
| 금액 | 총 청구 또는 명시적 추정, 수용 작업당 비용 | 실패·검증·router·캐시 비용 포함 |
| 시간 | 종단간 p50/p95, 대기·실행·검증·통합 시간 | API 응답 latency와 프로젝트 완료 시간 구분 |
| 사람 | 검토/승인/수정에 든 시간 | 값싼 AI가 사람에게 비용을 전가하는지 확인 |
| 협업 | 중복 작업, 파일 충돌, 통합 실패, 동시 실행 자원 | 병렬화가 실제로 이득인지 |
| 지역 자원 | peak RAM/VRAM, CPU/GPU 점유, 전력 추정 | 로컬 실행을 무료라고 단정하지 않음 |

명령에서 사용량을 받지 못했으면 null/unknown으로 기록한다. 추정값은 실제 청구와 같은 컬럼에 덮어쓰지 않고 `measurement_source`와 `estimator_version`을 붙인다.

## 3. 총비용 식

호출 j의 비용 항목은 공급자 정의에 맞게 다음처럼 분해한다.

```text
C_j = (U_j * P_uncached
     + R_j * P_cache_read
     + W_j * P_cache_write
     + O_j * P_output) / 1,000,000
     + separately_billed_components_j

C_total = Σ C_j
        + tool/API charges
        + local/cloud infrastructure
        + attributable human review/rework
```

U/R/W/O의 정의는 공급자마다 정규화한다. 어떤 공급자는 cache write를 일반 input에 포함하고 surcharge만 따로 부과할 수 있다. reasoning이 output 사용량에 포함되어 있다면 다시 더하지 않는다. 중복 계산을 막기 위해 raw usage도 보존한다. 캐시 정책이 모델별로 달라질 수 있다는 공식 예는 [조사 지도 S24](01-evidence-and-landscape.md).

구독 비용을 배분할 때에는 기간 고정비와 추가 과금, 실제 quota 소모를 나눠 기록한다. provider가 환산 규칙을 공개하지 않으면 ‘1 quota = 몇 토큰’으로 임의 환산하지 않는다.

```text
cost_per_accepted = 전체 시도의 총비용 / 최종 수용된 작업 수
```

수용 작업 수가 0이면 값은 정의 불가/무한대로 표시한다. 실패한 작업의 비용을 분자에서 제외하지 않는다. 서로 다른 구성이 다른 난도의 작업만 해결했다면 수용 개수뿐 아니라 task별 성패도 비교한다.

## 4. Jev 가격을 사용한 산술 예제

TypeSafe 공개 발표의 조사일 가격은 입력 100만 토큰당 US$0.042, 출력 무료다. [조사 지도 S01]

**가정**: 실제 청구 기준 입력이 호출당 5,000토큰이고 10,000번 호출한다.

```text
총 입력 = 5,000 × 10,000 = 50,000,000 tokens
입력 청구 = 50 × US$0.042 = US$2.10
```

이는 해당 입력 항목만 계산한 예다. 상태·질문·후보 설명이 무엇을 포함해 계량되는지는 실제 usage를 따라야 한다. 네트워크, 생성 모델, 테스트, 저장, 세금, 요금 조건은 포함하지 않았다. 사용자 시스템의 월간 총비용 예측도 아니다.

이 정도 사용량에서 로컬 판단 모델을 운영하는 일이 경제적으로 유리한지는 별도 문제다. 호출량 외에도 프라이버시·오프라인·지연·GPU 점유·유지보수가 결정 요인이다.

## 5. 싼 워커를 먼저 부르는 것이 손해가 되는 조건

단순 1회 상향 모델:

```text
C_direct = C_frontier + C_verify_frontier
C_cascade = C_router + C_cheap + C_verify_cheap
          + p_escalate * (C_frontier_fallback + C_verify_fallback)
```

상향 시 더 긴 문맥을 보낼 수 있으므로 `C_frontier_fallback`이 직접 호출 비용과 같다고 가정하지 않는 것이 원칙이다. 재시도·사람 개입·지연도 실제 평가에서 추가한다.

### 가상 비용단위 예시 — 실제 가격이 아님

가정: frontier 10, cheap 2, 검증 1, router 0.02, 상향 실행의 비용도 10+1.

- 직접 실행: 11.
- 상향 비율 25%: `0.02 + 2 + 1 + 0.25 × 11 = 5.77`.
- 상향 비율 80%: `0.02 + 2 + 1 + 0.80 × 11 = 11.82`.
- 손익 분기 상향 비율: `(11 - 3.02) / 11 ≈ 72.55%`.

동일한 최종 품질을 가정한 산술이다. 현실에서 cheap 경로가 미검출 오류를 만들면 이 계산만으로 유리하다고 할 수 없다. 그래서 어려운 작업을 즉시 frontier에 보내는 경로가 필요하다.

## 6. 실험군: 한 번에 모든 기능을 켜지 않는다

| ID | 구성 | 확인할 효과 |
|---|---|---|
| B0 | 단일 frontier 하네스 + 명시된 verifier | 기본 성능·비용 |
| B1 | B0 + 최소 문맥 구성/로그 필터 | context 선별 자체의 효과 |
| B2 | B1 + 규칙 기반 배정 + 저비용 워커 | AI router 없이 얻는 효과 |
| B3 | B2 + Jev 판단 | Jev의 추가 순이익 |
| B4 | B2 + 로컬/다른 router | Jev 고유 효과인지, 인터페이스 효과인지 |
| B5 | 검증된 단일 경로 + 제한 병렬 | 협업의 시간·비용·품질 효과 |
| B6 | 가능한 API 경로의 기존 LiteLLM router | 직접 만든 router의 필요성 |

캐시 on/off는 별도 축으로 대조하되 가능한 한 기준선에도 같은 혜택을 준다. Jev 경로에만 캐시·좋은 context·더 많은 재시도를 주고 이를 전부 Jev의 성능으로 기록하면 안 된다.

동일 task, base commit, 환경, verifier, 허용 tool, 시도 한도, 모델 설정을 기록한다. 하네스까지 달라지는 비교는 ‘모델 효과’가 아닌 ‘구성 전체 비교’로 표시한다.

LiteLLM의 2026-09-11 자체 평가는 동일 과제/검증기, 캐시, 실패와 classifier 비용을 함께 다룬 참고 사례지만 표본·반복의 제한이 있다. [05의 T08](05-tooling-and-roadmap.md)

## 7. 데이터셋은 사용자의 실제 작업 분포에서 만든다

초기 pilot에는 다음 작업군을 포함한다.

- 문서·설명·정해진 형식 변환.
- 재현되는 국소 버그와 작은 기능 추가.
- 여러 파일의 인터페이스 변경.
- 환경/설치/빌드 문제.
- 테스트 설계와 회귀 진단.
- 불명확한 명세, 누락 입력, 의도적으로 위험한 요청.
- 한국어 요청 + 영어 코드/로그가 섞인 사례.

50–100개 작업 정도의 pilot로 파이프라인과 오류 유형을 먼저 살펴보고, 좁은 routing 라벨은 더 많은 사례로 확장하는 방안을 제안한다. 이 수는 검증력이 보장되는 표본 크기가 아니다. 드문 위험 오류의 확률을 확인하려면 더 큰 표본과 별도 분석이 필요하다.

### 분할 원칙

같은 버그를 말만 바꾼 사례가 train/test 양쪽에 들어가지 않게 한다. 저장소·모듈·과제 계열 또는 시간 기준으로 나누고, 아직 안 본 프로젝트에 대한 prospective test를 남긴다. routing에 쓴 라벨로 최종 검증기를 조정해 holdout을 오염시키지 않는다.

benchmark 원문이나 수용 테스트를 보고 답을 맞추는 leakage도 통제한다. 워커가 작성한 테스트 외에 버전 고정된 독립 기준을 사용한다.

### 무엇을 정답 라벨로 삼을 것인가

‘frontier 모델이 cheap이라고 말했다’를 최종 정답으로 삼지 않는다. 이상적인 라벨은 해당 작업을 각 후보가 수행했을 때 같은 verifier로 수용되는지, 총비용·재시도가 얼마였는지에서 나온다. 모든 후보 실행이 비싸다면 일부 표본부터 counterfactual 비교를 하고 나머지는 불확실한 라벨로 구분한다.

## 8. 확률·보정·보류의 평가

세 가지 값은 서로 다르다.

1. ‘이 작업의 클래스는 cheap_worker’라는 분류 확률.
2. 공급자가 계산한 분포 집중도 등의 confidence.
3. 특정 작은 워커가 이 작업을 수용 기준까지 완료할 실제 성공 확률.

1이나 2를 검증 없이 3으로 이름만 바꾸지 않는다. 어떤 사건을 예측하는지 `score_semantics`를 평가 manifest에 기록한다.

평가할 항목:

- 분류 정확도와 작업군별 confusion matrix.
- 특히 **실제로 어려운 작업을 cheap 경로로 잘못 보내는 비율**.
- calibration 대상이 정해진 경우 Brier score/ECE와 reliability 자료.
- 자동 처리 비율(coverage)을 높일 때 오류가 얼마나 늘어나는지 risk–coverage 곡선.
- low-confidence 보류율, 고확신 오답률, 새로운 저장소에서의 성능.
- 비용이 큰 false-negative와 불필요한 상향을 따로 측정.

공통 confidence threshold 0.9를 모든 모델·작업군에 적용하지 않는다. 옵션 수/순서, 질문 표현, 한국어/영어, 미지 도메인에 따른 변화를 측정한다. 확률 합계와 유효한 schema는 최소 형식 검사일 뿐이다.

### 꼭 넣을 공격적/경계 사례

정답이 후보에 없는 요청, 모호한 표현, 이중 부정, 오래된 문맥, 빠진 파일, 위장된 정책 변경 요구, 로그 속 지시문, 매우 긴 입력, 옵션 순서 섞기, 같은 상태를 공유한 질문 간 의존성을 시험한다.

잘못된 선택을 확신 있게 반복하는 모델은 더 긴 프롬프트를 자동으로 넣어 해결했다고 간주하지 않는다. 규칙으로 차단하거나 추가 정보를 가져오거나 다른 경로로 보류한다.

## 9. 협업 및 장애 평가

다중 에이전트 평가는 모델 정답률만으로 끝내지 않는다.

| 시험 | 기대되는 안전한 결과 |
|---|---|
| 동일 task 동시 claim | 하나만 실행 권한 확보 |
| 예산이 부족한 두 병렬 요청 | 총 예약이 상한을 넘지 않음 |
| 워커가 수정 범위 밖 파일을 변경 | 후보 거부 또는 명시적 검토 |
| 테스트 자체를 지우고 PASS 보고 | 수용 실패 |
| 잘못된 base commit에서 만든 patch | stale 처리/재검증 |
| 옛 lease의 지연 결과 | 자동 ACCEPTED 금지 |
| 외부 동작 직후 crash | unknown outcome 조정; 맹목 재실행 금지 |
| 취소 후 자식 프로세스 존속 | 취소 완료라고 표시하지 않음 |
| 서로 합치면 깨지는 두 patch | merge queue 검증에서 탐지 |
| 사용량 보고 누락 | 0 비용으로 취급하지 않고 보수적 중단/추정 표시 |

이 시험은 실제 제어부·adapter·workspace 구현이 있어야 수행할 수 있다. 현재 저장소의 오프라인 JSON 계약 검사는 이 전체 시험을 대체하지 않는다.

## 10. 통과 기준의 예시

다음은 사용자와 확정할 **제안 기준**이지 현재 달성 수치가 아니다.

- 잘못된 자동 ACCEPTED, 권한 밖 실행, 중복 비가역 동작을 실험 중 발견하면 해당 경로 자동 중지.
- 정한 작업 분포에서 baseline 대비 품질 허용 범위 내이며, 비용 감소가 반복 관측될 때에만 routing 확대.
- 비용 20% 감소 등을 운영상 의미 있는 목표로 설정할 수 있으나, 품질을 맞추지 못하면 실패로 판단.
- 단일 실험의 평균뿐 아니라 task별 결과·p95·검토 시간·신뢰구간을 함께 검토.
- 병렬화는 비용을 줄이지 못하더라도 충분한 시간 단축 가치가 있을 수 있다. 그 경우 결과를 ‘시간 최적화’로 분류.

작업별 결과가 서로 의존하면 독립 토큰/턴을 표본으로 세어 과도하게 좁은 신뢰구간을 만들지 않는다. 과제 또는 프로젝트 단위로 반복·재표집하는 분석을 사용한다. small sample에서 같은 성공 개수만으로 동등 품질을 선언하지 않는다.

## 11. 운영 중 감시와 롤백

실제 routing을 켠 뒤에도 cheap 경로의 일부 결과를 독립 검토한다. 어려운 작업을 계속 잘못 하향 배정하는지 관찰하고, 새 모델/새 프로젝트/새 CLI 버전에서 shadow mode로 되돌린다.

모델 선택 변경은 `policy_version`, 모델 revision, threshold config, 시행 시점과 함께 기록한다. 결과가 나빠지면 이전 정책으로 복귀할 수 있어야 한다. 모델을 자동 학습·자동 배포하는 폐쇄 루프는 초기 범위에 넣지 않는다.

## 12. 평가 기록 예시

실측 결과 파일의 최소 컬럼:

```text
eval_id, config_id, task_id, repository_snapshot
model_ids, harness_versions, policy_version, context_builder_version
acceptance_version, attempt_count, final_accepted
uncached_input, cached_input, cache_write, output, reasoning_reported
provider_cost, estimated_cost, measurement_source
router_cost, tool_cost, verifier_cost, local_resource_cost
wall_time, review_minutes, failure_category, artifact_ids
```

실제 trace에는 민감한 내용이 있을 수 있으므로 원본을 공개 Git에 자동 업로드하지 않는다. 재현용 공개 결과는 비식별 task ID와 허용된 지표·환경·검증 근거만 포함한다.

## 13. 지금 말할 수 있는 것과 없는 것

말할 수 있는 것: typed decision API, 공개 로컬 구현, headless coding agents, gateway routing, 지속 원장·검증 패턴이 존재하며 연결 가능한 경계가 확인되었다.

아직 말할 수 없는 것: 사용자 프로젝트에서 몇 %를 절약하는지, 특정 local model이 한국어 작업에서 가장 좋은지, 몇 명의 에이전트가 최적인지, 현재 계정의 quota가 얼마나 늘어나는지, 무인 장기 운영이 검증됐는지.

따라서 첫 구현의 목적은 ‘성공을 시연하는 것’보다 **좋은 기준선과 비교해 이 구조가 정말 이득인지 판정할 수 있게 만드는 것**이다.
