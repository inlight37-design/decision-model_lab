# 무엇부터 넣으면 어떻게 도움이 되는가

우선순위는 현재 사용자가 요청한 **대대적 개편 준비와 재사용성**을 기준으로 한 판단이다. 기능의 유명세나 upstream 코드량으로 점수를 주지 않는다. 효과 수치는 아직 없으며 아래는 기대 효용이다. 모든 H/O/D/OP 항목의 배치는 [후보 지도](CAPABILITY-MAP.md)에 있고, 이 문서는 중복 후보를 실제 작업 묶음으로 정리한다.

**P0:** 지금 문서·탐색의 혼동을 없애거나 구조 변경의 기준을 준비. **P1:** 기존 기능의 활용과 핵심 연결에 직접 도움, cloud에서 작은 조각 가능. **P2:** R1/R2 기반 뒤 workflow·운영 확대. **P3:** 실측·외부 서비스·기기 조건이 큰 선택 확장. 이는 모든 P1을 끝내야 P2를 할 수 있다는 일렬 대기열은 아니다. 의존 관계가 먼저다.

## 지금 바로 수행한 것과 후속 구현을 구별

이번에 바로 수행하는 것은 문서 지도, 현재 코드·아키텍처 대조, 우선순위/누락 지도, 충돌하는 인계 문구 정리, 앱의 프로젝트 안내 탐색 개선이다. 실행/원장 의미를 바꾸지 않는 명확한 개선이다. 이 준비서의 R1/R2 구현은 “설계했으니 이미 반영됨”으로 표시하지 않는다.

후속 코딩 시작은 **2번의 공개 query 추출 한 조각**을 우선 권고한다. 사용자에게 눈에 보이는 것은 4·5·9·11번이고, 그 바탕을 함께 만드는 순서다. 동시에 모든 기능을 추상화하지 않고 현재 view parity를 유지한 채 작업/실행 상세의 읽기 경계부터 분리한다. 기존 S3/S6가 해결한 중복·순서 문제를 다시 구현하지 않는다.

## 우선순위를 바꾸는 조건

- 자료 준비 실패가 가장 큰 불편이면 8번을 먼저 진행하되 입력 snapshot 계약을 유지한다.
- 반복 설정이 부담이면 6번의 저장/복제만 먼저 넣을 수 있다. workflow engine까지 선행할 필요는 없다.
- 코딩 agent로 범위를 넓히는 것이 명확한 목표가 되면 15번이 올라가고, writer/restore/runtime 관측이 선행한다.
- 장시간 무인 작업이 실제로 필요해지면 14번의 지속 수명/예약을 올린다. 화면을 닫아도 결과만 다시 찾는 요구와 구별한다.
- 검색 평가에서 현재 방식이 충분하면 고급 검색·별도 DB는 P3에 남긴다. 기능 보류는 원문·재검토 조건의 삭제가 아니다.

## 완료를 판단할 효용 지표

| 목적 | 모델 없이 확인할 것 | 실제 사용/모델로 확인할 것 |
|---|---|---|
| 다시 찾기 | 같은 자료까지 클릭/검색 단계, 위치/hash 일치, 누락 fixture | 원하는 과거 결과를 찾는 시간·실패 사례 |
| 입력 준비 | 반복 입력 필드 수, template 복원, source 누락 감지 | 실제 자료 준비에 드는 시간·수정 횟수 |
| 실행 신뢰성 | 중복 spawn, 예산/미확정/공개 parity, migration 보존 | 현재 PC CLI·취소·격리·재시작 관측 |
| 검토 효과 | revision·quote·처분·check 결속 | 수정 후 새 오류/미해결/성공률과 전체 호출량 |
| 기억 효과 | 적격 범위·정답 fixture·필수 반례 유실 | 동일 과제의 기억 on/off 비교·지연·비용 |

측정하지 않은 시간 절감이나 품질 향상을 수치로 약속하지 않는다. 동작이 맞는지와 사용자에게 도움이 되는지를 둘 다 판단하되 서로의 증거로 대신하지 않는다.
