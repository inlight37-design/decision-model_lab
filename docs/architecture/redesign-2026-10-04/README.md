# Decision AI 구조 개편 준비서

2026-10-04 · 사용자 요청에 따른 **아키텍처·파이프라인 재구성 제안**. 오늘의 기능 조사들을 현재 코드와 대조해, 기존 앱을 크게 고칠 수 있는 설계와 이행 계획으로 연결했다. 이번 적용은 문서·안내 정리와 앱의 프로젝트 안내 링크 개선이다. 실행·원장 구조 변경과 외부 서비스 도입은 제안이며, v0.4를 운영 버전 v0.5로 승격하는 선언도 아니다.

**추천 방향은 실행 계약을 유지하면서 내부를 책임별 모듈로 다시 나누는 것이다.** 현재 Python·SQLite·native CLI를 출발점으로 삼되, `controller`의 작업·문맥·실행·검토·조회 책임과 역할별 호출 저장 방식을 재구성할 수 있게 설계했다. 기존 파일 구조나 화면 구성이 목표 아키텍처의 한계가 되지는 않는다.

## 무엇까지 크게 바꿀 수 있나

- `Controller`를 명령 처리, 실행 조정, 문맥 구성, 검토, 읽기 projection으로 분리하고 기존 API는 호환 facade로 둘 수 있다.
- 역할마다 다른 호출 저장 구조를 공통 invocation과 역할별 payload로 옮길 수 있다. 이때 예약·시작·결과·종료 미확정의 의미와 기존 회계는 보존한다.
- “한 번 실행하고 끝나는 화면” 위에 작업 명세·workflow·결과 판·재검토·기억/절차를 연결할 수 있다. 자동화는 같은 실행 관문을 통과한다.
- 검색 인덱스와 화면 읽기 모델은 버리고 재생성할 수 있게 만들고, 원본/기억 선택 정책/사용자 결정은 영속 자료로 구분할 수 있다.
- 장기 실행 service나 원격 worker, 파일 수정형 작업은 모듈 경계 위에 추가할 수 있다. 단순 리팩터링과 다른 관측·운영이 필요한 변경으로 표시한다.

반면 구독 경로, 격리 초안, 자동 기억의 역할 범위, 사용량 미상 처리, 한 writer, 같은 기기의 실행 관측 같은 사용자 확정 조건을 “전면 개편”이라는 이유로 없애지 않는다. 새 설계가 이 조건을 바꿔야 하는 경우에는 구조 변경과 정책 변경을 분리해 드러낸다. 현재 요청은 이 조건을 철회한 것이 아니다.

## 다음 구현의 출발점

[MIGRATION의 R0→R1→R2](MIGRATION.md)로 현재 동작의 비교 기준을 고정하고, **공개 조회 경계와 invocation 계약부터** 분리한다. 그 뒤 문맥/자료/기억과 검토 후 수정 경로를 연결한다. UI 편의는 이 경계 위에서 함께 개선한다. 검색창만 몇 개 더 붙이는 안으로 한정하지 않으면서도, 한 번에 원장·실행기·화면을 모두 교체하는 위험은 줄이는 순서다.
