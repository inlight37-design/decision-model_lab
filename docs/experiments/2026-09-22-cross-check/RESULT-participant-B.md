### 4. 가장 큰 설계 결함: “주장 원장에 들어오기 전에 사라진 내용”을 어떻게 발견할 것인가

> 추출·병합 결과: “이 구조는 안전하다.”  
> 이후 처리: 생성된 모든 claim ID에 출처와 disposition을 연결하고 보고서 작성 완료.

이 경우 원본 해시가 맞고, 참조가 모두 존재하고, 원장에 등록된 주장들이 빠짐없이 최종 처리돼도 핵심 조건은 사라졌습니다.

**더 위험한 경우는 초안 B의 반례가 애초에 claim으로 생성되지 않는 것입니다.** 그러면 “등록된 모든 주장에 대한 처리율”은 높게 나와도, 중요한 내용의 보존율은 알 수 없습니다.

문서에는 원문 연결, 합성 손실, 새 주장 처리, 의미 검증의 한계가 이미 명시돼 있습니다. 여기서 제가 추가로 강조하는 점은 **검사 대상을 생성된 원장 내부에만 두지 말고, 원문에서 원장으로 들어오는 단계까지 넓혀야 한다**는 것입니다.  

제안은 다음과 같습니다.

**처음에는 의미를 적극적으로 압축하지 말고, 원문을 보존한 연결을 우선하십시오.** 비슷한 주장 둘을 하나로 덮어쓰기보다 관련 있다고 연결하고, 각 주장의 조건과 원문 위치를 유지하는 편이 낫습니다. 중요한 결론은 `원문 구간 → 주장 → 지지·반박 근거 → 최종 처리`로 추적할 수 있어야 합니다. 중요도 하향이나 제외에도 이유를 남겨야 합니다.

그리고 초기 평가에는 **최종 합성 없이 원문과 대조표만 제공하는 조건**을 반드시 넣는 편을 권합니다. 합성이 없으면 사용성이 나쁜지, 오히려 올바른 소수 답변을 더 잘 발견하는지를 확인해야 합니다. 합성 호출이 실패하거나 한도가 부족할 때도, 이미 모인 원문과 반례를 정형 보고서로 제공할 수 있도록 하면 유용합니다. 이것을 완성된 합성 결과로 표시해서는 안 됩니다.

#### 이 위험과 별도로, 실행 가능성을 먼저 좌우하는 것은 구독·격리·native 동작의 결합입니다

공식 문서만 보아도 “native 비대화형 실행”을 하나의 균일한 능력으로 취급하기 어렵습니다.

| 경로 | 원문에서 확인한 차이 | 설계상 판단 |
|---|---|---|
| Codex `exec` | 기본 read-only sandbox를 문서화합니다. | 출발점으로 유리하지만 설치 버전과 유효 설정의 실제 적용은 별도 확인 대상입니다. |
| Claude Code `-p` | 일반 실행은 프로젝트·사용자 문맥을 읽습니다. 자동 로딩을 줄이는 `--bare`는 구독 로그인을 사용하지 않습니다. | blind를 위해 무심코 `--bare`를 쓰는 해결책은 구독 우선 조건과 맞지 않습니다. |

이는 공식 문서상의 차이이며 사용자 환경에서 실행해 확인한 결과는 아닙니다. :chatgpt-content-reference{index="15"}

또한 **worktree 분리는 blind를 위한 보안 경계가 아닙니다.** Git 공식 문서는 여러 worktree가 일부 refs와 기본 설정을 공유하며 다른 worktree의 refs에 접근할 수 있음을 설명합니다. 따라서 worktree만 나누었다고 동료 산출물이나 공통 저장소 상태를 읽지 못한다고 볼 수 없습니다. 접근 가능한 파일·도구·세션 문맥의 경계를 따로 시험해야 한다는 것이 제 추론입니다. :chatgpt-content-reference{index="16"}

여기서 read-only의 보호 대상도 명확해야 합니다. **사용자 원본과 구현 대상에 쓰지 못하는 것**과 native 도구가 자신의 세션 기록까지 전혀 쓰지 못하는 것은 다른 요구입니다. 논의자에게는 분리된 세션 작업공간을 주되, 보호 대상과 동료의 미공개 산출물에는 접근하지 못하게 하는 식으로 정의하는 편이 현실적입니다.

구독 정책은 과도하게 비관해서도 안 됩니다. 현재 읽은 Claude 공식 지원 문서의 상단 공지는, 발표했던 변경을 보류했으며 SDK·`claude -p`·제3자 앱 사용이 당분간 구독 한도에서 계속 차감된다고 설명합니다. 아래의 과거 크레딧 전환 설명은 시행 중인 내용이 아닙니다. 저장소 F18의 이 구분은 타당했습니다. :chatgpt-content-reference{index="17"}

다만 이것이 모든 제3자 인증 구현을 허용한다는 뜻은 아닙니다. 별도의 공식 정책 문서는 원본 Claude Code 실행, 바이너리·인증 기능 변경, 제3자 앱 자체 로그인과 자격증명 중개를 구분해 조건을 제시합니다. **사용자가 native 인증 흐름으로 로그인한 도구를 로컬에서 실행하는 구조와, 앱이 구독 토큰을 받아 자체 게이트웨이처럼 사용하는 구조는 같은 것으로 취급하지 않아야 합니다.** 배포 형태에 따른 허용 범위까지 이번 검토로 확정하지는 못했습니다. :chatgpt-content-reference{index="18"}

제 권고는 구독 조건을 포기하라는 것이 아닙니다. **공식적으로 지원되고 실제 확인된 경로만 실행 가능 상태로 두고, 모호하면 시작하지 않는 것**입니다. 다만 이 정책을 선택하면 일부 provider가 막혀 제품의 핵심 구성이 성립하지 않을 수 있다는 사업·운영 위험을 받아들여야 합니다.

**“가장 큰 결함”이라는 제 판단이 틀릴 조건:** 다루는 문제가 형식 검증·재현 가능한 테스트처럼 외부 판정이 강한 좁은 작업군이고, 원문에서 주장으로 옮기는 과정의 누락도 충분히 검증된다면 의미 손실은 주된 위험이 아닐 수 있습니다. 그 경우 공급자 정책, 실행 안정성, 유지보수 부담이 우선순위가 됩니다. 반대로 정답이 명확하지 않은 설계·조사에서는 검증자를 한 명 더 추가하는 것만으로 이 문제가 해결됐다고 보지 않겠습니다.

## assumptions

**유지한 전제:** 사용자 자신의 구독, native 하네스, blind 초기 답변, 단일 제어권, read-only 논의자와 단일 구현자라는 제약입니다. 이를 바꾸어야만 성립하는 유료 API 중심 설계는 대안으로 채택하지 않았습니다. :chatgpt-content-reference{index="24"}

**제품에 관한 가정:** 핵심 사용처는 단순 실행량 증대가 아니라 중요한 조사·설계·검토에서 오류와 누락을 발견하는 일이라고 보았습니다. 이 가정이 틀리면 첫 화면과 추가 검토 비용에 대한 권고도 달라집니다.

**구현에 관한 가정:** 최초 배포 범위는 로컬의 작은 실행 단위로 제한할 수 있다고 보았습니다. 기존 코드가 Python이라는 사실만으로 유지보수자의 Python 숙련도가 더 높다고 가정하지는 않았습니다.

**평가에 관한 가정:** 전체 문제의 객관적 정답을 항상 얻을 수는 없지만, 일부 작업에서는 중요한 오류·조건 누락·인용 불일치·불필요한 수정 등을 사람이 제한된 비용으로 판정할 수 있다고 보았습니다. 이것마저 어렵다면 품질 개선을 검증하는 비용이 크게 증가합니다.

## unknowns

현재 모르는 것은 **사용자 환경의 실제 CLI 버전, 유효 설정, 계정별 사용 가능 모델, 구독·추가 사용량 경로, 취소 후 프로세스 생존 여부, OS 수준의 쓰기·읽기 차단 동작**입니다. 따라서 세 native 제품이 고정 제약을 동시에 만족한다고 결론 내릴 수는 없습니다.

Orca의 전체 실행 경로, 안정적인 외부 확장 계약, 의존 패키지 전체의 라이선스도 감사하지 않았습니다. AionUi·Paseo·Superset의 구현을 동등한 깊이로 비교하지 않았으므로, 이들보다 Orca가 낫거나 나쁘다는 순위도 제시하지 않습니다. 첨부된 정확한 stars 수는 이번 검토에서 재확인하지 않았습니다.

**74개 테스트를 직접 실행하지 않았고, 문서·코드 용량과 근거 원장 55건도 독립 집계하지 않았습니다.** 또한 사람의 판단 품질이나 검토 시간이 실제로 개선되는지에 관한 실측은 없습니다. 이 숫자와 성과를 문서의 완성도에서 추정하지 않겠습니다.

배포형 앱에서 native 인증 흐름을 감싸는 정확한 허용 범위도 확정하지 못했습니다. 공식 과금 안내와 제3자 인증·배포 조건은 서로 다른 질문이므로, 구현 방식에 맞춘 확인이 남아 있습니다.

## checks_proposed

**검증 순서는 “연결이 가능한가 → 제약을 실제로 강제하는가 → 판단에 도움이 되는가 → 어느 구현이 유지보수하기 쉬운가”가 적합합니다.** 아래는 제안한 시험이며 실행 결과가 아닙니다.

| 단계 | 시험 | 통과·실패 판단 |
|---|---|---|
| 1. 실행·구독 적합성 | 실제 설치 버전, native 로그인 방식, 유효 모델·권한·과금 경로, 공식 지원 문구의 확인일을 한 manifest에 기록합니다. | 경로를 확인하지 못한 adapter는 실행 가능으로 표시하지 않습니다. 구독 로그인 성공만으로 추가 과금 차단까지 확인됐다고 처리하지 않습니다. |
| 2. 실행 전 차단 | 구조화 실행 미지원, 무효 제한 인자, 상속된 설정, 도구 거절을 모의 환경에서 주입합니다. | 필수 제한이 적용되지 않으면 **프로세스 생성 전** 차단해야 합니다. 다른 실행 방식으로 대체한 뒤 경고하는 것은 실패입니다. |
| 3. Blind·읽기 전용 | 동료 산출물·공유 저장소·설정·캐시에 식별용 자료를 두고 접근을 시도합니다. 보호 대상 파일 변경도 시도합니다. | 답변에 자료가 나타나지 않은 것만으로 통과시키지 않습니다. 접근·변경이 차단됐다는 관측이 필요합니다. |
| 4. 취소·재개 | 실행 직후 연결 끊김, 출력 후 종료 지연, controller 재시작, 이벤트 중복·역순 도착을 재현합니다. | 종료 불명 상태에서 재실행하거나 writer 권한을 다른 실행에 넘기지 않아야 합니다. 같은 요청을 다시 받았다는 이유만으로 두 번 실행해서도 안 됩니다. |
| 5. 의미 보존 | 조건 삭제, 부정 반전, 적용 범위 축소, 소수 반례 누락, 무관한 인용, 합성의 새 사실 추가를 fixture에 넣습니다. | 원장 내부 참조 검사뿐 아니라 **원문에서 주장으로 옮기는 단계의 손실**을 따로 측정합니다. 통과 범위는 해당 fixture로 제한합니다. |
| 6. 실제 효용 | 강한 단독 모델, 같은 검증 절차를 붙인 단독 모델, 두 모델 독립 답변 대조, 합성 추가 조건을 같은 과제로 비교합니다. | 중요한 오류·누락, 거짓 경보, 불필요 수정, 사람 검토 시간, 실패·중단을 함께 봅니다. 검증 절차의 이득을 모델 다양성의 이득으로 오인하지 않습니다. |
| 7. 의존성 선택 | 직접 native adapter와 제한된 Orca 재사용 경로에 동일한 실패 시험을 적용하고 버전 업그레이드도 시험합니다. | 자체 수정 범위, 회귀시험 부담, 배포·복구 비용을 비교합니다. “처음 연결하는 데 편했다”만으로 결정하지 않습니다. |
| 8. 화면 효용 | 사용자가 중요한 미해결 조건과 근거를 찾고 다음 검사를 선택하는 과정을 모델별 채팅 화면과 비교합니다. | 선호도뿐 아니라 잘못된 확신, 중요한 반례 발견, 판단에 걸린 시간을 봅니다. |

저장소의 기존 Q0–Q6와 pilot 계획은 이 비교의 좋은 출발점입니다. 다만 제안된 소규모 pilot은 연결과 계측을 점검하는 단계이지, 일반적인 품질 우위를 확정하는 표본으로 해석하면 안 됩니다. 

**지금 다음 산출물로 가장 가치 있는 것은 더 큰 아키텍처 문서가 아니라, V04-01의 실제 capability manifest, 두 읽기 전용 native 경로의 실패 시험 기록, 그리고 합성 전 원문을 대조하는 작은 화면입니다.** 이 세 가지가 있어야 Orca 의존 범위·언어 경계·화면 정체성을 추측이 아닌 결과로 결정할 수 있습니다.
