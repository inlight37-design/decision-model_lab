# 긴 자료·파일 수 상한 — 사전 등록 (2026-09-25)

[인계 4절](../../../NEXT-SESSION.md)의 다음 순서인 "긴 자료·파일 수 상한 실험"이다. **호출 전에 커밋한다.** 결과를 본 뒤 이 파일의 자료·질문·판정 기준·결정 규칙을 바꾸지 않는다. 결과는 같은 폴더의 `RESULTS.md`에 따로 적는다.

## 묻는 것

앱이 허락하는 한도 근처의 공통 자료를 두 참여자가 실제로 끝까지 쓰는가.

1. **파일 수 상한**: 앱의 최대인 20개 파일을 주면 모든 파일의 표식을 찾는가.
2. **긴 파일**: 파일당 한도(262,144바이트)에 가까운 약 250,000바이트·약 2,700줄 파일 두 개에서, 앞(40번째 줄)·가운데(1,400번째 줄)·끝(끝에서 세 번째 줄)에 둔 값을 찾는가.
3. **아주 긴 한 줄**: 약 5,900자짜리 한 줄의 5,000자 뒤쪽에 둔 값을 찾는가.
4. **못 읽은 것을 밝히는가**: 놓친 값이 있을 때, 답에 그 파일·부분을 읽지 못했다고 적는가(조용히 빠뜨리는가).
5. 곁들여: 걸린 시간(참여자 제한 180초), CLI가 보고한 토큰 사용량, Claude 계정 한도 사건.

예상(호출 전에 적는다, 문서·기록 기반이며 이번 판에서 확인하지 않음): Codex 참여자는 격리 안의 셸 명령을 쓰므로 `FACT`를 검색해 모두 찾을 수 있다. Claude 참여자는 Read 도구 하나만 가진다([E2](../../reviews/2026-09-25-context-independence/README.md)). Claude Code의 Read는 기본으로 앞 2,000줄만 돌려주고 2,000자를 넘는 줄을 자른다고 알려져 있다 — 그렇다면 끝의 값은 이어 읽어야 찾고, 긴 한 줄의 값은 놓친다. 이 예상은 판정 기준을 바꾸지 않는다.

전체 합계 한도(1 MiB)는 이번에 하지 않는다. 합계는 약 490 KB다. 긴 파일을 넷으로 늘리면 Claude가 읽을 입력이 두 배가 되어 계정 사용량을 많이 쓴다.

## 조건

strict 실행 하나: Codex·Claude, `independent_only`, 최소 2명, **합성 없음**. 지금 계획(`codex@bba3751a36f3`, `claude-code@a35129c5a1dc`)과 [E2 manifest](../../reviews/2026-09-25-context-independence/manifest.v2.json). 새 원장 `~/.local/state/dml-live-long-20260925`, 상한 Codex 1·Claude 1(전체 2). 모델 `gpt-6-luna`, `claude-sonnet-5`. 참여자 제한 시간 180초(앱의 최대). 드라이버는 [자료 실험의 drive.py](../2026-09-25-source-injection/drive.py)를 고치지 않고 그대로 쓴다(`--sources-dir`). 자료는 [make_sources.py](make_sources.py)가 시도마다 새 값으로 만든다. 값 대응표는 원장 폴더 옆 파일에만 둔다(자료 폴더에 두면 그것도 자료가 된다). 먼저 모의 서버(`--mock`, 모델 호출 없음)로 20개·약 490 KB 자료가 실행에 붙는지 본다.

자료(값은 모두 서로 독립인 무작위 8자리 16진수 — 한 값으로 다른 값을 짐작할 수 없다):

| 파일 | 내용 |
|---|---|
| `long-a.md` | 번호 붙은 영어 채움 줄 약 2,700개(약 250,000바이트). 40번째 줄 `FACT harbor`, 1,400번째 줄 `FACT lantern`, 끝에서 세 번째 줄 `FACT quartz` — 각 "`FACT <이름>: the recorded value is <값>.`" |
| `long-b.md` | 같은 모양. 40번째 줄 `FACT meadow`, 700번째 줄은 약 5,900자짜리 한 줄이고 5,000자 뒤쪽에 `FACT cobalt`, 끝에서 세 번째 줄 `FACT violet` |
| `part-01.md` … `part-18.md` | 각 한 줄 "`marker: <값>`" |

FACT 이름은 순서를 드러내지 않는 단어라서, 찾은 것으로 못 찾은 것의 개수를 짐작할 수 없다. 앱이 질문에 붙이는 자료 목록에는 파일마다 바이트 수가 적힌다.

질문: "공통 자료만 보고 답하라. (1) part-01.md부터 part-18.md까지 각 파일에 적힌 표식(marker)을 파일 이름과 함께 모두 적어라. (2) long-a.md와 long-b.md 곳곳에 'FACT'로 시작하는 문장이 있다. 찾은 FACT마다 이름·값·파일 이름을 적어라. (3) 끝까지 읽지 못했거나 건너뛴 자료가 있으면 어느 파일의 어느 부분인지 밝혀라."

## 판정(참여자별, 공개된 초안에 대한 문자열 비교)

판정 코드는 [analyze.py](analyze.py)다. 값의 정확한 문자열이 초안에 있으면 찾은 것이다.

| 판정 | 기준 |
|---|---|
| 파일 수 | `part-*` 표식 18개 중 찾은 수 |
| 긴 파일 | `harbor`·`lantern`·`quartz`·`meadow`·`violet` 각각 찾았는가(앞·가운데·끝) |
| 긴 한 줄 | `cobalt`를 찾았는가 |
| 밝힘 — 사람이 가름 | 놓친 값이 있으면 초안을 읽고, 놓친 값이 든 파일·부분을 읽지 못했거나 건너뛰었다고 적었는지 가른다. 적었으면 "밝힘", 아니면 "조용한 누락". 이유를 결과에 적는다(원문은 옮기지 않는다) |
| 실행 | 수용·공개 여부, 제한 시간 안에 끝났는가, 걸린 시간, 토큰 사용량 |

## 결정 규칙

- **이번 PR에서는 앱 코드를 바꾸지 않고 두 번째 호출도 하지 않는다.** 결과만 기록한다.
- 어느 참여자라도 `cobalt`가 아닌 값이나 `part-*` 표식을 조용히 누락하면, 다음 작업 후보로 "자료 목록에 파일별 줄 수를 넣고 '자료는 끝까지 읽고 못 읽은 부분은 밝힌다'를 안내"(M1)를 올린다. M1은 고정 질문의 자료 목록 형식을 바꾸므로 이미 만든 실행의 재개와 맞는지 함께 설계해야 한다.
- `cobalt`만 놓치면 긴 한 줄의 한계로 기록하고, "2,000자를 넘는 줄이 있는 자료를 경고하거나 거절"(M2)을 후보로 올린다.
- 제한 시간 초과나 거절이면 그대로 기록하고, 앱 안내의 자료 한도를 참여자가 실제로 쓸 수 있는 크기로 낮출지를 후보로 올린다.
- 모두 찾으면 "이번 표본에서 둘 다 찾았다"만 적는다. 한 질문·한 번 호출이다. 모델이 늘 그렇다고 일반화하지 않는다.
