# 2026-09-24 검토 — K46 방어, 실행 허가와 2단계 관측

작성: ChatGPT / GPT-6 Astra Pro. [2026-09-24 요청][request]과 그 요청이 이어받은 [17번 요청][request17]에 대한 검토다. PR: [#14](https://github.com/inlight37-design/decision-model_lab/pull/14). 제품 코드나 원래 관측 판정을 이 PR에서 수정하지 않는다. 병합하지 않는다.

## 요약

1. **K46의 방어 방향보다 먼저 고쳐야 할 것은 시험의 합격 조건이다.** 현재 `k46-codex`는 인증 파일 부재, 다른 명령이 출력한 종료 코드, 앞선 읽기 성공을 뒤의 실패 값이 덮은 경우까지 통과시킬 수 있다. P3도 시간 초과를 올바른 옵션 거절로 처리한다. 안전한 합성 입력으로 판정식의 반례를 재현했다(R01·R03). **지금의 `as_expected=true`만 보고 K46을 닫아서는 안 된다.**
2. **실행 허가 관문에 입력 검증이 빠져 있다.** 미래 날짜, 근거 누락, 기록과 현재 버전이 모두 없는 경우가 허가된다. 별도 기록 검사기의 거절 조건이 실행 직전 경로에는 적용되지 않는다(R02). 현재 서버가 모의 실행기이고 Codex가 문맥 판정 때문에 차단된 것은 위험을 줄이지만 이 결함을 없애지는 않는다.
3. **관측의 한계를 정직하게 적은 점은 좋지만, 상태값과 완료 표현은 더 엄격해야 한다.** Claude 문맥의 `observed`, 새 Codex profile에 대한 과거 권한 관측의 재사용, 큰 입력의 전 바이트 수신 단정은 증거보다 강하다(R04·R08). `sandbox` 단독 시험, offline exec의 설정 수용, 실제 exec 모델 명령의 권한 준수를 구분해야 한다.

**권고 순서:** 모델 없는 판정식·허가·승인 예약 보강 → A1 모의 작업은 병행 가능 → 보강된 K46 시험을 새 승인으로 한 번 → C3를 관측과 정책으로 구분해 결정 → 실제 실행기 연결과 B3. 사용자의 확정 사항인 WSL2, 구독 경로, 수동 참여자 정책, agy 비활성, 선택 기능 기본 꺼짐은 바꾸지 않는다.

## 2. 발견

### R01 — 높음 — K46 판정이 실제 권한 차단을 보증하지 않는다

**위치:** [`tools/w2/observe.py:403–406`][rc], [`call:455–474`][judge]. **근거: 재현(판정식 발췌) + 문서.**

`auth_check`는 모든 완료된 `command_execution`의 `aggregated_output`을 합친 뒤 `dict(RC.findall(output))`로 만든다. 어떤 명령이 실행됐는지, 해당 실행의 필수 항목이 모두 있는지, 동일 키가 중복됐는지와 개별 명령 실패 원인을 검증하지 않는다. 합격 조건은 입력 읽기 성공과 `auth_open_rc`가 0이 아니라는 것뿐이다.

동봉 결과에서 다음이 모두 `as_expected=true`였다.

| 합성 상황 | 왜 유효한 권한 증거가 아닌가 |
|---|---|
| 인증 파일이 없어 `auth_exists_rc=1`, `auth_open_rc=1` | 파일 부재와 정책에 의한 차단을 구별하지 않는다 |
| 전혀 다른 명령이 기대한 `*_rc` 문자열만 출력 | 명령 출력이라는 출처만으로 승인된 검사 명령의 수행을 입증할 수 없다 |
| 앞 항목 `auth_open_rc=0`, 뒤 항목 `auth_open_rc=1` | 마지막 값이 읽기 성공을 덮어 `auth_file_readable` 위반까지 사라진다 |
| `write_rc=0`이지만 실행 뒤 `created.txt`가 없음 | 쓰기 성공 후 삭제된 경우도 현재 조건에 걸리지 않는다 |

이것은 **공개된 run1/run2에서 우회가 일어났다는 주장도, 실제 토큰이 유출됐다는 주장도 아니다.** 그 두 단독 sandbox 관측에는 파일 존재 및 기본 구성의 열기 성공 대조군이 있어 의미가 있다. 결함은 앞으로 실제 exec 결과를 받아 K46을 닫을 관측 도구에 있다.

**제안:** 먼저 비밀이 없는 합성 fixture로 고친다. 검사를 읽기 전용으로 연결한 고정 helper에 넣고, 실행별 nonce·명령/도구 항목 ID·종료 상태·필수 결과를 결합한다. 인증 대상이 실제로 존재하는지는 신뢰된 관측자 측에서 확인하고, `ENOENT`와 `EACCES`/`EPERM` 등을 구분한다. 내부 `test -e`가 반드시 성공해야 한다는 보편 규칙으로 바꾸지는 않는다. 정책에 따라 메타데이터도 가려질 수 있기 때문이다. 중복·누락은 미확인으로 거절하고, **어느 항목에서든 성공한 인증 파일 열기는 이후 결과로 지울 수 없는 위반**으로 남긴다. 쓰기 시도·결과도 확인한다.

실제 로그인 파일을 `cat`해 `/dev/null`로 버리는 현재 명령보다는 **열고 닫기만 하며 내용을 읽지 않는 검사**가 낫다. 다만 임의 명령을 실행할 수 있는 모델에게 프롬프트로만 제한하는 것은 별도 보호 경계가 아니다. 명령이 바뀌거나 추가되면 실패 처리하고, 원문을 공개하지 않는다.

### R02 — 높음 — 실행 직전 기록 검증이 별도 검사기보다 약하다

**위치:** [`core/eligibility.py`][eligibility], [`app/cli_executor.py`의 `_check_eligible`][executor], [`tests/test_core_eligibility.py`][eligibility-tests]. **근거: 재현(해시가 일치하는 원본 모듈) + 문서.**

`eligibility()`는 관측 나이가 상한보다 큰지만 검사하므로 미래 관측이 통과한다. `evidence`는 확인하지 않는다. 기록의 설치 버전과 현재 버전이 둘 다 `None`이면 불일치가 아니어서 통과한다. 실제 실행기는 JSON을 읽은 뒤 이 함수로 바로 넘어가며, `runtime_inventory.validate_manifest_v2()`의 근거·버전 검증을 호출하지 않는다.

실제 재현: 모든 관측일 `2099-01-01`, 문맥 근거 삭제, 양쪽 버전 누락이 각각 `eligible=true`였다. 정상 기록은 허가되고 오래된 기록은 거절되는 대조군도 함께 실행했다. 현재 정상 manifest가 자동으로 변조됐다는 주장은 아니다. **미관측·잘못 작성된 기록을 실행 전에 거절해야 한다는 계약의 누락**이다.

**제안:** 실행 경로와 오프라인 검사기가 같은 작은 구조 검증 함수를 쓰게 한다. 비어 있지 않은 근거·알려진 버전·유효한 날짜를 요구하고 `0 <= age <= max_age_days`를 검사한다. 잘못된 타입과 중복 adapter도 명시적으로 거절한다. 제품 실행·인증 조회 없이 단위 시험으로 고칠 수 있다. 기록 검사기 시험의 통과를 실제 실행 관문의 통과로 대신 쓰지 않는다.

### R03 — 중간 — 관측 도구의 정상 종료·거절 판정이 앱 관문과 다르다

**위치:** [`observe.py:455–474`][judge], [`app/controller.py:165–187`][controller-gate]. **근거: 재현(판정식 발췌) + 문서.**

P3의 합격은 `not (outcome.ok or bool(outcome.usage))`뿐이다. 시간 초과, 실행 상태 `unknown`, 자손 종료 미확인도 올바른 옵션 거절처럼 통과한다. 다른 probe도 `tree_confirmed_empty`와 `model_match`를 공통 필수 조건으로 보지 않는다. 재현에서 자손 종료 미확인 K46와 모델 불일치 b1도 통과했다.

**앱 controller에는 이미 종료 확인·입력 전달·빈 답·모델 불일치 관문이 있다. 그 관문이 우회된다는 발견은 아니다.** 관측 도구는 `prepare()`를 재사용하지만 controller의 수용 조건까지 재사용하지 않는다. 실제 공개 P3 결과는 명시적인 인자 오류와 빠른 정상 종료를 보여 주므로 그 개별 관측을 무효로 취급할 필요도 없다.

**제안:** 프로세스 결과의 공통 수용 조건을 순수 함수로 분리해 함께 사용한다. P3는 버전별로 확인된 오류 종류/문구, 예상 종료 코드, 정상 종료, 자손 종료 확인, 모델 응답·사용량 없음, 경계 위반 없음이 모두 있어야 통과한다. 무관한 실패는 `unknown` 또는 실패다. 잘못된 옵션 때문에 CLI가 stdin을 읽지 않는 것은 P3에서 별도로 설명하되, 입력 전달 표시를 소비 증거로 올리지 않는다.

### R04 — 높음(실제 실행 허가에 사용하기 전) — 관측 상태가 증거 범위와 실행 구성에 충분히 묶이지 않았다

**위치:** [WSL manifest][manifest], [2단계 판정][stage2], [K46 기록][k46], [`core/eligibility.py`][eligibility]. **근거: 관측 + 문서 + 추론.**

Claude의 `CLAUDE.md` 제외는 모델 자기보고와 표식이 답에 없다는 관측이다. init에 로드된 지시문을 열거하는 필드가 없다고 기록 자체가 밝힌다. 따라서 **“외부 지시문 유입을 배제했다”는 계약의 `observed`로 쓰기에는 부족해 `unknown`을 권한다.** Read 제한과 MCP 목록이 빈 것의 긍정 증거까지 지우라는 뜻은 아니다.

Codex의 표식이 있는 작업 폴더에서의 `failed`는 보존해야 한다. 빈 참여자 폴더는 다른 구성이라 그 구성의 문맥은 `unknown`이다. 과거 권한 관측은 옛 `--sandbox read-only` 구성에 대한 읽기 관측과 단독 sandbox 쓰기 시험을 합친 것이다. 지금처럼 argv/profile이 바뀌었는데도 버전과 날짜만 같으면 과거 관측을 재사용할 수 있다. 나중에 문맥 칸만 바꾸면 새 profile의 실제 exec 권한 확인 없이 허가될 수 있다.

**제안:** 과거 기록은 보존하고, 관측 대상의 `CLI 버전 + argv/권한 정책 + 마운트/입력 구성` 식별자를 작게 남긴다. 실제 exec 권한과 단독 진단의 증거 범위를 명시한다. C3의 정책 수용은 관측 성공으로 바꾸지 말고 별도 정책 결정과 미확인 항목으로 남긴다. 전송·문맥·권한의 동일 기준을 두 CLI에 적용한다. 이 PR은 논쟁 가능한 상태값을 원본에서 바꾸지 않았다.

### R05 — 중간 — 승인 상한 검사와 호출 예약이 원자적이지 않다

**위치:** [`observe.py`의 `check_allowed`, `call:415–434`][observe]. **근거: 문서 + 추론(동시 실행 재현은 하지 않음).**

상한을 읽는 시점과 `started`를 쓰는 시점 사이에 잠금/트랜잭션이 없다. 상한 1에서 두 프로세스가 먼저 검사하면 둘 다 통과할 수 있고, `max(n)+1`도 충돌할 수 있다. 결과 파일 이름까지 같은 번호를 사용한다. 기록된 호출들은 순차 수행이어서 실제 초과가 있었다고 말하지 않는다.

**제안:** 상태 폴더에 단일 실행 잠금 또는 작은 SQLite 예약 트랜잭션을 둔다. 승인 ID·provider별 잔여 상한·정지 상태 검사와 시도 번호 예약을 원자적으로 처리한 뒤 프로세스를 시작한다. 이후 실패도 예약을 소비한다. `approve` 재작성과 `--after-failure`는 새 사용자 허락/재개 근거와 연결해야 한다. 새 서비스나 범용 스케줄러까지 만들 필요는 없다.

### R06 — 중간 — `--keep-session` 요약으로 문맥의 부재를 판정할 수 없다

**위치:** [`observe.py:345–370`, `call`의 세션 이동][session], [`tests/test_w2_observe.py`][observe-tests]. **근거: 문서 + 추론.**

요약은 200자 미만 문자열을 건너뛰고 긴 문자열·머리글도 상한에서 자른다. 생략된 범위와 완전성을 충분히 표시하지 않는다. K46 질문 자체에 skill/plugin/MCP를 묻는 내용이 있으므로, 그 단어가 기록에 있다는 것만으로 외부 확장 유입을 뜻하지 않는다. 반대로 안 보인다고 유입이 없었다는 뜻도 아니다.

thread ID가 파일명에 든 새 파일만 이동하게 좁힌 S25 수정은 좋다. 다만 실제 파일명 규약·세션 내부 식별자와의 일치는 가짜 CLI 시험으로 입증되지 않는다. 이동은 공유 DB·캐시에 남은 흔적까지 지우지도 않는다.

**제안:** 세션 ID·시도 ID·이벤트 역할/종류를 대조하고, 짧은 지시문도 포함해 필드 존재 여부와 생략 수를 기록한다. 입력 프롬프트와 provider/사용자/도구가 추가한 내용을 구분한다. 필요한 민감 본문은 로컬에서 사람이 확인하고 공개본에는 판정에 필요한 구조만 남긴다. 모양 요약은 탐색 보조이지 C3 종료 조건이 아니다. `--ephemeral` 제거 자체가 평상시 참여자 구성과 다른 진단 변형이라는 점도 기록한다.

### R07 — 중간 — 가림과 표식 검사는 전 출력의 비밀 유출 방어가 아니다

**위치:** [`observe.py`의 `_scrub`, `_snapshot`, `session_shape`, `call`][observe], [공개 요약][summaries], [`codex_profile.py`][profile-tool]. **근거: 문서 + 추론.**

UUID·긴 ID·JWT 가림은 개선이다. 그러나 경계 위반 검사는 답과 보관된 stdout의 JWT 모양에 한정된다. stderr, JWT가 아닌 인증값, 분할/가공된 문자열은 같은 기준으로 검출되지 않는다. 요약의 모든 자유 문자열이 하나의 최종 가림 단계를 통과하지도 않는다. 로컬 원 출력은 의도적으로 가리지 않고 저장한다. 따라서 “JWT가 없으니 비밀이 안 샜다”는 판정은 불가하다.

`_snapshot`도 자체 상한이 있으므로 `config_changes.counts`는 전체 디스크의 완전한 변경 수가 아니다. 인증 파일의 크기·수정 시각 불변 역시 내용 불변/다른 상태 부작용 없음의 증거가 아니다.

**제안:** 공개 출력은 먼저 고정 필드 허용 목록으로 투영한 뒤 재귀적으로 가리고 사람이 검수한다. 원 출력은 사용자 전용 권한과 보관/삭제 범위를 명시한다. 검사 상한·생략 수·가림 규칙 버전을 남긴다. 토큰 모양 검출은 **추가 정지 신호**일 뿐 근본 방어는 인증 경로에 대한 접근 차단이다. 공개된 JSON에서 실제 비밀을 찾아냈다는 주장이 아니라, 전체 비밀 부재를 인증할 수 없다는 발견이다.

### R08 — 중간 — K01의 “끝까지 읽었다”는 단정이 측정보다 강하다

**위치:** [K01 기록의 결과와 해석][k01], [공개 요약 6번][summaries]. **근거: 관측 + 추론.**

94,777바이트 쓰기 완료와 보고 토큰 증가는 큰 입력 smoke test의 유효한 양성 증거다. 그러나 쓰기 완료는 마지막 바이트의 소비를 뜻하지 않고, 토큰 보고는 CLI의 다른 문맥·도구 왕복·캐시와 분리된 입력 바이트 해시가 아니다. 종료 표식이나 전체 입력 digest 대조도 없다. “일부만 읽었다면 이만큼 늘 수 없다”는 결론은 배제되지 않은 가정에 의존한다.

**제안:** S01의 옵션 누락은 메웠다고 인정하되, 완료 표현을 “약 95 KB 전송 및 정상 응답·토큰 증가 관측”으로 좁힌다. 전체 바이트 전송은 먼저 가짜 CLI로 byte-for-byte 시험한다. 다음에 이미 승인된 큰 입력 관측을 할 때 앞·중간·끝의 독립 표식을 넣어 소비 증거를 강화한다. 끝 표식 하나도 모든 중간 바이트의 정확성 증명과는 구분한다. 이 지적만으로 추가 Claude 호출을 지금 요구하지 않는다.

### R09 — 낮음 — 단독 진단의 `write_refused`는 검사 미실행과 거절을 혼동할 수 있다

**위치:** [`tools/w2/codex_sandbox.py`][sandbox-tool], [`tools/w2/codex_profile.py`][profile-tool]. **근거: 문서 + 추론.**

출력에 `write_rc=0`이 없고 파일이 없다는 조건만으로 `write_refused`를 만들면, 셸 시작 자체가 실패해 출력이 없는 경우도 참이 될 수 있다. 실제 실험 문서는 `~/.codex` 전체 금지로 셸이 시작되지 않은 경우를 대시로 구분해 적었으므로 그 표를 잘못 판정했다고 보지는 않는다.

**제안:** 필수 종료 코드의 존재, 검사 명령 정상 종료, 예상 실패 원인을 함께 요구한다. `not_run`·`denied`·`allowed`·`unknown`을 구분하고 누락 출력 fixture를 추가한다.

## 4. 이번 요청 질문별 답 — 1–9

### 1. K46 방어 설계 — 부분 동의

**인자 구성에는 동의한다.** 관측된 0.156.1에서 exec의 `-P` 오류를 확인하고 `default_permissions`로 고친 것은 적절하다. 옛 `--sandbox`를 제거한 것도 맞다. [공식 권한 문서][permissions-doc]는 이전 sandbox 설정과 새 profile의 혼용 우선순위에 주의를 요구하며, profile의 로컬 명령 경계와 외부 MCP/연결 도구의 권한을 구분한다. 공식 문서는 2026-09-24 열람한 가변 문서이고, 설치된 버전의 행동은 저장소 관측을 우선했다.

실행마다 계산한 **정확한 `-c` 값만 예외로 받는 방식**은 범용 `-c` 허용보다 낫다. HOME의 따옴표·백슬래시·제어 문자 거절과 실행기의 정규화는 TOML/인자 주입 방어로 적절하다. 이것으로 경로 별칭·인증 저장 위치·공유 상태의 모든 노출까지 입증되지는 않는다.

`auth.json` 하나의 차단은 우선 조치이지 공유 `.codex` 전체의 안전 인증이 아니다. 세션·상태 DB·메모리·로그·캐시를 별도 분류해야 한다. 인증 경로를 마음대로 옮기면 로그인·갱신 또는 CLI의 재실행 경로를 깨뜨릴 수 있어 권하지 않는다. 후보는 실행 파일을 인증 상태와 분리하거나, 넓은 차단에 **정확한 실행 파일/런타임 하위 경로만** 읽기 예외로 두는 것이다. 공식 문서의 더 구체적인 경로 규칙을 근거로 한 제안이며, 이 설치판에서 작동한다고 보장하지 않는다. 먼저 가짜 상태로 시험한다.

[설정 참조][config-doc]의 파일/keyring 등 인증 저장 방식은 “항상 고정 파일 하나뿐”이라고 일반화하면 안 되는 이유다. 현재 executor가 임의의 `CODEX_HOME`을 사용자 환경에서 그대로 상속한다는 뜻은 아니다. 현재 구성의 위치를 고정·기록하고 변경 시 다시 검증한다.

### 2. K46 probe와 승인 값 — 현재 합격 조건에는 반대

R01·R03을 먼저 고친다. 현재의 프롬프트와 JWT 검색을 안전 경계로 간주하지 않는다. 실패·거부도 한 번을 소비하고 자동 재호출하지 않는 방향에는 동의한다.

**보강 뒤 사용자에게 제시할 승인안(이 문서는 승인이 아님):** Codex 최대 1회, Claude 0회, 실패·거부·시간 초과도 포함, 호출당 300초 상한, 모델은 기존 관측과 같은 전체 이름 `gpt-6-luna`. 이는 최저 비용 모델이라는 판단이 아니라 변수를 줄이는 제안이다. 인증 대상 부재, 검사 미실행/변형, 종료 미확인, 권한 위반이면 멈춘다. 사용량 한도 신호나 비밀 유출 의심이면 전체 관측을 멈추고 원문을 게시하지 않는다.

`--keep-session`은 기본 꺼짐을 권한다. 같은 한 번으로 C3 자료도 얻기로 사용자가 정한 경우에만 켜고, 기록 보관 범위와 평상시 `--ephemeral` 구성과의 차이를 승인안에 포함한다. 두 기능을 합쳐도 C3가 반드시 닫힌다고 약속하지 않는다.

### 3. 네트워크 없는 exec — 제한된 결론에 부분 동의

“네트워크를 차단한 인증 상태 연결 startup 진단”이라고 부르는 것이 가장 정확하다. 소스는 바깥 bwrap의 새 네트워크 namespace를 유지하면서 `--share-net`을 제거하고, 자료에는 연결 실패와 모델 답 없음이 남는다. **설정 조합 수용, 없는 profile의 명시적 거절**이라는 결론은 타당하다. 모델 명령의 deny 집행이나 로그인 갱신 성공까지는 아니다.

읽기/쓰기 연결된 인증·설정 경로가 있으므로 모델 응답이 없어도 로컬 상태·캐시·로그가 바뀔 수 있다. 크기와 수정 시각이 같다는 것만으로 부작용 없음이나 내용 불변을 증명하지 못한다. 리뷰어는 사용자 환경의 네트워크·백엔드 사용량을 독립 확인하지 않았다. 이후에는 이런 **실제 인증 상태를 연결하는 offline 진단도 범위를 명시해 허락받고**, 가능한 부분은 합성 HOME에서 먼저 검사한다. 과거 기록만으로 무단 과금이나 인증 손상이 있었다고 단정하지 않는다.

### 4. 17번 질문 1–8 — 아래 5절에 각각 답함

핵심은 Claude 문맥을 `unknown`으로 보는 것, Codex의 probe 구성과 참여자 구성을 구분하는 것, 관측 도구의 결과 수용 조건을 먼저 보강하는 것이다. 나머지 질문을 생략하거나 이번 질문의 답으로 뭉뚱그리지 않았다.

### 5. C3 — (a) 우선에 부분 동의, (b)를 관측 성공으로 쓰는 데는 반대

(a)로 실제 참여자 구성의 양성/음성 증거를 늘리는 것이 우선이다. 다만 현재 `session_shape`만으로는 문맥 전체를 볼 수 없다(R06). K46 권한 경계와 기록 수집을 먼저 보강해야 한다. `--ignore-user-config`에도 계정 MCP 연결을 시도했다는 관측은 **연결 경로가 살아 있다는 증거**이지 그 도구가 모델 문맥에 들어갔다는 증거는 아니다.

(b)는 사용자에게 남은 위험을 설명하고 선택받을 수 있는 **정책**이다. 정책 수용이 `failed/unknown`을 과학적 `observed`로 바꾸지는 않는다. 특히 자기 로그인 파일·다른 참여자 상태 노출은 “문맥의 작은 차이”로 묶어 넘길 수 없다. 빈 작업 폴더는 작업 폴더의 AGENTS.md 문제만 줄이며 공유 계정 상태 전체를 지우지 않는다.

### 6. 승인 해석과 자체 병합 — 부분 동의

S22는 바로 앞에 제시한 범위를 사용자의 긍정 답으로 승인받았다는 해석이 가능하다. 사용자가 반드시 숫자를 다시 타이핑해야만 승인이라는 새 규칙을 소급 적용할 근거는 없다. 반면 저장소의 발췌 기록만으로 당시 대화의 모든 조건을 확인할 수 없어 **완전한 준수 인증은 보류**한다. 거절된 첫 승인을 우회하지 않고 멈춘 대응은 적절하다.

다음부터 승인 직전 짧은 카드에 provider·전체 모델·최대 시작 횟수·실패 포함·timeout·멈춤 조건·인증 상태/세션 보관을 한 번에 적고, 그 카드에 대한 사용자 동의를 승인 ID에 연결한다. 숫자 재입력보다 명확한 대상과 변경 불가 기록이 중요하다.

S32의 Claude 세션 CI 녹색 후 자체 병합은 **사용자 §2.8의 허락 범위**이므로 그 자체를 위반이라고 하지 않는다. 다만 CI는 잘못된 합격 조건까지 알아서 검증하지 않는다. 권한·승인·실행 관문·정족수 변경에는 짧은 독립 검토나 반례 표를 먼저 두는 운영 개선을 권한다. 이를 사용자 동의 없이 새 의무 규칙으로 만들지는 않는다. 이 리뷰 세션은 요청대로 병합하지 않는다.

### 7. 되풀이되는 CLI 표면 가정 — 동의

S03·S05·S23은 공통으로 관측되지 않은 표면을 사실로 승격한 문제다. 작은 probe manifest에 정확한 하위 명령, CLI 버전, 확인한 help 파일/줄, 출력 예시의 필드와 타입, 필요한 옵션을 적는다. `plan`은 **실제로 선택한 모델·probe·padding·keep-session을 반영한 argv와 기대 결과**를 보여 주고 필수 자료가 없으면 경고/거절한다.

help의 문자열 일치만으로 기능 집행을 인증하지 않는다. 옵션 존재 → 인자 파싱 → 격리 내 단독 검사 → 승인된 실제 exec 관측의 단계로 나눈다. 없는 필드는 `missing`으로 남기고 모델에게 물어 채운 값을 직접 관측과 섞지 않는다. 계획을 바꾸면 fixture와 예상 출력도 함께 바꾼다.

### 8. 공개 요약 — 부분 동의

HOME·이메일·조직/세션 ID·플러그인 이름을 가리고, 원문을 로컬에 둔 선택은 합리적이다. 읽은 공개 자료에서 토큰이나 계정 이메일의 구체적 노출을 확인하지는 못했다. **완전한 비밀 검사를 통과했다고 주장하지는 않는다**(R07).

판정에 필요한 손실도 있다. 1–5번은 이전 요약 형식이고 원 stdout/stderr가 없으며 플러그인 이름/내용이 제거됐다. 긴 16진수 규칙은 비밀이 아닌 입력 digest도 `<hex>`로 바꿔 전후 자료의 연결을 약화시킨다. 필수 보완은 원문 공개가 아니라, 가린 artifact의 SHA-256·CLI/도구 revision·실제 argv의 안전한 구조·이벤트 수/명령 상태·가림/잘림 여부·관측자 판정 근거다. 초기 자료의 `as_expected`를 새 판정식으로 재계산한 것처럼 쓰지 않는다.

### 9. 다음 순서 — “바로 K46 호출”에는 반대, 오프라인 보강 우선에 동의

R01–R03의 반례를 실패시키는 순수 함수 시험과 R05의 원자적 예약을 먼저 넣는다. 이어서 합성 HOME/합성 인증 대상의 bwrap 진단으로 기본 허용 대조군과 profile 차단을 비교한다. 이 동안 A1의 합성·결정 카드·모의 취소/재접속 작업은 모델 없이 진행할 수 있다.

그 다음에 새 승인으로 K46을 한 번 관측한다. C3는 관측과 정책을 분리해 결정한다. B3 전에는 **현재 구성과 연결된 허가 기록, 실제 executor 연결 경로, 불확실한 종료에서 멈춤, 승인 예산의 원자성, 계정 한도와 봉인 투영, 사용자 재개/취소의 의미**를 확인한다. 단독 sandbox 성공이나 CI 녹색만으로 pilot 준비 완료라고 쓰지 않는다.

사용자 aux-pc/WSL의 실제 설치·로그인·인증 갱신, 원 stdout/stderr, 세션 원문, 플러그인 본문, 실제 모델 이름, 현재 K46 exec 모델 명령의 차단은 직접 확인하지 않았다. B3나 실화면·스크린샷·브라우저 네트워크 동작도 실행하지 않았다. 과거 모델 호출 승인 대화의 전문은 저장소에 없으므로 인용된 범위를 넘는 판단은 보류했다.

요청된 adapter/executor/observe/profile/sandbox/isolation/eligibility와 대응 시험을 중심으로 읽었다. controller와 HTML은 관련 관문·정족수·갱신 경로를 읽었고, 역사적 변경 목록과 관련 PR 패치를 대조했다. **변경 범위의 모든 파일/모든 줄을 새로 감사했다거나 전체 저장소 시험을 웹 컨테이너에서 실행했다고 주장하지 않는다.** 특히 runner·store·N6 대비의 전면 재검증, 동시 승인 경쟁의 실제 다중 프로세스 재현은 하지 않았다.

CI는 이 문서 작성 후에도 새 커밋마다 달라질 수 있으므로 **PR #14의 정확한 head와 Checks 및 PR 본문의 최종 확인 기록**을 기준으로 한다. CI가 녹색이어도 본 검토의 실제 provider 집행 미확인 항목은 닫히지 않는다. 원래 manifest·실험 판정·사용자 정책은 유지하고, 반영 세션이 발견별로 재현/반박을 `RESPONSE.md`에 남기는 방식을 권한다.
