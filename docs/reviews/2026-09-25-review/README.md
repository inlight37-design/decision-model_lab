## 발견

심각도는 이 개인용 도구의 정확성·재현성·명시한 안전 경계를 기준으로 한다. `재현`은 아래 스크립트가 실행한 범위만, `관측`은 이 세션의 코드/API 확인, `문서`는 기존 기록·공식 설명, `추론`은 그로부터의 영향 판단이다. 높은 등급이라고 실제 침해나 유료 호출이 일어났다는 뜻은 아니다.

### R01 · 높음 · Windows 설치 실패를 최종 성공으로 덮을 수 있음

**위치:** [setup-windows.ps1](https://github.com/inlight37-design/decision-model_lab/blob/2f76a1a6fdd6b4ca8edf5111460f7ae806c8977b/tools/setup/setup-windows.ps1)의 winget 루프, pip/hook 설정, 마지막 `-Wsl` 분기와 `$LASTEXITCODE` 반환. **근거: 관측(코드), 문서(S1), 추론. Windows 재현 아님.**

winget 실패는 경고만 쓰고 설치 시도 수를 올린다. 그 뒤 설치 완료·새 셸 안내와 종료 0으로 끝날 수 있다. WSL 쪽 설치 스크립트가 실패해도 곧바로 Windows의 `check_setup.py`를 실행하여 그 종료 코드로 끝낸다. Windows 필수 항목이 준비되어 있으면 WSL 실패가 전체 성공처럼 보인다. pip와 git 설정 실패도 해당 명령 직후 검사하지 않는다. PowerShell의 `$LASTEXITCODE`는 마지막 네이티브 명령의 값이지 앞 단계 실패의 누적값이 아니다.

**제안:** 외부 명령마다 종료 코드를 즉시 보관·판정한다. 실패하면 실패 단계와 재개 명령을 내고 비영으로 끝낸다. 재부팅 필요·새 셸 필요는 실패와 구분하되 전체 준비 완료로 쓰지 않는다. `-Wsl`은 선택한 배포판의 실제 WSL2 상태와 Linux 검사 결과까지 완료 조건으로 삼는다. 윈도우 도구 준비만 확인한 결과를 Linux 참여자 준비로 확대하지 않는다.

**회귀:** winget 실패, pip 실패, wslpath 실패, WSL bash 실패+Windows 검사 성공을 각각 명령 대역으로 주입한다. 이 경계를 통과한 다음 깨끗한 Windows에서 설치·재실행·중단 후 재개를 확인한다.

### R02 · 높음 · 관측 버전 고정이 실패 시 최신판 선택으로 바뀜

**위치:** [setup-wsl.sh:52–55](https://github.com/inlight37-design/decision-model_lab/blob/2f76a1a6fdd6b4ca8edf5111460f7ae806c8977b/tools/setup/setup-wsl.sh#L52-L55), `check_setup.py::observed_versions`. **근거: 관측, 재현, 문서(S2).**

기본값을 두 CLI 모두 `latest`로 넣고, process substitution에서 버전 조회를 읽는다. 조회 실패의 종료 코드는 while 문의 성공으로 전달되지 않는다. 파일 없음은 빈 버전 표가 되고, 잘못된 구조는 예외가 될 수도 있지만 어느 쪽도 명시적인 `--latest` 선택과 구분되지 않는다.

재현에서는 관측 조회 대역이 **7**로 실패했는데 원본 셸의 `--check`는 두 CLI에 `wants latest`를 출력하고 최종 검사 대역의 성공에 따라 **0**으로 끝났다. 실제 최신판을 내려받은 실험은 아니다. 설치 모드가 같은 `want` 값을 사용하는 것은 코드로 확인했다.

**제안:** 먼저 조회 결과와 종료 상태를 별도로 확보하고, 필요한 adapter의 중복 없는 비어 있지 않은 버전이 모두 있는지 검사한다. 누락·형식 오류·조회 실패는 다운로드 전에 중단한다. `latest`는 오직 사용자가 그 모드를 명시했을 때만 선택한다. 해시 고정과 버전 고정은 서로 다른 검사다.

### R03 · 높음 · 설치 변경 승인이 검토한 바이트에 묶이지 않음

**위치:** [setup-wsl.sh:69–80](https://github.com/inlight37-design/decision-model_lab/blob/2f76a1a6fdd6b4ca8edf5111460f7ae806c8977b/tools/setup/setup-wsl.sh#L69-L80), [SETUP](../../SETUP.md)의 설치 스크립트 변경 승인 안내. **근거: 관측, 재현.**

해시가 다르면 파일 A를 임시 경로에 남기고 읽어 보라고 한다. 그러나 `--accept-installer-change`로 다시 실행하면 **새 파일 B를 다운로드하고 모든 해시 불일치를 무조건 허용**한다. Codex와 Claude 파일 모두에 같은 포괄 승인이 적용된다. A를 검토한 사실이 B를 승인한 근거가 되지 않는다.

무해한 설치 대역 A/B로 재현했다. 첫 호출은 3으로 멈추고 A를 보존했다. 이후 응답을 B로 바꿔 승인 옵션으로 재실행하면 B의 표식이 두 번 출력됐고 A는 실행되지 않았다. 네트워크 요청·실제 설치·공급자 파일 변조는 하지 않았다.

**제안:** 설치 프로그램별로 검토한 정확한 SHA-256을 인수나 검토된 설정으로 지정하고, 실행 직전 파일이 그 해시와 같은지 다시 검사한다. 또는 안전하게 보관한 검토 파일 자체를 그 해시로 확인해 사용한다. 일반적인 `accept-any-change`는 제거한다. 임시 파일 정리·실패 시 보존 규칙도 명시한다. 이 수정이 설치 프로그램의 후속 다운로드 전체를 검증하는 것은 아니므로 최종 바이너리 버전 및 공급망 신뢰 범위는 따로 남긴다.

### R04 · 중간 · 설치 확인의 성공이 구독·관측판 준비를 뜻하지 않음

**위치:** [check_setup.py:194–258](https://github.com/inlight37-design/decision-model_lab/blob/2f76a1a6fdd6b4ca8edf5111460f7ae806c8977b/tools/setup/check_setup.py#L194-L258), [설치 확인 시험](../../../tests/test_check_setup.py). **근거: 관측, 재현.**

- API 키 로그인은 두 CLI 모두 `warn`이지만 필수 실패가 아니다. 다른 필수 항목이 정상이라는 조건에서 `render`는 종료 0과 `필수 항목 모두 준비됨`을 낸다.
- Claude 상태 명령의 종료 코드가 1이어도 JSON에 `loggedIn: true`와 구독 방식이 들어 있으면 `ok`가 된다.
- 버전은 부분 문자열로 비교하여 관측 `0.156.1`과 설치 `0.156.10`을 같다고 표시한다. 셸의 설치 생략 판정도 같은 종류의 비교다.

세 경우를 대역 입력으로 재현했다. **실제 실행의 API 과금 관문을 우회했다는 결과는 아니다.** `core.eligibility`에는 별도 구독/버전 검사가 있다. 문제는 설치 완료 안내의 의미와 자동화에서 쓰는 종료 코드가 불일치한다는 것이다.

**제안:** 표시 상태와 필수 준비 여부를 명시적으로 나누고, 구독이 아닌 로그인·실패한 상태 조회는 구독 준비 완료에서 제외한다. 버전은 알려진 출력 형식을 파싱하여 정확히 비교한다. `도구 설치됨`, `구독 로그인 확인됨`, `이 환경의 관측 유효`, `strict 준비 허가`를 하나의 초록색 문구로 합치지 않는다. 계정 원문 출력은 계속 금지한다.

### R05 · 높음 · #70의 정리 실패는 초안 본문 외 메타데이터에서도 가능

**위치:** [controller.py](../../../app/controller.py)의 `_attempt`, `_finish`, `submit_manual`, `_checked_sources`; [report.py](../../../app/report.py)의 `build_report`; [카드 #70](https://github.com/inlight37-design/decision-model_lab/issues/70). **근거: 관측(코드), 문서(기존 전체 재현), 재현(Unicode/SQLite 경계), 추론.**

기존 카드의 RUNNING 고착·worker 제거·자리 점유 관측과 코드가 맞는다. 다만 `_finish`는 초안을 해시하기 **전에** `summary`를 `ensure_ascii=False`로 JSON화하여 SQLite에 넣는다. `detail` 등 문자열 메타데이터에 고립 surrogate가 있어도 이 저장 경계가 실패할 수 있다. 이번 재현에서 정상 JSON 이스케이프를 읽은 고립 surrogate의 UTF-8 인코딩과, 그 문자를 담은 JSON 메타데이터의 SQLite 바인딩이 각각 `UnicodeEncodeError`를 냈다. **전체 controller를 돌려 이 추가 경로의 상태 고착까지 재현한 것은 아니다.**

**제안:** 수용할 초안의 Unicode scalar/UTF-8 유효성을 저장 전에 검사하여 잘못된 답은 형식 오류로 거절한다. 봉인할 본문을 조용히 치환하거나 정규화하여 digest 의미를 바꾸지 않는다. 진단 메타데이터는 별도 안전한 직렬화 정책을 두고 변환 사실을 표시한다. 저장/수용 예외가 worker 밖으로만 빠지지 않도록 종결 경로를 마련하되, **자손 종료 확인이 있을 때만 rejected로 정리하고 미확인은 unknown으로 유지**한다. 호출한 예산을 환불하거나 자동 재호출하지 않는다.

**회귀 범위:** 본문·메타데이터·수동 제출·질문·공통 자료·보고서·합성 입력/결과 경계를 나눠 시험한다. 재시작·취소·다음 queued 시도·봉인 상태·슬롯 해제를 검사한다. 정상 보충평면 문자와 글자 그대로의 `\\ud800`은 허용되는 양성 대조다. #68의 공개 후 실패 원문 escape 정책은 적절한 별도 용도이지 봉인 초안 치환의 선례가 아니다.

### R06 · 높음 · #71은 strict뿐 아니라 모든 실제 호출의 환경 적합성 문제

**위치:** [core/eligibility.py](../../../core/eligibility.py), [app/readiness.py](../../../app/readiness.py), [E2 manifest](../2026-09-25-context-independence/manifest.v2.json), [SETUP 4절](../../SETUP.md), [카드 #71](https://github.com/inlight37-design/decision-model_lab/issues/71). **근거: 관측, 문서, 추론.**

허가 함수에는 현재 기기를 받는 인자도, manifest의 `host`를 읽는 검사도 없다. 같은 버전·명세·날짜의 관측을 다른 PC에 복사했는지 알 수 없다. SETUP이 그 위험을 밝힌 것은 좋지만, 관측 전에는 `--allow-context-unverified`로만 실행하라는 안내는 충분하지 않다. 이 옵션은 C3만 제외한다. 새 기기의 인증·전송·권한까지 확인된 것으로 만들지 않는다.

**제안:** 질문 3의 로컬 등록안을 모든 실제 모드의 시작 전 조회와 실행 직전 재검사에 공통 적용한다. C3 완화 정책도 환경 불일치를 건너뛰지 못하게 한다. 같은 설치판으로 고정했다는 이유로 옛 관측을 새 PC에 자동 등록하지 않는다. 문서는 새 환경의 비-C3 관문도 충족해야 함을 분명히 해야 한다.

## 질문별 답

### 1. A/B/C 분류가 맞는가 — **부분 동의**

A의 제목은 `못 고치는 것`보다 **현재 보장할 수 없는 것과 남은 위험**이 정확하다.

| 항목 | 판정 | 구분과 필요한 행동 |
|---|---|---|
| A1 실제 제공 모델 미보고 | 현재 관측 범위의 한계에는 동의 | 요청 모델, 계정의 가용 모델, 응답이 보고한 제공 모델을 분리한다. 설치판/공식 통로가 바뀌면 다시 볼 수 있으므로 영구 불가능으로 고정하지 않는다. 응답이 모델을 자칭한 문장은 공급자 메타데이터가 아니다 |

| A3 합의·인용과 사실 | 동의 | 글자 일치 검사와 실행 가능한 검산은 별개다. 정답이 정의된 하위 과제는 코드·수학적 검산을 더할 수 있으므로 모든 사실 검증을 포기할 이유도 없다 |

| A6 원격 변화 | 부분 동의 | 공급자의 미래 변화를 막을 수는 없지만, 실행 전 표면 차이 확인·실행 설정 고정·만료·거절은 구현 가능한 완화다. #64/C6은 실제 작업으로 남긴다 |
| A7 네트워크 | 부분 동의 | 공급자 연결 필요와 호스트 전체 네트워크 공유는 같은 요구가 아니다. C7로 localhost·임의 목적지 노출을 줄일 여지가 있다. 프록시가 모든 CLI·갱신·DNS 경로와 맞는지는 미검증이다 |

**B에 추가할 것:** R01–R04 설치기의 실패 경계와 무해한 설치 명령 대역 시험. #70에는 메타데이터/예외 정리를 명시한다. B4·B10은 `관측 수명과 환경`이라는 공통 절차를 쓰되 기존 PC 갱신과 새 PC 등록을 다른 사건으로 기록한다. B9의 입력 파일 바꿔치기는 CPU/메모리 제한으로 해결되지 않으므로 별도 완료 조건이 필요하다.

**줄일 것:** A–F 전체 재실행, 이미 병합된 #69 재수정, 공급자가 주지 않는 정확한 구독 차감의 추측, 전체 1 MiB 재시도를 당장의 최우선으로 두는 일, 카드 시범을 위해 새 조정자/DB를 도입하는 일. C2는 L1의 보조 측정, C9는 현재 시범 기록으로 처리하여 별도 큰 프로젝트로 만들지 않는다.

### 2. 새 PC 준비 도구는 안전하고 빠짐없는가 — **부분 동의; 설치 완료 승인에는 반대**

공식 설치 통로, 로그인은 사람이 하기, API 환경변수의 이름만 표시하기, 계정 식별 값 비출력, SHA 변화 시 기본 중단, 설치와 확인 모드 분리는 좋은 선택이다. winget 약관을 자동 수락하지 않는 것도 사용자의 동의 경계를 존중한다. 그러나 그 결과 생기는 거절/중단을 설치 성공으로 덮어서는 안 된다(R01).

R01–R04를 고친 뒤 `아무것도 없는 PC → Windows 도구 → 정확한 WSL2 배포판 → Linux 의존성/CLI → 사람의 로그인 → 이 환경의 관측 → strict 준비 조회`를 단계별로 확인해야 한다. 최초 Git 설치 후 새 셸의 PATH, Python 실행 별칭/여러 버전, 한글·공백 경로, 의도한 배포판이 아닌 다른 Ubuntu만 있는 경우, 중간 실패 후 재실행을 포함한다. 암호·로그인까지 무인으로 처리하는 설치기로 넓히지는 않는다.

현재 Python 단위시험은 주로 가짜 조회 응답을 검사한다. 설치 셸 자체의 오류 전파와 승인 대상을 검사하는 통합 경계가 빠져 있다. 이번 probe는 그 빈틈을 보이는 **고정판 특성 재현**이며 회귀 시험 전체나 깨끗한 PC 설치의 대체물이 아니다.

### 3. #71 이름표 대 기기 해시 — **이름표 단독에는 반대, 공개 기기 해시에는 판단 보류, 로컬 등록안 권고**

(a) 명시적 이름표 비교는 실수 탐지에는 도움이 되지만 새 PC에서 `aux-pc-wsl`을 적으면 통과한다. (b) 기기 식별자의 단순 해시를 공개 저장소에 올리는 것은 필요 이상의 지속 식별자를 만든다. systemd는 원래 machine ID를 외부에 노출하지 말고 애플리케이션별 비가역 식별자를 권고한다(S4). 그렇더라도 공개가 꼭 필요한 것은 아니다.

**작은 대안:** 관측을 마친 환경마다 임의 등록 ID를 만들고, 저장소 밖 사용자 전용 상태에 `등록 ID ↔ 로컬 환경 지문 ↔ 허용한 관측 판`을 저장한다. 공개 manifest에는 의미 없는 등록 ID와 사람이 읽는 이름표만 둔다. 로컬 환경 지문은 애플리케이션별 유도 ID와 필요한 실행 환경 범위에 묶되 공개하지 않는다. 매 실제 계획/실행에서 현재 환경과 로컬 등록을 대조하고, 등록 없음·불일치·손상은 거절한다. 처음 clone했다는 이유만으로 자동 등록하지 않는다. 기밀 인증 파일의 내용을 지문 재료로 읽지 않는다.

`host.label`은 설명이고, 실제 권한 근거는 이 환경에서 수행한 관측과 로컬 등록이다. 구형 manifest는 날짜를 고쳐 쓰지 말고 명시적인 이행·새 기록을 만든다. 배포판 export/import, 재설치, 다른 OS 사용자, 실행 설정 변화의 재등록 규칙도 정한다. **전체 VM과 로컬 상태를 복제한 악의적 주체까지 막는 원격 attestation은 아니다.** 이 도구의 현실적 목표인 우발적 cross-PC 재사용 방지와 그보다 강한 위협 모델을 구분한다.

완료 조건은 이름표 불일치 하나가 아니라 등록 없음·잘못된 환경·관측 만료·판/버전 변화·C3 완화 모드·조회 후 실행 전 변경을 모두 거절하고, 실제 기존 환경의 적법한 새 등록만 허용하는 것이다. 최소 구현을 먼저 택하되 명칭을 `기기 증명`으로 과장하지 않는다.

### 4. #70 거절 대 치환 — **거절에 동의**

봉인하는 초안은 원문이므로 `errors=replace`나 전역 escape로 조용히 바꾸면 안 된다. 입력 경계에서 유효하지 않은 Unicode를 형식 오류로 거절하고 안전한 고정 오류 코드로 끝내는 것이 맞다. 질문·자료·수동 답의 잘못된 입력은 요청 오류로 돌려주고, 실제 실행된 참여자 결과는 종료 증거에 맞는 종결 상태를 원장에 남긴다.

진단 원문은 다른 계약이다. #68처럼 공개 후 검사 실패한 합성 원문을 escape·길이 제한·표시와 함께 남길 수 있다. 그 텍스트의 digest 정책과 봉인 초안의 UTF-8 digest 정책을 혼용하지 않는다. R05의 메타데이터 경계와 예외 복구도 함께 고쳐야 본문 검사만 통과한 뒤 같은 고착이 다시 생기지 않는다. `build_report`와 합성의 초안 재검사도 손상 데이터에 임의 500/worker 예외 대신 명시적 실패를 내도록 본다.

### 5. 우선순위와 E2 갱신 대 L1 — **부분 동의**

권고 순서는 **#70 및 R01–R04 → #71과 새 PC의 관측 절차 → #64/C6의 작고 저렴한 설정 고정·표면 검사 → L1 → 큰 자료/편의 기능**이다. #70과 설치 수정은 독립 브랜치로 병렬 준비할 수 있지만 같은 파일의 writer는 하나로 둔다. 새 PC의 실제 호출은 그 환경의 관측 없이 먼저 하지 않는다.

E2 갱신은 모든 작업을 무조건 막는 오늘의 긴급 실험이 아니라 **사용할 환경/판과 만료일의 선행 조건**이다. 현재 코드의 날짜 비교와 manifest에서 가장 오래된 2026-09-24 인증 관측을 적용하면 2026-10-24는 30일, **2026-10-25는 31일로 거절**된다. 설치판·계획·환경이 바뀌면 달력 만료 전에도 다시 관측해야 한다. 같은 유효 환경에서 더 이른 날짜에 L1을 한다면 이를 위해 E2 전부를 먼저 반복할 필요는 없다. 새 PC에서 L1을 한다면 그 PC 관측이 먼저다.

기한 가까이 여유 없이 갱신하기보다 필요한 새 설정(#64 등)을 먼저 정하고 그 **정확한 최종 판**을 한 번 관측한다. 만료를 피하려고 관측 날짜만 새로 쓰거나 max_age를 늘리는 방법은 쓰지 않는다. 갱신 때 C4의 전역 문맥 대조도 가능한 범위에서 묶어 중복 호출을 줄인다.

### 6. 가치 큰 추가 조사 세 가지와 L1 방법 — **C1·C6·C8 우선에 동의(권고)**

**첫째 C1/L1: 추가 합성이 잘못된 자기 계열 초안보다 정답을 선택하는가.** 초기 D는 합성자와 맞은 초안이 같은 계열이었다. D 후속 T1은 두 초안의 최종 결론이 같았고 합성은 형식 실패였다. T2의 잘못된 설명 전이는 두 실험에서 합성자 계열을 바꿔도 생겼지만 초안 자리와 문체가 얽혀 있었다. 이것만으로 제 계열 편향이나 일반적 합성 이득을 확정하지 않는다.

실험 전에 과제 풀·정답/실행 가능한 검산·조건·반복 수·최대 provider별 시작 횟수·시간 상한·멈춤 조건·제외 규칙을 커밋한다. 오류가 난 과제만 사후 선택하지 말고 모든 시작한 실행, 무불일치, 형식 실패, timeout도 분모와 비용에 남긴다. 주 지표는 객관적 정확성, 맞는 초안의 보존, 잘못된 설명의 전이, 유효 합성 완료율, 추가 시간/호출이다. 모델 채점은 정답의 권위가 아니라 별도 보조 자료로 두고, 공급자와 초안 대응을 가린 뒤 과제별로 짧게 나눈다.

앱 계약은 **그 실행에 있는 CLI provider 중 합성자 선택, 실행마다 한 번 합성**이다. 따라서 현 앱으로는 같은 두 초안에 두 합성자를 교차 적용하는 짝지어진 비교를 할 수 없다. 앱을 바꾸지 않는 최소안은 과제별 독립 반복에서 합성자 provider를 균형 있게 배정하고 실제 초안·이름표 대응·정답 여부를 저장하는 것이다. 이는 초안도 다시 생성되므로 `동일 초안 짝비교`라고 부르면 안 된다. #68의 해시 순서는 고정된 provider 순서를 깨지만 작은 표본의 정확한 균형까지 보장하지 않는다. 배정은 결과를 보기 전에 정하고 한 번 실행한 결과를 순서가 마음에 안 든다는 이유로 재추첨하지 않는다.

동일 초안의 인과 비교가 꼭 필요하면 공개·동의된 **고정 초안 challenge를 받는 실험 전용 하네스**를 별도 설계한다. 생성 출처와 편집 여부를 기록하고 provider/순서를 교차한다. 인위적으로 만든 오답은 실제 그 모델이 냈다는 증거가 아니므로 자연 생성 L1과 다른 실험으로 보고한다. 기존 원장·한 번 합성 제한을 우회하거나 미공개 초안을 꺼내 쓰지 않는다.

**둘째 C6(+ #64): 추가 모델 호출 없이 원격/문맥 표면 변화를 싸게 잡을 수 있는가.** 우선 계획에서 명시적으로 끌 수 있는 앱·플러그인·메모리 항목을 고정한다. 기존 모델 없는 도구/스킬 목록과 입력 렌더링을 최종 계획으로 실행해 허용 목록/최소 지문과 대조하는 작은 전후 시험을 설계한다. 합성 데이터의 설정 하나만 바꿔 탐지되는 양성 대조도 필요하다. 계정 식별 값과 인증 원문은 버리고 관측 시각·설치판·명세·분류된 차이만 기록한다. 알 수 없는 표면은 경고만 내고 독립으로 세는 대신 정책에 따라 거절/미확인으로 둔다. 이 검사는 최종 요청이나 공급자 내부 상태의 완전한 증명이 아니므로 A1·A2를 해결했다고 하지 않는다.

**셋째 C8: 실행 자원 제한을 기존 종료 계약에 결합할 수 있는가.** WSL의 systemd 지원 자체는 공식적으로 문서화돼 있다(S5). 그러나 해당 사용자 세션에서 user manager·cgroup 위임·bubblewrap과의 조합은 별도로 봐야 한다. 실제 모델 없이 짧고 제한된 합성 부하를 CPU·메모리·자손 수별로 하나씩 주고, 제한 발동 뒤 controller가 멈추지 않는지, 자손 종료 증거·원장 기록·슬롯 회수가 맞는지 확인한다. 제한기가 없으면 조용히 무제한으로 시작하지 않는다. 정확한 시스템 서비스 옵션과 그 환경의 지원 여부는 구현 때 확인하고, 단순히 명령 앞에 wrapper를 붙였다는 이유로 runner의 `tree_confirmed_empty`를 참으로 바꾸지 않는다.

C2는 첫 조사에 붙이고 C4는 다음 E2에 붙인다. C3(출력 도중 취소)도 중요하지만 공급자 내부에서 요청을 받았는지/과금을 되돌렸는지는 로컬 프로세스 종료만으로 답할 수 없다. C7은 별도 네트워크 위협 모델·메타데이터 조회/인증 갱신 경로까지 포함한 설계가 필요하다. C5/전체 1 MiB는 현재 목적상 다음 순위다.

### 7. 카드 보드 시범 — **작게 계속하는 데 동의; 정식 채택은 판단 보류**

[사전 등록된 시범](../../experiments/2026-09-25-card-pilot/README.md)에는 사용자 중계, 다른 세션의 이어받기, 중복 없음, 검토 왕복, 호출 상한이 기준으로 있다. #59는 실제 GitHub 댓글 경로를 열었고 #60·#66 기록은 재설명 없이 인계한 사례를 제시한다. 동시에 #60은 실행 설정·로그인 셸 안내가 부족했고, 교차검토의 지적 없음만으로 강한 품질 보증이 되지는 않는다.

초기 끝 조건은 원래 카드 #58–#61이 닫히거나 사용자가 그만할 때다. 새 카드를 계속 추가해 끝 조건을 무한히 미루지 않는다. 이익을 사용자 중계 감소와 재개 성공으로 판단하고, 모델 성능 향상이나 작업 시간 절감의 정량 증명으로 확대하지 않는다. 현재 카드+기존 Git+인계 포인터를 유지하고 별도 보드 DB·자동 슈퍼바이저는 추가하지 않는 것이 적절하다.

이번 리뷰도 카드와 요청서만으로 범위를 파악했고 원격 체크포인트를 남겼다. 다만 담당 댓글은 첫 커밋보다 늦었다. 이것도 운영상 흠으로 #73에 기록했다. 다음에는 **카드 확인·담당 댓글 → 브랜치 작업 → 중간 원격 커밋 → 결과 PR** 순서를 지킨다. 종료 시점의 채택 여부는 사용자가 정한다.

## 재현 자료와 확인하지 못한 것

[probe.py](probe.py), [실제 결과](probe-results.json). 실행 명령:

```sh
python docs/reviews/2026-09-25-review/probe.py --root .
```

기준 설치 파일의 blob SHA가 다르면 스크립트는 중단한다. Python은 필요한 함수만 AST로 읽어 대역 명령을 주입한다. 셸은 원본 파일을 임시 디렉터리로 복사하고 curl·설치·sudo·CLI·관측 조회를 무해한 대역으로 바꾼다. 원본 관측 기록이나 인증 값을 읽지 않는다. 성공 종료는 **발견한 현상을 재현했다는 뜻**이지 애플리케이션 시험 통과가 아니다.

직접 하지 않은 것: 깨끗한 Windows/WSL 설치, PowerShell 실제 종료 코드 실험, 실제 구독 CLI/로그인/모델 호출, controller 전체의 #70 재현, 원본 앱 전역 메모리 행동 대조, systemd 자원 제한/네트워크 허용 목록 실험, 실제 브라우저 조작, 전체 로컬 시험 및 모든 문서 링크의 자동 전수 검사. 전체 CI 상태는 PR의 정확한 최종 head에서 따로 확인해야 한다. 기존 E2/D 등의 실제 PC 관측을 취소하거나 낮춰 적는 것이 아니라 이번 세션의 접근 범위를 한정한 것이다.
