# 구조 전수검사 — 덧대기인가, 구조적 해결인가 (2026-09-24)

작성: claude (Claude Code 웹 컨테이너 — 사용자 PC·WSL·로그인된 CLI 없음, 모델 호출 없음). 기준 main `99d9bb44720bed2d6917dd4626eb8a172af5ab23`(PR #18 병합 뒤).

사용자 요청: "우리 아키텍처가 최소 코드·최대 효율로 문제 부분을 다시 짜서 구조적으로 해결하는 식이 아니라, 누더기처럼 덧대는 식으로 짜고 있는지 전수검사."

**독립성.** ChatGPT가 같은 주제를 따로 검사하고 있다(`chatgpt/lean-cancellation-20260924`). 이 문서를 처음 커밋할 때까지 그 브랜치와 `.review-work/`는 읽지 않았다. 따라서 이 문서는 blind 초안이다. 두 결과의 비교는 따로 적는다. 두 결과가 같다고 해서 검증된 것은 아니다. 비교는 이 초안을 커밋(`9353779`)한 뒤 [COMPARISON.md](COMPARISON.md)에 썼다.

## 결론

**뼈대는 구조적이고, 살은 덧대기다.** 전면 재작성은 필요 없다. 필요한 것은 흩어진 사본을 한 주인으로 모으는 통합이고, 그 통합은 대부분 코드를 줄이는 방향이다.

- **뼈대(유지할 것).**
  - 실행 층이 나뉘어 있다: runner → isolation → adapters → executor → controller.
  - 상태 변경은 기대 상태를 조건으로 거는 UPDATE다.
  - 공개 판정을 같은 거래 안에서 하고, 원장은 덧붙이기만 한다.
  - 수용 관문은 순수 함수이고, 봉인은 허용 목록이며, 보고서는 순수 투영이다.
  - 관측 도구에는 승인 장부가 있다.
- **살(고칠 것).** 리뷰 발견이 올 때마다 발견된 자리에 분기·플래그·검사를 하나씩 붙였다.
  - "한 곳이 주인"이라고 적어 두고 실제로는 연결하지 않은 곳이 여럿이다.
  - 그래서 같은 규칙의 사본이 3–5벌로 흩어졌다(가림, 출력 해석, 참여자 상태, 봉인 규칙, 기록 검사).
  - 문서가 약속한 것과 코드가 다른 곳도 생겼다. 4절의 아홉 가지는 모두 직접 재현했다. 지금 흐름에서 실제로 뚫린 것은 없지만, 다음 기능(K17 실제 실행기 연결, K19 취소)이 들어오는 순간 드러난다.
- **복붙은 원인이 아니다.** 6줄 이상 같은 코드는 한 곳뿐이다. 누더기는 개념의 사본과 특수 분기의 형태로 쌓였다.
- **과정이 코드보다 더 덧대기이고, 코드의 덧대기를 만든다.**
  - 제품 코드를 고친 커밋은 14%다. md만 고친 커밋은 49%다.
  - 문서는 제품 코드의 약 3.4배이고, 인계 문서는 27시간 동안 6번 통째로 다시 쓰였다.
  - 알려진 한계는 지금 41개가 열려 있다. 지금까지 닫힌 5개 가운데 코드 변경으로 닫힌 것은 없다.
  - 리뷰 반영은 대부분 조건과 필드를 더했다(`if/elif` +113/−35).
  - 발견 하나에 국소 수정 하나, 사건 번호 주석 하나, 문서 단서 하나를 붙이는 반영 방식이 그대로 코드 모양이 됐다(3절 이력).
  - 2026-09-24에 이 세션이 브랜치 정리를 5곳의 상시 규칙으로 적은 것도 같은 무늬다(H-07).

## 1. 방법

- **범위:** `core/`, `app/`, `tools/`의 모든 파일, 그 파일을 고정하는 `tests/`, main의 전체 이력, 규칙·인계·검토 문서.
- **나눔:** 네 갈래(core, app, tools, 이력·문서)를 같은 지표로 병렬 검사했다. 각 갈래는 파일을 전부 읽고, 파일마다 `git log -p`로 자란 과정을 따라갔다.
- **확인:** 결론과 4절의 틈은 이 문서를 쓴 세션이 코드와 재현 명령으로 직접 다시 확인했다. LOC 추정은 설계 스케치 기준의 대략값이다.
- **지표:**

| 지표 | 뜻 |
|---|---|
| P1 | 특정 provider·probe·버전·사건을 위한 분기가 일반 코드 안에 있다 |

## 3. 영역별 판정

### core/ — 두 파일이 누더기, 나머지는 대체로 구조적

| 파일 | 판정 | 근거 |
|---|---|---|
| `runner.py` | 혼합(대체로 구조적) | `RunResult`가 사실만 담는다. reader/writer 소유권, 표식 계수는 구조적이다. `pid_namespace` 플래그와 bwrap 모양 검사는 덧댄 흔적이고, 약 110줄은 CI가 돌리지 않는 동결 Windows 경로다 |
| `adapters.py` | 누더기 | `build_spec` 매개변수 11개 중 5개가 한 provider 전용이다. 공용 `_check`에 codex 예외가 있다. 거절 판정 3세대가 함께 남았다. 명세 판(`SPEC_REVISION`)은 손으로 쓰는 전역값이다 |
| `isolation.py` | 혼합 | `Sandbox → plan → run` 층은 좋다. 연결 겹침 규칙은 리뷰마다 한 개씩 늘었다(4절 G1). 내부 함수(`_trusted_bwrap`)를 app과 tools가 직접 부른다 |
| `env.py` | 구조적 | 변수 목록 하나에서 파생한다. 토큰 정책만 isolation과 다르다(G8) |
| `membership.py` | 구조적이지만 연결되지 않음 | 순수 함수다. 그러나 controller가 결정의 `action`·`note`를 버리고 정족수를 따로 센다 |
| `eligibility.py` | 누더기 | 공유한다던 `row_problems`를 `eligibility()`가 부르지 않고 같은 검사를 다시 쓴다(G5) |

### app/ — 핵심은 구조적, 상태 동기화와 가장자리가 덧대기

| 파일 | 판정 | 근거 |
|---|---|---|
| `controller.py` | 혼합 | 수용 관문, 조건 UPDATE, 같은 거래 안의 공개 판정은 구조적이다. 그러나 참여자 상태를 두 곳에 두고(참여자 행과 `runs.roster` JSON) 전이마다 손으로 맞춘다. 모의 실행기 지식이 일반 코드에 있다(G6) |
| `store.py` | 구조적(가장자리만 덧댐) | 파일 잠금, 거래, 덧붙이기 사건은 좋다. 기본값이 앱보다 느슨하다(G7). 이중 try는 잠금 획득·해제를 enter/exit에 나눈 탓이다 |
| `server.py` | 혼합 | 헤더·길이·토큰 검사는 한 곳에 있다. 본문 검증과 라우팅은 if 사슬과 점점 커지는 예외 튜플이다. 넓은 `except`가 controller 내부 버그까지 400으로 감춘다 |
| `cli_executor.py` | 혼합 | 계획 → 실행 → 해석 흐름은 깔끔하고 관측 도구와 공유한다. provider별 if가 있고, 모의 실행기와 계약이 다르다(시작 전 거절이 한쪽은 rejected, 한쪽은 unknown) |
| `report.py` | 구조적 | 봉인된 view의 순수 투영이다. 흠은 봉인 해시를 대조하지 않고 다시 계산한다는 것이다 |
| `static/index.html` | 혼합 | `h()`는 좋다. 그러나 controller 규칙("승인 대기", "공개됨")을 화면에서 다시 유도한다 |

**참여자 상태 전이의 복붙:** 모든 전이가 같은 순서를 되풀이한다. roster 읽기 → `m.decide().roster` → 참여자 UPDATE → roster UPDATE → 사건 → `_maybe_reveal`.
- `m.decide`: `controller.py` 362·369·450·481·498
- `UPDATE runs SET roster`: 371·401·454·485·503
- 조건 UPDATE는 pump와 `_finish`에만 있다. submit·withdraw·acknowledge·`_recover`는 SELECT로 확인한 뒤 조건 없이 UPDATE한다.
- 시험이 쓰는 구성(Store 하나에 controller 둘)에서는 submit과 withdraw를 교차시키면 참여자는 `accepted`인데 roster에는 `dropped`로 남는다. 운영 구성(controller 하나 + RLock)에서는 재현되지 않았다.

집계 방법: `git log origin/main --no-merges`에서 부모가 없는 루트 커밋을 뺐다. 파일 목록은 `git diff-tree`로 분류했다. 줄 수는 `git grep -c -v -e '^[[:space:]]*$' <sha> -- <경로>`로 셌다. 인계 크기와 K 표의 변화는 병합 커밋마다 `git show`로 봤다. "사건에서 나온 규칙"과 "부류 제거" 분류는 커밋 메시지와 `git log -S`에 근거한 판단이다.

## 6. 유지할 것

- `RunResult`는 사실만 담는다. `tree_confirmed_empty`는 한 곳에서 파생한다. `_Reader`는 자기 스트림을 스스로 닫는다.
- `Sandbox`는 frozen 명세이고, 환경 값은 argv에 싣지 않는다. `ETC_LINKS`는 일반 규칙이다.
- `env`는 변수 목록 하나에서 파생하고, 의존 방향을 시험이 지킨다.
- `acceptance()`는 순수 관문이고 관측 도구와 공유한다.
- 기대 상태·시도 ID를 조건으로 거는 UPDATE와 바뀐 행 수 확인. 없애지 말고 모든 전이로 넓힌다.
- 같은 거래 안의 공개 판정, 단일 작성자 파일 잠금, 덧붙이기 사건, 새 스키마 거절, 허용 목록 봉인, 순수 보고 투영.
- 관측 도구의 승인 장부(flock 안의 승인 검사·예약, 실패도 1회), 모델 말이 아니라 명령 출력으로 판정하는 `k46_check`.
- `runtime_inventory`의 Adapter/Feature 표. probe 표(5절 6)가 본뜰 모양이다.

## 7. 한계와 검증하지 않은 것

- 모델·실제 CLI·사용자 PC·WSL은 쓰지 않았다. G1–G9는 코드 경로와 오프라인 재현이다. 실제 호출에서 이메일이나 민감한 이름이 나온 적이 있는지는 원 출력(사용자 PC)을 보지 못해 모른다.
- LOC는 설계 스케치 기준의 추정이다. 5절 1·3의 "판정 차이 0"은 검사 갈래가 스크래치 사본에서 한 무작위 비교다. 이 문서의 세션이 그 시제품을 다시 돌리지는 않았다.
- 3절의 경합(controller 둘)은 시험 구성에서만 재현됐다.
- 이 컨테이너는 root로 돈다. 그래서 전체 시험의 `test_only_a_root_owned_bubblewrap_is_trusted`는 일반 사용자로 돌려야 한다(PR #16·#18과 같은 사정).
