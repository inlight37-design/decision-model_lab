# 두 검사의 비교 — claude 구조 전수검사 ↔ ChatGPT 간결성·수명 검토 (2026-09-24)

작성: claude.
- 이 폴더의 [blind 초안](README.md)을 커밋(`9353779`)한 뒤에 ChatGPT의 [검토](https://github.com/inlight37-design/decision-model_lab/blob/201d9d7b831f6eef7e01e606997ed1c708c07f76/docs/reviews/2026-09-24-lean-lifecycle/README.md)와 코드를 읽고 썼다. - 두 초안은 서로를 보지 않고 쓰였다. ChatGPT의 검토 체크포인트(`0dca5ca`)와 수정(`32c1e2a`)은 claude 초안보다 먼저 커밋됐고, claude는 초안을 커밋할 때까지 그 브랜치를 읽지 않았다.

## 1. 같은 판단

- 전면 재작성은 필요 없다. 단일 프로세스, SQLite 원장, 빌드 없는 화면, 실행 층 분리, controller의 상태 권위는 유지한다.
- 의존 방향은 깨끗하다: server → controller → store, executor → isolation → runner.
- 실제 낭비와 결함은 기존 구조 안에서 고친다.

## 2. 근거가 갈리는 곳

| 주제 | ChatGPT | claude | 정리 |
|---|---|---|---|
| "간결"의 기준 | 새 부품(모듈·패키지·서비스·엔진)을 더하지 않는다. 런타임 낭비를 잰다(화면 조회 18.1 ms → 0.05 ms, 합성 측정) | 같은 규칙의 주인을 하나로 모으고 사본을 지운다. 문서가 약속한 것과 코드를 대조한다 | 둘은 다른 축이고 둘 다 필요하다. ChatGPT의 축은 런타임 비용, claude의 축은 규칙의 소유와 불일치다 |
| 문서·과정의 무게 | 연구 문서의 양을 제품 런타임 복잡도와 혼동하지 말라 | 과정이 코드 덧대기의 원인이다. 제품 코드를 고친 커밋이 14%이고, 반영이 조건·필드 추가 중심이다 | 런타임 복잡도로는 ChatGPT가 맞다. 그러나 "덧대는 식으로 짜는가"라는 질문에는 과정의 근거가 있다. 이견이라기보다 범위 차이다 |
| **K19 취소 설계** | 되돌리지 않는 플래그 `runs.cancel_requested`를 둔다. "membership에 두 번째 상태 기계를 얹지 않는다" | 참여자 상태의 주인을 하나로 모으고, gate를 파생한 뒤, 취소를 전이 하나로 넣는다(초안 5절 4). 지금 구조에 넣으면 새 플래그와 손 동기화가 하나 더 는다고 예측했다 | **미해결. 근거가 갈린다.** 아래에 따로 적는다 |
| `tools/` | 제품 런타임 기준이라 범위 밖 | 관측 도구가 두 번째 controller로 자랐다. 가림 5벌, 약속한 이메일 가림 누락이 있다 | claude만 봤다 |

**K19 취소 설계의 두 입장.**
- **PR #20의 모양:** controller가 판단에 `cancel_requested`를 읽는 곳이 7곳이다.
  - 대기 조회(228), pump(287), `_finish`의 결과 덮어쓰기(368), `_maybe_reveal`(405), `submit_manual`(461), `approve_reduction`(509)
  - 화면의 호출 집계는 `status != "cancelled_before_start"` 문자열 비교로 한다(578).
  - `cancel_run`은 참여자 행을 바로 UPDATE하고 명단(roster)은 맞추지 않는다. 공개가 막혀서 지금은 드러나지 않는다.
  - claude 초안이 예측한 모양이다.
- **ChatGPT의 걱정도 타당하다.** 두 번째 상태 기계는 비대하다.
- **둘은 양립한다.** claude의 제안은 새 기계를 얹는 것이 아니다. 기존 참여자 행을 유일한 주인으로 두고 `gate()` 하나를 파생하는 것이다. 그 `gate()`가 `cancel_requested`를 읽으면 7곳이 1곳이 되고, 플래그는 그대로 쓸 수 있다.

## 3. 한쪽만 찾은 것

- **ChatGPT만 찾았고 PR #20이 고쳤다**(회귀 시험 22건, PR CI 녹색):
  - 화면이 사건 전체를 읽는다(→ SQL `LIMIT 12`).
  - 보고서 하나를 위해 모든 실행을 투영한다(→ `view(run_id)`).
  - 끝난 스레드 참조가 쌓인다.
  - 시작에 실패해도 예약이 남는다.
  - 잔류 I/O 집계에 경합이 있다.
  - 인증 전 연결 수와 I/O 기한에 상한이 없다.
- **claude만 찾았고 아직 고치지 않았다:** 초안 4절의 G1–G9.
  - 격리 계획의 시스템 경로 연결, 이메일 가림 누락, init 이름 공개 정책, 관측 argv와 명세 판, `row_problems` 미공유, 모의 표시, 원장 기본 정책, 토큰 변수 정책, membership 결정.
  - PR #20은 이 가운데 어느 것도 바꾸지 않는다. 해당 문자열과 함수가 PR #20 head에서도 같다.

## 4. PR #20에서 본 과정

- PR #20의 커밋 11개 중 7개는 소스 전달·정리용 chore다(임시 워크플로, base64 체크포인트, 적용, 제거). ChatGPT의 분석 컨테이너가 git에 직접 닿지 못하기 때문이다(PR #18·#20 본문).
- 결과 tree에는 남지 않았다. 그러나 환경 제약이 만든 과정 덧대기다. ChatGPT 쪽에서 직접 clone/push가 되면 사라진다.
