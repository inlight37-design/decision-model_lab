## 1. 결론

**핵심 실행 구조는 유지한다. 역할판 A의 결과·상태 표시를 바로잡고, 기존 실행 수명의 예외 처리를 보완한 다음 B–E를 진행하는 편이 맞다. codex-peek에서 가져올 것은 또 다른 엔진이 아니라, 현재 결과와 검토의 결속·명확한 처분·제한된 입력 기록이다.**

[Codex의 구조 검토](../2026-09-26-architecture-health/README.md)는 “우리 코드의 어디가 깨지는가”, [Claude의 Peek 검토](https://github.com/inlight37-design/decision-model_lab/blob/6d6fdb9debc07ef835dd3d3f0b224f372a918c01/docs/reviews/2026-09-26-codex-peek-claude/README.md)는 “외부 도구에서 무엇만 배울 것인가”에 답한다. 둘은 경쟁하는 설계가 아니라 다른 층의 검토다. 다만 우선순위와 일부 구현 표현은 아래처럼 수정해서 받아들여야 한다.

## 4. 수정할 때 놓치기 쉬운 부분

### 4.1 ‘판단 완료’는 결과의 판과 함께 저장한다

현재 `view()`는 human_reviewed 사건이 한 번이라도 있으면 참이고, `mark_reviewed()`는 두 번째 사건을 남기지 않는다. 합성은 반복할 수 있으므로 의미가 맞지 않는다. **기존 events에 결과 seq/attempt 또는 명시적 generation을 결속**하는 작은 변경이 우선이다. 새 승인 DB는 필요하지 않다.

화면이 본 판과 API가 확인하는 판도 맞춘다. 오래된 화면에서 ‘판단 완료’를 눌렀는데 그 사이 새 합성이 끝났다면, 새 결과를 확인했다고 기록하지 않아야 한다. 새 결과 뒤에는 재확인이 가능해야 하며 같은 판의 중복 확인은 멱등이어야 한다.

실행 종료, 합성 형식 실패, 사람의 확인을 구분한다. 종료가 확인된 형식 실패를 사람이 확인해도 실패 기록을 지우거나 품질 통과로 바꾸지 않는다. 과거 unknown 시도가 남아 있으면 최신 결과가 좋아도 종료 확인 의무와 슬롯을 유지한다.

### 4.2 N3는 마지막 else 한 줄 문제가 아니다

`task_projection(tasks, runs)`에는 controller의 `paused`가 들어가지 않는다. 먼저 **자동으로 진행할 수 있는 알려진 상태**를 명시하고, 그 밖의 상태는 확인 필요로 표시한다. paused인 queued와 실제 실행 중인 시도는 같은 것으로 취급하지 않는다. 수동 입력·축소 승인·unknown의 행동 우선순위도 유지한다.

옛 `runStatus`가 남아 있다는 것만으로 삭제하지 않는다. 작업 목록과 실행 상세가 각각 다른 정보를 표현할 수 있다. 지속 상태와 행동 가능성의 판단은 서버의 공개 투영 한 곳을 따르게 하고, 화면에는 표현만 남기는 것이 목표다.

### 4.3 N1은 좁은 예방 방어이지 완전한 문맥 격리가 아니다

현재 `codex_global_instructions`는 빈 AGENTS 일반 파일을 건너뛴다. **상수 목록에 hooks.json만 추가하면 빈 hooks.json도 허용**되어 N1의 ‘크기 0도 거절’ 조건과 충돌한다. 지시문과 훅 파일의 존재 규칙을 구분하고, 내용·인증 값을 읽거나 출력하지 않는 검사를 제안한다.

공식 문서에는 hooks.json 외 inline 설정·프로젝트·플러그인·managed 훅 층도 있다. 이 문서만으로 현재 관측된 CLI 판의 실제 동작을 확정할 수 없다. 실제 적용 HOME/설정 층을 정하고 합성 HOME의 무모델 대조부터 확인해야 한다. argv가 같아 기존 revision 계산값이 같다는 사실은 새 경계의 검증 완료가 아니다. argv·설정·참여자 표면을 바꾸면 그 계획으로 재관측한다. 출처와 한계는 [EVIDENCE](EVIDENCE.md#공식-문서로-보완한-n1)를 따른다.

### 4.4 폴링 정확성과 속도 개선을 분리한다

#105는 진행 중 요청 가드·시간 제한을 TM 계획의 후보로 두지만, AH-05에는 이미 구체적 정확성 반례가 있다. **응답 역전·시작 성공 후 안내 소실은 먼저**, 전체 이력 크기·중복 SQL 감소는 그다음이다.

진행 중이면 새 요청을 버리는 가드만 넣어서는 mutation 직후 갱신 요구를 잃는다. pending 요청 또는 generation을 함께 관리한다. 실행 상태와 quota 조회 실패를 분리하고, 생성 POST가 성공한 run_id/task_id는 후속 전체 조회의 성공 여부와 무관하게 보존한다. 재조회 오류를 ‘실행 생성 실패’로 보여 다시 시작하게 하지 않는다.

S1–S3은 역할판 A를 다음 실제 기능에 연결하기 전에 우선 처리할 정확성 보완이다. S4는 관측 전에, S5는 launcher 안정화로, S6는 증가 구조를 측정하면서 진행한다. **모든 저우선 후보가 끝날 때까지 B를 무기한 막지는 않는다.** 각 수정은 관련 반례를 먼저 회귀 시험으로 만들고 제품 변경 후 정상 기대값으로 확인한다.

AH-08과 Plan의 얕은 불변성·예약 전 알려진 입력 오류는 B의 계획 경로 변경에 흡수한다. 없는 decision-report의 일관된 오류 응답은 S3의 API 확인에, headless 입력 크기 선검사는 해당 입력 경로 변경에 붙일 수 있다. 공통 설정 helper 이동·호환 재노출 정리는 실제 사용처를 바꿀 때 한다. 이들을 별도 대규모 아키텍처 개편 사유로 만들지 않는다.

## 6. B–E에는 설계 문서가 아니라 필요한 완료 조건을 더한다

[역할판 검토](../2026-09-26-role-board-review/README.md)의 단계 순서와 사용자 요구를 유지한다. 아래는 #102·#103·#105 제안을 현재 주인 모듈에 흡수한 권고다.

| 단계 | 흡수할 조건 |
|---|---|
| B 실제 모델·추론 선택 | (adapter, model, 추론)의 허용 조합, 구독/추가 크레딧 경계, 요청값·보고값·미보고 구분. 재시도·합성을 포함한 실제 경로에 명시 설정. 조용한 대체 없음. Plan 기록/실행 일치, manifest 한 판 검사, 바뀐 계획 즉시 재관측 |
| C 일반 팀원·자료 | 역할이 받은 자료의 이름·내용 해시·크기·종류·범위를 실행에 결속. 원문/지도/AI 요약/기존 답을 구분. 요약만 받은 답을 원문 독립 검토로 표시하지 않음. 비밀 형태 선별은 방어 보강이며 완전 탐지 보증 아님 |

#101에는 이미 입력 확인 manifest·confirmation·task_id·고정 role_config가 있다. 합성에도 인용·초안 해시·unresolved 처분·사실 확인 미실시 표기가 있다([기존 비교 4절](../2026-09-26-codex-peek-comparison/README.md)). 따라서 TaskSpec·receipt·disposition을 모두 새로 만들기 전에 **없는 의미와 수명만** 채운다.

## 7. 기억·검토 절차·벤치를 어떻게 받아들일까

**기억에 관한 두 입장은 충돌하지 않는다.** #105의 자동 수칙서·curator 반대와 #102·#103의 ‘사람이 고른 짧은 공통 자료’ 시범은 다른 것이다. 전자는 상시 자동 정책 생성·전역 주입이고 후자는 기존 입력 전달 기능을 쓰는 통제된 효용 실험이다. 자료 제공, 실제 전달, 응답의 인용, 원문 일치, 모델의 실제 이해는 별개의 사실이다.

새 기억 DB 없이 같은 예산의 기억 없음/관련 자료/낡거나 반박된 자료를 비교할 수 있다. 이득과 선택 비용을 확인한 뒤 검색 자동화를 판단한다. 개발 세션의 기억 저장소나 봉인 중 동료 답을 격리 참여자에 연결하지 않는다. 이 문서는 실험 호출을 실행하거나 새 상한을 승인한 기록이 아니다.

**개발 교차검토 N2는 과정 증거를 남기는 것으로 축소한다.** 검토 대상 SHA, 요청/보고된 추론 옵션, 종료와 결과 파일, 실패·중단·미확인을 분리한다. ‘none 또는 미보고니까 모든 검토가 무효’라는 범용 판정은 만들지 않는다. 반대로 높은 추론의 ‘지적 없음’도 정당성 증명이 아니다. 모델별 의미와 실제 읽은 범위·검증 근거를 본다. N4를 구현한다면 CI와 다른 검사 목록이 새로 갈라지지 않아야 한다.

**벤치 비판은 ‘효과가 없다’가 아니라 ‘우리 효과를 확립하지 못했다’로 쓴다.** Warm 결과는 올바른 기억을 주는 통제 조건의 관측이지 자동 기억 획득·우리 작업의 일반 성능 보장이 아니다. 원자료 없이 시나리오 단위로 다시 계산한 구간을 정확한 대체 신뢰구간으로 제시하지 않는다. 두 신뢰구간이 겹친다는 이유만으로 효과가 같다고 결론 내리지도 않는다. 동일 총예산의 강한 단독 모델과 비교하고, 맞던 답을 망친 비율·미해결 보존·지연·사람 검토 비용까지 봐야 한다. 이번에는 모델 벤치를 재실행하지 않았다.

## 8. 가져오지 않을 것과 남겨 둔 사용자 판단

codex-peek 전체 설치, 전역 Stop 훅과 증명 파일, 별도 job/JSON 원장, 격리 참여자의 영속 공유 세션, 자동 Scout·수칙 승격·curator, 유료 API fallback은 이번 해결책에서 제외한다. SQLite/controller를 유지하며 TypeScript 전환·프레임워크 교체·마이크로서비스로 이 문제를 우회하지 않는다. 파일 길이나 시험 개수만으로 구조 건강성을 평가하지 않는다.

#105의 ‘권고가 있는 사용자 판단을 세션이 자동 확정해도 되는가’는 **기존 기술 작업 위임과 구분**한다. NEXT-SESSION 2절 22에 필요한 기술 수정·시험의 위임은 이미 있지만, 미확정 제품 선호를 포괄적으로 확정하거나 이 세션의 병합 권한을 넓힐 근거로 쓰지 않는다. 이번에는 Q4·합성 기본값·카드 보드 채택 등 기존 미확정 상태를 보존한다. 기술 결함을 고칠 수 있는지 매번 같은 질문을 다시 하자는 뜻은 아니다.

## 9. 인계·검증·병합 주의

원래 날짜 리뷰는 고치지 않고 통합 판단과 정정을 이 폴더 및 검토 목록에 연결한다. 진행 중 체크포인트도 원격 커밋으로 보존했다. NEXT-SESSION에는 다음 순서의 링크만 두고 상세 지적을 복제하지 않는다.

원래 쌓임은 #101→#102→#103→#104→이번 통합이다. #105는 별도 가지이므로 사용자 또는 권한 있는 세션이 병합할 때 검토 목록의 두 항목과 NEXT-SESSION의 사용자 미확정 상태·새 순서를 함께 보존해야 한다. ‘충돌 없는 파일’이 곧 내용상 인계가 맞다는 뜻은 아니다. **선행 PR이 열린 동안 이번 PR의 main diff를 문서 전용 변경으로 보고 통째 병합하지 않는다.** 각 원본 PR과 고유 diff를 따로 검토한다.

직접 수행한 범위는 GitHub의 고정 소스·리뷰 대조와 문서 작성이다. 기존 리뷰의 대역 재현·성능 측정은 전달 근거로 사용했으며 이번 실행으로 세지 않는다. 로컬 전체 suite·실제 브라우저·사용자 WSL·CLI·계정·모델 품질은 검증하지 않았다. 최종 head와 그 head에 연결된 CI 결과는 이 PR 본문에 기록한다. **CI 성공, 반례 재현 성공, 결함 수정 완료는 서로 다른 주장이다.**
