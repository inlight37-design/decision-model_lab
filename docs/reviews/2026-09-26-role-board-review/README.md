# 역할판·홈·일반 오케스트레이션 검토

2026-09-26 · ChatGPT · [PR #98](https://github.com/inlight37-design/decision-model_lab/pull/98)

**판정: 1부의 사용자 구상은 그대로 유지하고, 2부를 보완해 작은 단위로 구현하는 것을 권한다.** 역할판 자체나 일반 오케스트레이션을 포기할 이유는 없다. 그러나 추론 옵션을 일괄 같은 실행 판으로 승인하는 것, 공통 AI 요약을 원문 독립 검토처럼 표시하는 것, 기존 provider 설정을 역할 카드와 동일시하는 것은 지금 제안대로 구현하면 안 된다. 캐시 최적화보다 먼저 작업 범위·자료 전달·산출물 재사용을 정리하는 편이 작고 검증하기 쉽다.

이 판정은 **설계 검토 의견이지 사용자 확정이나 구현 완료 선언이 아니다.** 아래 ‘높음’은 새 설계를 실제 실행에 연결하기 전 해결할 항목이라는 뜻이며, 아직 없는 기능을 현재 앱의 재현된 버그라고 부르는 것이 아니다.

## 0. 범위·증거·접근 한계

[요청서](../2026-09-26-role-board-request/README.md) 전체를 읽었다. **W1–W10은 전제**이고 P1–P10·G1–G8을 검토한다. 요청서가 가리킨 이전 기준은 `a4d9a26`이고 이번 직접 대조 기준은 요청서가 main에 들어온 `9526bbe382b68c74bd7d784c09af3e02f55393ca`다. 시작 시 열린 PR은 없고 원격 브랜치는 main만 확인했다. 자기 브랜치 `chatgpt/role-board-review-20260926`에서 작업했으며 main 병합은 하지 않는다.

접근 범위는 GitHub 연결 도구와 공개 웹 자료다. 사용자 PC·WSL·설치 CLI·로그인에는 접근하지 않았고, 웹 컨테이너의 git clone은 DNS 오류로 실패했다. **앱 코드·관측 허가·모델 설정 변경 및 모델 CLI 호출은 없다.** 저장소의 실행 기록을 직접 읽은 것과 그 실행을 재현한 것은 다르다. 논문 수치는 저자 보고이며 이번 검토가 재현한 절감률이 아니다.

근거의 정확한 위치·원문 링크·읽은 수준은 [EVIDENCE.md](EVIDENCE.md)에 있다. C는 기준 코드·기록, O는 공식 문서, R은 논문이다. ‘전문 해당 절 직접’은 초록만 본 것과 구별하지만 논문의 모든 증명·부록·코드까지 검증했다는 뜻은 아니다. 날짜가 붙은 원본 요청서는 보존한다.

## 3. 우선 수정할 설계 항목

### RB-01 — 추론 강도의 일괄 정규화는 아직 승인할 수 없다 [높음]

**연결: W1·W4·W10 / P4·P10 / G1·G3·G4 / 질문 3·4·8.**

코드에서 `--model` 값을 가리는 사실과 Claude·Codex effort 미연결은 확인했다(C1·C2). 하지만 ‘추론이라는 이름의 옵션이므로 권한·문맥·하위 실행이 모두 같다’는 일반화는 성립하지 않는다. 공식 Claude 문서에는 `ultracode`가 내부 작업 분배도 켜는 값이며, 지원하지 않는 값이나 조직 상한으로 요청 강도가 낮춰질 수 있다고 적혀 있다(O5). 요청서에 열거된 low–max와 이 설정을 같은 부류로 취급해서는 안 된다.

최소 수정은 **현재 모델·CLI에서 지원을 확인한 유한한 강도만 허용**하고, 임의 문자열·추가 옵션·특수 workflow 값은 거절하는 것이다. 첫 실제 구현에서는 선택한 강도를 argv와 계획 기록에 남기고 바뀐 판으로 관측한다. 만료일인 2026-10-26까지 기다렸다가 바꾸는 것이 아니라 **판이나 CLI 버전이 바뀌는 시점에** 기존 기록의 적용 여부를 판단한다.

나중에 low/high 등의 값이 관측 계약상 동등함을 입증하면 그 값 부분만 정규화할 수 있다. 단순히 해시에서 없애기 전에 허용 집합·모델별 지원·실행 경계·실제 적용/하향 적용·오류 처리·timeout을 시험하고, 관측이 뒷받침하는 조합을 기록해야 한다. 매번 모든 강도를 무조건 처음부터 실험하자는 뜻도 아니다. 지금 스키마에서 그 범위를 표현·검증하는 비용까지 비교하면 첫 단계는 좁게 시작하는 편이 낫다.

Codex 공식 `model_reasoning_effort`와 `model/list`의 지원 강도 메타데이터는 조사할 경로가 있다(O1·O2). **기록된 도움말에 독립 플래그가 없다는 것은 기능 부재의 증거가 아니다.** 다만 공식 웹 문서가 있다는 것만으로 aux-pc-wsl의 실제 반환값·안전 계획을 관측했다고 처리하지 않는다. 실행 화면은 ‘요청 high / 적용 미보고’처럼 구별하고, 같은 이름의 high가 회사 간 같은 계산량이라는 척도도 만들지 않는다.

### RB-02 — 공통 AI 요약을 받은 독립 답변의 의미를 분리해야 한다 [높음]

**연결: W4·W6·W9·W10 / P3·P6·P8-A / G3·G6·G8 / 질문 3·6.**

P8-A는 큰 자료의 반복 읽기를 줄일 수 있는 후보지만, 요약자가 빠뜨린 조건·잘못 정한 쟁점이 모든 답에 퍼질 수 있다. 다른 답을 보지 않았다는 실행 격리와 원자료를 각각 조사했다는 증거 독립성은 별개다. 원문 링크를 같이 넣어도 실제로 확인하지 않았다면 이 차이는 없어지지 않는다.

**보고서의 작은 각주만으로는 부족하다.** 실행을 고정할 때 입력을 ‘원문/기계적 지도/발췌/AI 요약/기존 답·평가’로 구별하고 작성자·원본 위치·판을 남겨야 한다. 기존 답이나 상위 모델의 결론을 넘긴 경우에는 후속 검토로 분류해 기존 strict 초안 정족수로 승격하지 않는다. AI 요약만 제공한 경우에는 적격 격리 참여자 수를 기술적으로 셀 수 있어도, 이를 ‘원자료 독립 검토 완료’로 노출하면 안 된다.

최소판에서는 **AI 요약이 들어간 조합을 별도의 입력 조건/후속 단계로 명시하고, 현재의 무조건적인 독립 성공 라벨과 성공 집계 경로를 재사용하지 않는 편**을 권한다. 더 정교한 판에서는 ‘답안 비공유가 확인된 수’와 ‘원자료 확인 상태’를 따로 투영한다. 공유 자료라는 이유만으로 모든 격리 답을 자동 탈락시키거나, 같은 provider라며 임의로 0.5명씩 세는 새 규칙은 제안하지 않는다.

첫 단계의 기본은 **기계적으로 만든 목차·파일 지도 + 변경 불가 원문 + 정확한 위치 참조**다. 요약은 명시적으로 켜는 보조 자료로 둔다. 요약자가 보았던 팀 대화·개인 기억까지 붙이지 않는다. 요약으로 1 MiB 입력의 시간 초과가 줄어드는지도 실측할 가설이지 이번에 확인된 성과가 아니다.

### RB-03 — 봉인은 결과 탭이 아니라 모든 투영·수신 경로의 규칙이다 [높음]

**연결: W4·W7·W8·W9·W10 / P2·P5·P6·P8 / G1·G5·G8 / 질문 3·6·9.**

P6의 ‘격리 칸은 공개 뒤 다시 보기’는 맞다. 그러나 새 홈·문서함·검색·다운로드·Windows 내보내기·알림·상위 모델 입력이 원장이나 파일을 직접 읽으면 기존 결과 탭을 가려도 초안이 드러난다. 현재 controller가 Claude 계정 한도까지 봉인 상태에 맞춰 내보내는 이유와 같다(C4 및 controller의 `claude_account_limit`).

새 화면은 기존 공개 가능 데이터의 **서버 측 허용 목록 투영**을 사용해야 한다. 일반 팀원에게도 문서함 전체를 마운트하지 말고 그 단계에 승인된 자료만 읽기 전용 사본으로 준다. 실시간 일반 작업 화면·공유 계정 게이지가 동시에 진행 중인 격리 답의 길이·진행 시간을 간접 노출하는지도 봐야 한다. 첫 단계에 다중 작업 실행까지 동시에 넣지 않는 것이 이 위험과 구현량을 줄인다.

자료를 편집하면 새 문서 판을 만들고, 이미 시작한 실행의 사본은 바꾸지 않는다. 봉인 중인 답을 읽은 세션이나 fork를 새 독립 참여자로 재사용하지 않는다. namespace·구독 메시지 종류·문서함 탭은 보안 경계 그 자체가 아니다.

### RB-04 — 역할 인스턴스와 provider 계정은 다른 단위다 [높음]

**연결: W1·W2·W3·W4·W5 / P2·P4·P5·P10 / G1·G4 / 질문 1·3·8.**

현재 `Provider`에는 모델 하나가 들어가고 설정은 서로 다른 provider만 받는다(C3). 이는 ‘같은 회사의 다른 모델을 슈퍼바이저·팀원에 각각 둔다’는 역할판과 다르다. UI만 바꾸면 선택이 실행에 반영되지 않거나 한 역할을 바꿀 때 다른 역할까지 덮어쓸 수 있다.

**역할마다 `assignment_id`와 요청 모델·강도·권한·입력 조건을 고정하고, 예산은 기존 provider/계정 단위로 합산**하는 것이 필요한 최소 분리다. 모델 카드 한 개를 복제해도 provider 한도가 복제되면 안 된다. 동일 provider·모델의 두 격리 시도가 가능해지는지는 별도 구현·관측 항목이며, 프로세스상 비공유와 모델 다양성을 서로 다른 표시로 둔다. 새 계층형 agent 프레임워크는 필요 없다.

첫 실제 단계가 현재의 provider별 한 모델만 지원해도 괜찮지만 그 제한을 보여야 한다. 이것을 역할별 모델 선택 전체의 완료라고 표시하지 않는다. 지원 불가 모델·계정 소진은 명시적으로 막되, 오래된 게이지나 미조회 상태를 ‘확실히 소진’으로 단정하지 않는다. 실행 허가 없음은 실행 불가이고, **허가된 C3 미확인 예외**만 보조 참여로 받는 현재 구분도 유지한다. 어느 경우든 다른 모델로 조용히 대체하지 않는다.

### RB-05 — 모든 AI 역할은 같은 예약·취소·복구 관문을 지나야 한다 [높음]

**연결: W3·W5·W10 / P1·P2·P5·P9 / G1·G3·G6·G8 / 질문 2·3·8.**

controller를 자리에서 뺀 P1에 동의한다. 슈퍼바이저나 오케스트레이터에게 프로세스 시작·예산 증가·공개·원장 편집 도구를 직접 주지 않는다. 모델은 **다음 행동의 제안 데이터**를 내고, 프로그램이 고정된 허가·예산·상태를 검사해 기존 실행 경로로 보낸다. 사람이 낸 같은 행동도 같은 관문을 거친다.

모델이 만든 계획·요약·취합·재시도·교차검토를 모두 같은 상한에 예약해야 한다. 승인 버튼을 두 번 누르거나 재시작해도 동일 행동을 두 번 실행하지 않도록 작업/실행/시도와 승인을 연결한다. 종료 미확인 상태에서는 다음 호출로 넘어가지 않는다. 상위 모델이 다음 실행을 제안했다는 이유로 새 원장을 계속 만들어 상한을 우회하지 않게 해야 한다.

현재 원장이 세는 것은 controller가 예약하는 CLI 시작 단위다. native 하네스가 내부적으로 몇 번 추론·subagent 호출을 했는지까지 같은 숫자라고 주장하면 안 된다. 내부 fan-out을 통제·관측할 수 없는 기능은 초기 프로필에서 빼거나 제한을 명시한다. SupervisorAgent의 무모델 필터도 **개입 모델 호출 전체가 공짜**라는 뜻은 아니다(R의 해당 행).

### RB-06 — 빈 상위 칸은 ‘숨은 자동 판단’이 아니라 구체적인 사람의 차례다 [중간]

**연결: W2·W3·W5·W7 / P1·P2·P3·P6 / G5·G8 / 질문 1·2.**

역할의 산출물을 다음처럼 좁히면 중복이 줄어든다. 슈퍼바이저는 목표·완료 조건·팀 변경·다음 실행 필요 여부를 제안한다. 오케스트레이터는 승인된 실행 안에서 작업 분담·자료 수신자·결과 취합을 맡는다. controller는 의미 판단 없이 허가된 전이를 수행한다.

슈퍼바이저만 AI이고 오케스트레이터가 사람인 조합도 지원해야 한다. 이때 AI가 던진 모호한 계획만 보이는 것이 아니라 ‘담당/자료 확인 후 시작’, ‘공개된 답을 직접 정리’, ‘추가 실행 여부 선택’처럼 완료 가능한 행동을 표시한다. 반대로 상위 칸이 모두 비어 있어도 고정된 작업 양식과 사용자의 명시적인 분담으로 일반 팀원을 실행할 수 있어야 한다.

상위 역할 모델을 반드시 서로 다른 모델로 강제하거나 싼 모델로 고정할 필요는 없다. 같은 모델을 두 역할에 쓰더라도 제안 권한·입력·예산 기록은 분리한다. 처음에는 둘 다 사람이 맡는 흐름으로 검증하고 모델은 선택적으로 연결한다.

### RB-07 — P7은 앞부분 캐시보다 ‘읽을 필요 자체’를 먼저 줄인다 [중간]

| 먼저 | 담당·완료 조건·필수 공통 조건을 명확히 나눔(P7-2·5·7) | 모든 작업자가 전체 저장소를 다시 조사하지 않게 함. 다만 사용자가 정한 팀·필수 검토를 자동으로 축소하지 않음 |

### RB-08 — 캐시 기록의 사실과 포함 한도 절감은 분리한다 [중간]

**연결: W1·W6·W10 / P4·P7 / G1·G2·G3·G4·G8 / 질문 4·5·7.**

G1에서 작업 폴더가 실행/참여자별로 다른 것은 맞다. **실제 CLI HOME이 그 옆 `-home`이라는 설명은 틀리다.** 실제 `CliExecutor`는 `self.home`을 상자의 HOME으로 사용하며 그 경로에 빈 HOME과 허용된 연결을 구성한다(C4). 따라서 cache miss 가설의 원인을 설명할 때 모의 실행의 경로를 실제 실행에 적용하면 안 된다.

G2의 strict·L1 수치는 기록과 맞는다(C6). 다만 토큰 합계만으로 ‘이 부분이 CLI 기본 앞머리이며 우리 질문·자료는 전부 새로 계산됐다’고 확정할 수 없다. 캐시가 반복된 위치나 내용을 직접 보여주는 기록이 아니기 때문이다. ‘기본 prefix 재사용일 가능성’으로 낮추고 자료만 바꾼 대조로 확인해야 한다. `reasoning_output_tokens=0`만으로 실제 추론 설정이 `none`이었다고 판정하는 것도 피한다.

토큰 필드도 회사별로 구분한다. 해당 strict 기록에서 Codex의 비캐시 입력은 **12524−9984=2540**이다. Claude는 새 입력 2·캐시 생성 753·캐시 읽기 5728을 따로 보고하므로 총 입력을 비교할 때는 **6483**, 새 처리/생성 합은 **755**다. 이 계산은 그 필드의 해석이며 청구액이나 구독 소진량의 공식이 아니다. 출력·추론 사용량도 따로 남긴다.

공식 Codex 가격 문서는 **크레딧 가격만으로 구독 포함 사용량이 결정되지 않는다**고 명시한다(O3). Claude Code 문서도 API 상당 비용과 구독 사용량을 구분한다. 따라서 양쪽 모두 ‘캐시 읽기 가격이 1/10이므로 구독에서 열 배 더 쓸 수 있다’는 약속은 하지 않는다. 이번 확인에서는 두 구독의 캐시 가중치를 재현 가능하게 계산하는 공개 계약을 확보하지 못했다.

실험은 같은 과제·같은 모델·도구·완료 기준에서 단일 기준선과 역할 분담을 비교한다. uncached/cache-write/cache-read/output, 전체 완료 시간, 실패·재시도, 사람 수정량, 반례 보존을 함께 기록한다. 계정 사용률은 다른 세션·집계 지연·반올림 때문에 보조 관측으로만 쓴다. 봉인 중 표시 정책을 풀거나 표시를 위해 모델을 추가 호출하지 않는다. 무작위 pruning은 필요할 때 오프라인 연구 대조군으로만 둔다.

## 6. 작게 시작하는 구현 경로

### RB-10 — P10을 작은 수직 기능 순서로 조정한다 [중간]

**연결: W1–W10 / P3·P4·P6·P9·P10 / G1·G5·G8 / 질문 1·8.**

P10의 위험이 작은 것부터 한다는 취지는 좋다. 다만 모델→추론→격리 역할판을 모두 끝낸 뒤에 홈과 일반 작업이 보이는 순서라면 사용자는 오랫동안 새 구상 대신 설정 UI만 받는다. 다음과 같이 각 단계에서 실제로 쓸 수 있는 흐름을 만든다.

| 단계 | 작게 완성할 사용자 흐름 | 포함하지 않을 것·검증 경계 |
|---|---|---|
| A. 모의 수직 기능 | 홈에서 새 작업 → 네 역할 칸 배치(빈 상위 칸=사람) → 입력·수신 자료 확인 → 기존 모의 실행/결과 → 홈으로 돌아오기. 기존 실제 결과도 작업 안에서 읽기 | 새 실행 엔진·AI supervisor·자동 memory·동시 다중 작업 없음. 미지원 조합은 명시 표시 |
| B. 현재 실제 경로 연결 | 관측된 provider 조합의 모델 선택을 실행 명세·원장까지 연결. 문서함은 기존 자료의 읽기 전용 목록·고정 사본·공개된 산출물부터 | 모델 선택만 가능한 단계와 역할별 자유 배치 전체를 구별. effort는 좁은 지원 집합을 관측한 뒤 연결하며 다른 화면 개발을 막지 않음 |
| C. 일반 전용 흐름 | 사람이 분담한 읽기 전용 작업 → 담당별 자료 → 원본 산출물 저장 → 사람이 취합. 일반 팀원만으로 완료. 기존 runner/예약/취소/원장 재사용 | 새 normal profile은 필요한 전송·권한 관측을 거침. blind 정족수 라벨 사용 안 함. 새 writer·자율 재귀 분해 없음 |
| D. 선택적 상위 모델 | 승인된 역할 제안·분담·취합을 기존 실행 관문으로 연결. 기존 결정/차례의 미완료 상태와 재시작 복구 | 빈 역할 자동 충원·한도 자동 증액·숨은 API 대체 없음. 각 의미 판단 호출을 기록 |
| E. 혼합·최적화 | 공개 뒤 제한 교차검토부터. AI 사전 요약, 같은 내부 경로, fork·장기 기억은 별도 실험 후 | 격리 프로필에 복제·팀 기억 연결 금지. 먼저 W6의 실측 불편이 있는지 확인 |

최소 데이터 확장은 작업을 묶는 `task_id`, 역할 인스턴스 식별자, 실행에 고정되는 역할/입력 조건, 자료의 작성자·판·공개 상태 정도에서 출발한다. 기존 run·attempt·source snapshot·controller·SQLite를 새 프레임워크와 이중으로 관리하지 않는다. 일반 흐름을 만들기 위해 새 큐 서버·벡터 DB·범용 DAG 엔진·TypeScript 이행을 선행 조건으로 만들 필요는 없다.

이 순서는 W5나 W8을 버리는 축소가 아니다. 요구는 유지하고 미지원 상태를 드러내면서 완성 단위를 줄이는 것이다. P9의 ‘일반 작업도 처음에는 읽기 전용’과 ‘한 writer는 나중’에도 동의한다. 읽기 전용 참여자의 문서 산출물은 controller가 응답에서 저장하면 되므로 문서함 전체 쓰기 권한을 줄 필요가 없다.

### RB-11 — W8은 ‘전부의 내부 사고’가 아니라 검증 가능한 실행 증거로 충족한다 [중간]

**연결: W4·W7·W8·W9 / P6·P9·P10 / G1·G3·G5 / 질문 1·3·9.**

| 시점·종류 | 보여 줄 것 |
|---|---|
| 시작 전, 모두 | 프로그램이 실제 전달할 목표·제약·공통 자료/담당별 자료·모델/강도 요청·역할·상한. 실행에 사용한 판을 고정 |
| 격리 실행 중 | 기존에 허용한 대기/실행/완료 같은 거친 상태. 초안 내용·길이·토큰·소요 시간·모델 보고·읽은 파일 목록을 우회 노출하지 않음 |
| 격리 공개 뒤 | 실제 전달 입력, 반환된 답, 기록·검사한 도구 이벤트/자료 참조·시간·사용량·종료 상태. 수집하지 않았거나 가린 부분은 미관측으로 표시 |
| 일반 실행 중/뒤 | 허용된 입력과 단계 진행·공개 가능한 도구/산출물. 동시에 봉인된 다른 실행의 데이터는 섞지 않음 |

현재 결과 구조의 도구 이벤트 수가 곧 ‘어느 파일을 언제 읽었는지’의 완전한 이력은 아니다. 원시 CLI 스트림을 저장·공개하면 비밀 값·사용자 경로·허용하지 않은 자료가 섞일 수 있으므로 필요한 공개 사건만 수집한다. 앱이 넣은 입력은 그대로 보여 줄 수 있어도 하네스 내부의 숨은 system prompt·내부 추론 전부를 복원했다고 주장하지 않는다.

따라서 공개 뒤 재생은 **격리 요구와 양립하는 W8의 핵심 해법**이지만, 일반 칸까지 아무 진행도 안 보여 주거나 ‘로그 없음’을 ‘아무 도구도 안 씀’으로 표시하면 부족하다. 완성된 모의 흐름에서 실제 사용자가 입력·자료 수신자·결과 이동을 이해할 수 있는지는 화면 사용성 검토로 확인할 항목이다.

## 8. 다음 구현자가 바로 할 일과 아직 열린 선택

**바로 할 일은 A 단계의 홈→작업→역할판→기존 결과 모의 흐름과 위 입력/공개 계약을 함께 만드는 것**을 권한다. 그다음 B의 실제 모델 선택 연결, C의 사람 주도 일반 전용 흐름으로 간다. 캐시 경로 통일이나 새로운 framework 도입부터 시작하지 않는다.

사용자가 아직 정하지 않은 상위 모델 자동 실행 범위, 동일 모델 중복 격리, Windows 내보내기 위치, 요약 입력 선택은 이번 리뷰가 대신 확정하지 않는다. 기본안은 상위 모델 끔·기존 지원 조합·앱 안에서 읽기·원문 우선이다. 기존 ‘필요한 작업은 승인’ 위임을 취소하거나 매번 설정 변경마다 다시 허락을 묻자는 뜻은 아니며, 자동 제품 동작의 범위를 새로 정하는 문제다.

실행 재관측은 해당 PC의 담당 세션이 새 계획·provider별 상한·멈춤 조건을 고정한 뒤 수행해야 한다. 이번 PR의 CI는 문서 무결성·기존 오프라인 회귀 검사의 결과일 뿐, 이 제안의 실제 CLI 적용이나 구독 절감을 증명하지 않는다. 확인한 최종 head와 CI 상태는 PR 본문에 남긴다.
