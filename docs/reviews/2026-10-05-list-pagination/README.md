## 통합과 선택

조회 #169 → 기억 #171 → 흐름 #173을 merge commit 방식으로 순차 통합했다. 앞 PR과 같은 head에서 새 draft PR을 열었다가 취소된 CI가 필수 검사 상태를 가려 병합이 처음 거절됐다. 취소된 검사들을 재실행해 정상화하고 보호 규칙을 유지했다. 최종 main의 [CI](https://github.com/inlight37-design/decision-model_lab/actions/runs/37256637131)는 Linux/Windows 통과, 트리는 #173의 검증한 head와 동일했다.

화면의 작업·타임라인·내 차례에 cursor 페이지를 붙였다. 시각과 ID로 순서를 고정하므로 같은 시각의 기록을 구별한다. 직접 링크는 선택 작업/실행을 별도로 가져온다. 계획의 선행 선택은 제한된 제목 검색을 사용하고 다른 검색 결과로 이동해도 선택을 유지한다. 명령·기존 overview/state/report 형식은 유지한다.

전역 완료·선행 상태를 페이지에 보이는 실행만으로 계산하면 오래된 미확정 호출이 숨는다. 그래서 기존 전체 공개 projection을 사용하고, 변경 없는 polling에만 프로세스 내 집계를 재사용한다. 원장 쓰기/외부 commit, pause/상한/합성 worker 소유권/잔류 입출력이 달라지면 무효화한다. 거래 중 조회는 저장하지 않고, 실제 명령은 항상 기존 fresh 관문을 쓴다. 최초/변경 후 조회는 선형이며 별도 상태 DB나 incremental materialized view는 도입하지 않았다.

## 측정

`python tools/benchmark_queries.py --runs 100 1000 --repeats 3`은 [작업이 많은 원장](many-tasks.json), `--runs 1000 --runs-per-task 1000 --repeats 3`은 [한 작업의 긴 이력](long-timeline.json)이다. 임시 합성 수동 답·자료만 사용하며 CLI를 실행하지 않는다.

집계 캐시의 첫 비용/보관 메모리는 이력에 비례한다. 위 값은 페이지 API 응답의 직렬화를 포함한 이 컨테이너의 합성 수치다. 실제 대형 계획·공개 전/후 상위 역할·다듬기/분담 본문 분포, 여러 클라이언트, 사용자 PC는 대표하지 않는다. 연결 전 planning 이력과 선택 상세의 본문은 이번 페이지화 대상이 아니다. 전체 본문 검색의 선형 비용도 남아 있다.

## 검증과 제한

동시각 cursor·새 삽입·페이지 밖 직접 링크, 모든 내 차례 순회, 페이지 밖 선행 차단, 봉인 비노출, 쓰기/외부 commit/rollback/메모리상의 상태 변경에 따른 캐시 무효화, 호출자가 반환값을 고쳐도 다음 조회가 변하지 않는 것을 확인했다. HTTP parameter 검증과 실제 JS의 늦은 페이지 응답/작업 이동도 검사했다.

Chromium에서 작업/수신함/타임라인 다음·이전, 목록 밖 실행 열기, 제목 검색으로 선행 선택 후 다른 검색/저장, 모바일 가로 넘침을 확인했다. page error는 없었다. 공개 전 초안·원장 원문·사용자 계정 정보는 기록에 옮기지 않았다.

로컬 전체 suite는 기존 클라우드 runner 자손 회수 `test_children_left_behind_are_counted_and_ended`의 `unknown != exited` 실패와 OS/환경 skip이 남았다. 새 회귀는 통과했고 기존 실패를 바꾸거나 skip 처리하지 않았다. 최종 PR CI는 최신 head의 Checks를 기준으로 한다. 사용자 PC 재관측·실제 모델 품질·별도 AI 교차검토는 하지 않았다.
