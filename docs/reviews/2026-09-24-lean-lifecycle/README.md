# 간결성·효율·수명 관리 검토와 수정

2026-09-24 · ChatGPT · [PR #19](https://github.com/inlight37-design/decision-model_lab/pull/19)

기준은 아직 열린 PR #18의 `2e9a74731770b59f2c57f154abe28a9d84654154`다. 사용자 요청은 “최소 코드·최대 효율인지, 아키텍처가 비대하거나 누더기인지 검토하고 남은 문제도 해결”이었다. 접근 범위는 GitHub와 격리된 Linux 분석 컨테이너다. 사용자 PC/WSL·실제 로그인 CLI·계정 한도에는 접근하지 않았으며 실제 모델 호출은 0회다.

## 1. 판단과 실제 규모

**기본 구조가 과도하게 비대해졌다는 근거는 없지만, 최소 코드·최대 효율을 달성했다고 단정할 수도 없다.** 단일 Python 프로세스, SQLite journal, 빌드 없는 HTML/JS, 실행기 인터페이스와 OS 실행 경계가 현재 제품이다. 실행 경로에 ORM·메시지 브로커·플러그인 프레임워크·다중 서비스가 없다. 연구 문서/과거 관측의 양을 제품 런타임 복잡도와 혼동하면 안 된다.

반면 실제 낭비는 있었다. 화면이 마지막 사건 이름만 보여 주면서 사건 전체 payload를 매번 읽고 JSON으로 풀었다. 보고서 한 개를 만들 때도 모든 실행을 투영했다. 완료한 스레드 참조가 계속 남았고, 하위 runner에는 취소가 있는데 controller의 영속 상태와 연결돼 있지 않았다. 이 부분을 기존 구조 안에서 고쳤다.

| 측정 항목 | 기준 코드 | 이번 수정 코드 |
|---|---:|---:|
| `app/*.py` + `core/*.py` 직접 Python 파일 | 14 | 14 |
| 같은 파일의 물리적 줄 수 | 2,796 | 2,905 |
| 제품의 외부 Python 패키지 import | 없음 | 없음 |
| 새 서비스·실행 엔진·런타임 모듈 | 해당 없음 | 추가 없음 |

물리적 줄 수에는 주석·빈 줄·모의 CLI도 포함한다. 순증 109줄은 취소의 영속 상태·실행기 연결·자원 상한에 쓰였다. **기능을 추가했는데 줄 수까지 줄었다고 주장하지 않는다.** 시험/연구용 도구와 브라우저 검증의 선택 의존성은 제품 런타임과 분리한다. 정확한 원자료는 [measurements.json](measurements.json), 재측정은 [audit.py](audit.py)다. 측정의 수정 코드 commit은 `32c1e2a4402037d9b065d72eb12d629fe542f584`다.

의존 방향은 `server → controller → store`, 실행 시 `executor → isolation → runner`와 adapter 판정이다. `report`는 공개 투영만 읽는 순수 변환이다. 정적 import에서 `core → app` 역방향이나 제품 모듈 사이 순환을 찾지 못했다. controller의 상태 권위를 쪼개거나 별도 취소 엔진을 붙이지 않았고, 기존 `Event` 신호를 끝까지 전달한다. `test_app_lean.py`에 stdlib/역방향 의존 회귀를 추가했지만 절대 줄 수 제한은 넣지 않았다.

## 2. 발견과 수정

| 문제 | 수정과 확인 |
|---|---|
| 마지막 사건만 보여 주는데 전체 payload를 조회/해석 | SQL에서 `SELECT kind … ORDER BY seq DESC LIMIT 12`; 화면에는 역순을 다시 뒤집어 원래 순서 보존. 큰 payload가 투영되지 않고 제한된 쿼리만 나가는 시험 |
| 한 보고서를 위해 모든 실행을 투영 | `view(run_id)`를 기존 함수의 선택 인자로 추가. 보고서 경로는 해당 실행만 읽고, 기본 화면의 기존 전체 조회 계약은 유지 |
| 완료한 스레드 참조 누적 | 활성 시도의 `(thread, cancel_event)`만 보관하고 `finally`에서 제거. 합성 실행 반복 후 목록이 비는 시험 |
| 취소가 원장/API/화면과 단절 | 스키마 3에 `cancel_requested` 추가. 같은 거래로 취소 의도·시작 전 취소를 저장하고 COMMIT 뒤 신호. 실패 시 신호를 보내지 않는 rollback 시험 |
| 늦은 정상 답·재시작이 취소 의도를 무시할 가능성 | 취소된 실행의 시작·수동 제출·축소 승인·공개 차단. 늦은 답 배제, 재시작/재개 후 비활성 유지, 이미 봉인한 초안은 비공개 보존 |
| 시작 전/입력 쓰기에서 신호 미확인 | runner에서 Popen 전 확인, writer는 청크 사이 확인. 실제 실행기는 같은 Event를 isolation에 전달. 모의·실제 실행기 인터페이스가 갈라지지 않음 |
| 스레드 시작 실패 시 예약 상태 잔류 | 실행 전 실패로 같은 결과 수용 경로에 전달, 활성 참조 제거. 이미 예약한 예산은 보수적으로 유지하고 확인된 빈 자리는 해제 |
| 잔류 I/O 집계 경쟁 | 잔류 스레드 등록/회수에 같은 잠금 적용. 격리 없는 POSIX 자손 전체의 종료를 새로 보장한다는 뜻은 아님 |
| 인증 전 연결·느린 전송의 자원 점유 | 인증 전 포함 동시 연결 16개, 연결별 I/O 기한 15초, 기존 유휴 5초 유지. 연결/타이머/스레드 시작 실패 때 자리 회수 |

HTTP의 15초는 **소켓 I/O의 기한**이다. Python 계산 전체를 강제로 중단하거나 이미 확정한 상태 변경을 되돌리는 제한이 아니다. CPU·메모리 상한(K10)이나 공용 인터넷 서비스 수준의 서버가 완성됐다고 하지 않는다. 연결을 늘리는 전용 큐·웹 프레임워크는 추가하지 않았다.

## 3. 취소의 정확한 계약

`phase`는 마지막 진행 단계를 보존하고, 원장의 단조로운 `cancel_requested`가 재시작 불가능한 중단 여부를 나타낸다. 기존 membership에 두 번째 전체 상태 기계를 얹지 않는다. API의 200/화면 “취소 요청됨”은 모든 프로세스가 끝났다는 뜻이 아니다.

| 시점/조건 | 처리 |
|---|---|
| 아직 예약하지 않은 CLI·수동 입력 대기 | 시작 전 취소, 새 CLI 시도 예산 없음 |
| 예약/실행한 시도 | 취소 신호 전달. 예약 예산은 환불하지 않음 |
| 자손 전체 종료 확인 | 답을 받지 않고 취소 종료로 기록, 실행 자리 해제 |
| 종료 미확인/실행기 자체 오류 | `unknown` 유지, 자리 유지, 예산 유지. 취소 클릭만으로 종료 확인을 꾸미지 않음 |
| 늦은 정상 답, 중복 취소, 재시작 후 재개 | 초안 수용/공개/재실행 없음; 취소 사건은 한 번 |
| 이미 봉인한 답 | 삭제하지 않고 비공개 유지. 취소한 실행의 보고서도 공개 불가 |
| 이미 공개한 실행 | 취소로 다시 숨기지 않음 |
| 원본 앱의 수동 작업 | 우리 앱의 답 접수만 중단. 실제 원본 앱 중단은 사용자가 따로 수행 |

프로세스 생성 전 검사와 생성 사이에는 OS 호출 경쟁 창이 있고, 이미 진행 중인 한 번의 파이프 쓰기를 Event가 취소 가능한 시스템 호출로 바꾸지는 않는다. 다음 입력 청크는 보내지 않고 기존 프로세스 종료/파이프 정리 경로를 사용한다. 외부 서비스에 이미 맡긴 작업의 종료도 보장 밖이다. 구독 사용량이 취소로 환불됐다고 표시하지 않는다.

스키마 2 → 3 시험은 기존 질문을 유지하며 취소 칸을 기본 false로 만든다. 상향 이전만 지원하므로 이전 코드로 돌아갈 가능성이 있으면 먼저 journal을 백업한다. 이 변경은 실제 CLI 호출 승인이나 기기 관측 갱신이 아니다.

## 4. 효율 측정과 검증

**합성 SQLite 조회만 측정:** 실행 하나에 사건 3,000개, 각 `detail`에 ASCII 2,048바이트, 워밍업 뒤 20회. 이 컨테이너의 `Controller.view()` 중앙값은 **18.141 ms → 0.0528 ms**였다. 이전 코드는 전체 사건 JSON을 매번 풀고 마지막 이름만 남겼으며 수정 코드는 DB에서 이름을 제한해 가져온다. 네트워크, 모델 응답, 전체 UI 시간, 최대 메모리를 측정한 결과가 아니므로 “앱 전체가 몇백 배 빨라졌다”고 일반화하지 않는다.

- 로컬 전체 시험: **347건, 실패/오류 없음, 환경 의존 18건 skip**. 비-root Linux/Python 3.13.5에서 실행. baseline은 325건/18 skip이고 신규 회귀는 22건이다. skip을 통과에 합치지 않는다.
- 신규 회귀: `test_app_cancel.py`, `test_runner_cancel.py`, `test_server_limits.py`, `test_app_lean.py`. 실제 소켓 인증/취소, 느린 전송 기한, 시작 실패 후 자리 회수, 거래 rollback, 늦은 답·재시작·봉인·예산을 각각 확인한다. 실제 모델은 쓰지 않는다.
- Chromium 144의 오프라인 DOM: 기존 보고서 원문/한글/다운로드/스크립트 문자열의 텍스트 처리 회귀를 그대로 재실행. 새 [browser_cancel.py](browser_cancel.py)는 390px 화면의 취소 버튼·확인 뒤 상태·제출/축소/보고 차단과 가로 넘침 없음 확인. page error 없음.
- 오프라인 DOM은 네트워크를 막고 fetch/auth bootstrap을 fixture로 바꾼다. 실제 HTTP 소켓 시험과 합쳐서 브라우저부터 서버까지 종단 간 시험에 성공했다고 하지 않는다. 사용자 PC/WSL, Windows job object 실기기, 실제 로그인 CLI, 장시간 운용, 접근성/교차 브라우저는 미검증이다.
- 깨끗한 코드 checkpoint `7390530cfcd8f78b7b5e86c64c712ccddbe63c73`의 [CI 실행](https://github.com/inlight37-design/decision-model_lab/actions/runs/35953859289)은 성공했다. 문서까지 포함한 **최종 head의 Python 3.12/3.13 결과는 PR #19의 Checks와 본문**을 기준으로 다시 확인한다. Linux 격리 통합은 로컬 skip과 구분해 CI의 `DML_REQUIRE_BWRAP=1` 결과로 본다.

## 5. 저장·인계·남은 순서

제품 수정은 `32c1e2a4402037d9b065d72eb12d629fe542f584`, 임시 파일 정리는 `7390530cfcd8f78b7b5e86c64c712ccddbe63c73`에 저장했다. 직접 Git 네트워크가 없어 자기 브랜치에서 추적된 공개 소스만 아카이브해 읽고, 검증한 소스 diff를 SHA256 및 app/core/tests tree 대조 뒤 적용했다. 환경·비밀·사용자 파일은 전송하지 않았다. 임시 workflow/압축 diff/중간 패치는 최종 코드 tree에서 모두 제거했다. 검증한 깨끗한 tree는 `180d8591a9249e32e780eb1c818ee3479cea6dc0`다.

`NEXT-SESSION.md`와 앱 안내의 “취소 없음” 및 연결 상한 부재 설명을 원본에서 고쳤고, 사용자 결정·금지 사항은 그대로 보존했다. 이전 날짜의 리뷰·관측 기록은 고치지 않고 이 기록을 목록에 연결했다. PR #18을 먼저 main에 병합하고 PR #19를 main으로 retarget한 뒤 CI를 다시 확인한다. ChatGPT는 main이나 이전 세션 브랜치를 병합/수정하지 않았다.

다음은 확장을 서두르지 않는 순서다.

1. **기존 controller 위의 모의 합성자·주장 대조·결정 카드:** 하나의 사용자 흐름을 완성하고 반례·미합의·확인 불가를 보존한다. 새 엔진·무제한 합의 루프보다 우선한다.
2. **조회와 사용량 표시:** 기본 `/api/state`는 아직 모든 실행/공개 답을 읽는다. 이력이 커지면 목록 페이지화/선택 실행 상세부터 측정한다. 주기 조회의 중복/오래된 응답(TM 계획 A)은 아직 미채택 후보다. 계정 전체 잔여는 실행별 관측과 구분하고 표시 때문에 모델을 부르지 않는다.
3. **승인과 실제 기기 검증:** K46의 실제 exec 인증 파일 차단, C3 문맥 독립성 판단, K17 실제 서버 연결, B3 비교는 별도 승인·기기 관측이 필요하다. 합성 시험을 근거로 `observed`나 실사용 안전 판정을 올리지 않았다. CPU·메모리/디스크 상한과 장시간 안정성도 별도 과제로 남긴다.

요약하면 **전면 재작성은 하지 않았고, 필요한 경계를 보존하면서 관측한 낭비를 제거하고 빠진 수명 관리를 연결했다.** 최대 효율이나 모든 미해결 문제의 완료를 선언하는 대신, 다음 변경도 재현되는 비용·결함과 하나의 사용자 흐름을 기준으로 제한한다.
