## 2부 — Claude의 제안

모두 제안이다. 사용자 확정이 아니며, 구현하지 않았다.

### P1. 빈 판이 지금의 앱이다

지금도 역할은 있다. 사용자가 슈퍼바이저 겸 오케스트레이터다 — 질문을 쓰고, 원문 대조표를 읽고, 실제 합성 버튼을 누른다. 참여자가 격리 팀원이고, 합성자가 오케스트레이터 일의 일부를 한다. 그래서 **상위 칸이 모두 빈 역할판 = 지금 앱**으로 두고, 칸에 모델을 놓을수록 사람이 하던 일을 모델이 넘겨받게 한다.

**판 자체는 자리가 아니다.** 호출 상한, 예약, 봉인과 공개, 자손 종료 확인, 원장 기록은 지금처럼 controller(코드)가 맡고 어느 칸에도 넘기지 않는다. v0.4 설계의 "실행 순서·횟수·권한은 일반 코드가 관리"와 작업 방식 검토의 "판단은 AI, 실행 관리는 프로그램"을 그대로 따른다. 모델 슈퍼바이저·오케스트레이터가 부르는 호출도 같은 원장·상한에서 예약한다.

### P2. 칸마다 하는 일

| 칸 | 하는 일 | 비우면(사람이) | 넘지 않는 선 |
|---|---|---|---|
| 슈퍼바이저 | 목표를 받아 질문을 다듬고 팀 구성을 제안한다. 결과를 보고 "한 번 더 / 교차검토 / 여기서 끝"을 정한다 | 지금처럼 사용자가 질문을 쓰고 다음 일을 정한다 | 팀원을 직접 부르지 않고 새 실행을 판에 요청만 한다. 봉인된 답은 공개 전에 못 본다. 사용자 위임을 넓히지 않는다 |
| 오케스트레이터 | 격리 칸이 있으면 공개된 답을 모아 정리한다(지금의 실제 합성). 일반 칸이 있으면 일을 나눠 맡기고 결과를 모은다 | 격리: 모델 없이 코드가 만든 원문 대조표를 사용자가 읽는다. 일반: 사용자가 일을 나눈다 | 공개 전 답을 못 본다. 호출 수를 늘리지 못한다 |
| 팀원(격리) | 같은 질문에 서로 못 보고 답한다. 독립 정족수에 센다 | 비울 수 없다(격리 모드면 최소 1) | 개인 메모리·다른 답·작업 기억을 받지 않는다. 읽기 전용 |
| 팀원(일반) | 오케스트레이터가 나눠 준 일을 한다. 문서함으로 자료와 결과를 공유한다 | 비울 수 있다 | 독립 정족수에 세지 않는다. 처음에는 읽기 전용(조사·검토), 파일을 고치는 팀원은 나중에 한 명만 |

슈퍼바이저 칸이 모델이고 오케스트레이터 칸이 비어 있어도 된다. 빈 칸의 일은 그 차례가 오면 사용자에게 "내 차례"로 넘어온다.

### P3. 칸 조합과 v0.4 실행 모드

| 채운 칸 | 동작 | v0.4 모드 |
|---|---|---|
| 일반 팀원 1명 | 단독 실행 | `single` |
| 일반 팀원 여럿 | 보통 오케스트레이션 — 나눠 맡고 모은다(P7의 절약 규칙) | 새 모드. `build_review`는 구현자·검토자를 둘 때 |
| 격리 팀원 여럿 (+ 오케스트레이터) | 지금 방식. 봉인·공개 뒤 정리 | `cross_check` |
| 격리 → 공개 → 일반 팀원이 검토 | 공개 뒤 교차검토 한 바퀴(P8의 B) | `deliberate` |
| 일반 팀원이 준비 → 격리 팀원이 답 | 큰 자료를 한 번만 읽고 요약을 나눠 준다(P8의 A) | 새 조합 |

### P4. 모델과 추론 강도 고르기

- 카드마다 모델과 추론 강도를 드롭다운으로 고른다.
- **모델 목록:** Codex는 이미 있는 계정 조회(모델 호출 없음)가 받는 `model/list`를 쓴다. Claude는 모델 없이 물을 통로가 없으므로 정한 목록을 두고, 실행 뒤 "실제로 답한 모델" 보고로 맞는지 표시한다(지금 방식).
- **추론 강도:** Claude는 관측한 도움말에 `--effort`가 있다(G1). Codex의 추론 옵션은 우리 기록에 없어 미확인이다 — 쓰기 전에 도움말이나 관측 출력으로 확인한다(인계 5절).
- **재관측이 드는지가 다르다.** 모델 이름은 참여자 계획의 판에서 `<model>`로 가려져 있어 바꿔도 strict 허가가 그대로다. 추론 옵션은 argv에 새 옵션을 더하므로 판이 바뀌고, strict 허가를 다시 받아야 한다. 마침 2026-10-26 전에 재관측이 예정돼 있으니 **추론 옵션을 넣은 계획으로 함께 관측한다.** 강도 값도 모델 이름처럼 판에서 가리면 한 번의 관측으로 모든 강도에 쓸 수 있다 — 강도가 파일·권한·문맥 경계를 바꾸지 않는다는 가정이며, 검토 질문 4다.
- 요청한 강도와 실제 적용을 따로 표시한다. CLI가 보고하지 않으면 "요청: 높음 · 확인 안 됨"이다. 없는 값을 조용히 기본값으로 바꾼 CLI가 있었다(agy, V04-01).
- 강도가 높으면 시간과 사용량이 는다. Claude는 큰 자료에서 이미 180초를 넘긴 적이 있다([1 MiB 결과](../../experiments/2026-09-25-1mib-sources/RESULTS.md)). 카드에 경고하고, 제한 시간도 고를 수 있게 한다.

### P5. 끌어다 놓을 때 판이 막거나 알리는 것

- **원본 앱 카드**는 지금처럼 격리 칸에 들어가 봉인에 참여할 수 있지만 "독립 미확인"으로 표시하고, strict 정책에서는 정족수에 세지 않는다. 일반 칸에도 들어갈 수 있다.
- 이 기기에서 strict 허가가 없는 CLI 계획은 격리 칸에서 "허가 없음"으로 보이고 strict 정족수에 세지 않는다.
- 한도를 다 쓴 모델 카드는 흐리게 보이고 놓을 수 없다. 빈자리를 다른 모델로 채우지 않는다(D18).
- 오케스트레이터가 격리 팀원과 같은 회사 모델이면 경고한다. D 후속에서 Codex 합성이 Codex 초안의 틀린 설명을 주장으로 받은 관측이 한 번 있다([D 후속](../../experiments/2026-09-25-d-followup/RESULTS.md)).
- 같은 모델 두 개를 격리 칸에 넣으면 "같은 모델은 같은 실수를 하기 쉬워 독립이 약하다"고 표시한다. 지금 코드는 provider당 하나만 받는다(G1).
- 놓을 때마다 "이 구성으로 최대 몇 번 부르나"를 계산해 보인다. 슈퍼바이저·오케스트레이터도 같은 상한(원장 하나에 합계 10)에서 쓴다.
- 시작한 실행의 구성은 고정한다(지금 정족수 정책처럼). 바꾸려면 새 실행이다.
- 끌기 대신 "카드 누르고 → 칸 누르기"도 된다(키보드·접근성, 남은 일 K27).

### P6. 홈, 작업 안, 문서함

**홈 = 작업 목록.** "새 작업" → 역할판 → 목표 입력. 작업마다 제목, 팀 구성, 상태(작업 중·내 차례·끝남·문제), 쓴 호출 수. 맨 위에 **"내 차례"** 모음 — 사람이 맡은 칸에 할 일이 생긴 작업(질문 확인, 원본 앱 답 붙여넣기, 공개 뒤 판단).

**작업 안.** 대화처럼 흐르는 타임라인: 목표 → (슈퍼바이저 제안) → 실행 카드 "팀원 3명 작업 중 · 봉인" → 공개 → (정리) → 다음 제안. 한 작업에 실행이 여러 개 이어진다(2절 20의 후보 "새 실행으로 넘기기"가 여기서 생긴다). 실행 카드를 누르면 지금의 결과 화면이다. 팀원마다 **무엇을 받았나**(실제로 보낸 질문 전문·자료 목록·지문)와 **어떻게 일했나**(시작·끝, 읽은 파일, 도구 사용, 시간, 토큰, 종료 확인)를 보인다.

**단, 격리 팀원은 공개 전에 "작업 중 / 끝남"만 보인다.** 지금도 공개 전에는 초안의 내용·길이·토큰·시간을 내보내지 않는다 — 진행을 보면 답을 짐작할 수 있기 때문이고, 격리의 핵심이다. W8의 "어떻게 일하는지"는 공개 뒤 다시 보기로 준다. 일반 팀원은 실시간으로 보여도 된다.

**문서함(작업마다 오른쪽 패널).** 받은 자료, 만든 문서(초안·정리 결과·결정 보고서), 내보내기. 문서마다 "누가 언제 볼 수 있나"를 붙인다. 격리 칸에서는 봉인 규칙이 이 표를 정하고, 일반 칸에서는 오케스트레이터나 사용자가 정하는 **전달 규칙**이 된다(P7의 4).

| 문서 | 격리 팀원 | 일반 팀원 | 오케스트레이터 | 슈퍼바이저·사용자 |
|---|---|---|---|---|
| 공통 자료 | 처음부터(읽기 전용) | 전달 규칙대로 | 처음부터 | 처음부터 |
| 격리 팀원 A의 답 | 못 봄 | 공개 뒤, 교차검토를 켰을 때만 | 공개 뒤 | 공개 뒤 |
| 정리 결과 | 못 봄 | 전달 규칙대로 | 자기가 만듦 | 바로 |

실제 저장 위치는 WSL 안이라 사용자가 직접 볼 수 없다. 앱 안에서 바로 읽게 하고, "저장" 버튼으로 Windows 폴더에 Markdown으로 내보낸다. 답 원문이 들어가므로 GitHub에는 자동으로 올리지 않는다.

**Claude·ChatGPT 프로젝트에서 가져올 것:** 왼쪽 작업 목록, 작업별 파일 모음, 작업별 지침, 오른쪽 문서 패널. **가져오지 않을 것:** 프로젝트 기억을 격리 팀원에게 주는 것. 슈퍼바이저·오케스트레이터·일반 팀원은 작업 기억을 가져도 되지만, 격리 팀원은 매번 고정된 질문과 자료만 받는다.

### P7. 일반 칸의 중복 읽기를 줄이는 규칙

3부의 조사(G3–G6)에서 구독 CLI를 따로 띄우는 우리 구조에서도 되는 것만 골랐다.

1. **공통 머리말을 맨 앞에, 모두에게 글자 그대로 같게.** 규칙·자료 지도·공통 파일 목록을 판이 만든다. 공급자 캐시는 앞부분이 정확히 같을 때만 맞는다(G3).
2. **각자 할 일은 맨 뒤에, 겹치지 않게 구체적으로.** 작업 설명이 모호하면 에이전트가 같은 일을 중복한다(G3, Anthropic).
3. **캐시가 맞을 조건을 맞춘다.** 같은 모델·같은 추론 강도·같은 도구 목록으로 띄운다. Claude는 작업 폴더가 다르면 캐시를 못 나누는데 지금 격리는 참여자마다 폴더가 다르다(G2) → 일반 칸은 상자 안에서 **같은 경로로 보이게** 한다(실측 필요). 첫 팀원을 먼저 띄우고 나머지는 그 응답이 시작된 뒤 띄운다(G3).
4. **결과는 파일로, 넘길 때는 요약과 경로만.** 팀원은 결과를 문서함에 쓰고 오케스트레이터에는 짧은 요약과 경로만 돌려준다. 원문은 필요할 때만 연다(G3).
5. **필요한 사람에게만 보낸다.** 모든 결과를 모두에게 뿌리지 않는다. 역할마다 받을 문서를 정한다(G5 MetaGPT, G6).
6. **공통 지도 한 장.** 자료·코드의 목차 지도를 한 번 만들어 주고 팀원은 필요한 파일만 찾아 읽는다(G5 Aider). 지도는 모델 없이 코드로 만들 수 있다.
7. **기본은 한 명, 필요할 때만 늘린다.** 나눠 읽고 모을 수 있는 일이나 검토가 필요할 때만 팀원을 더한다(G6). 파일을 고치는 팀원은 하나다.
8. **줄었는지 잰다.** 팀원마다 새로 읽은 토큰과 캐시로 읽은 토큰을 보인다. 이미 받는 값이라 모델을 더 부르지 않는다. 캐시로 읽은 양이 구독 사용량에서 덜 깎이는지는 모른다(G3·G4) — 약속하지 않고 잰다. 무엇을 넣든 "팀원 한 명"과 "무작위로 줄이기"를 기준으로 비교한다(G7).

한 번 읽은 세션을 복제해 팀원을 띄우는 방법(fork)은 문서상 캐시를 그대로 이어 쓴다(G3·G4). 다만 지금 참여자는 세션을 남기지 않게 돌리므로(`--no-session-persistence`, `--ephemeral`) 일반 칸에서만 바꿔야 하고 실측 전이다. 나중 후보로 둔다.

### P8. 격리 칸과 일반 칸을 같이 쓰기

- **A. 일반이 준비하고 격리가 답한다.** 일반 팀원 하나가 큰 자료를 먼저 읽고 요약·지도를 문서함에 올린다. 격리 팀원은 그것을 받아 각자 답한다. 1 MiB 자료에서 Claude가 180초를 넘긴 문제가 줄어든다. 대신 요약에서 빠진 것은 격리 팀원이 모두 함께 놓친다 — 읽는 단계의 독립이 사라진다. 보고서에 "자료: 요약본(작성자 ○○)"이라고 남기고, 원문과 요약본 중 무엇을 줄지는 사용자가 실행마다 고른다.
- **B. 격리가 답하고 일반이 검토한다.** 공개 뒤 일반 팀원이 검토한다. 답이 서로 다른 부분만 넘기고, 같은 말을 한 팀원은 검토에서 빼면 낭비가 크게 준다(G6 S2-MAD). 이미 있는 후보 "공개 뒤 교차검토"(2절 20)와 같다. 검토한 팀원은 독립 참여자로 세지 않는다.

### P9. 조심할 점

- 슈퍼바이저가 다듬은 질문은 모든 격리 팀원에게 똑같이 들어간다. 팀원들이 같은 쪽으로 끌려가도 합의처럼 보일 수 있으므로 사용자의 원래 목표와 실제로 보낸 질문을 나란히 보관하고 보인다.
- 역할이 늘면 호출이 빨리 준다(원장 하나에 합계 10). 슈퍼바이저 모델은 기본으로 끈다(2절 20). 상태 확인에는 모델을 부르지 않는다(2절 5).
- 일반 칸의 실행 방식(argv)은 격리 칸과 달라 새 참여자 계획이 된다. 독립 정족수에 세지 않으니 문맥 독립 관측(C3)은 필요 없지만, 권한·전송 관측은 필요하다.
- 화면 부품: island-ui는 ai_unslop에서 복사만 하고 여기서 고치지 않는다([부품 안내](../../../app/static/island-ui/README.md)). 끌어다 놓는 판·카드 같은 새 부품을 ai_unslop에서 먼저 만들지 앱 전용으로 둘지 정해야 한다. 화면이 여러 페이지로 커지면 미뤄 둔 Q3(TypeScript 이행)도 다시 올라온다.
- 앱이 돌리는 결정 작업과 이 저장소를 만드는 개발 작업(카드·PR)은 섞지 않는다(작업 방식 검토의 "서로 섞으면 안 되는 두 공간").

### P10. 만드는 순서

1. **모델 선택** — 재관측 없이 된다. 지금 화면의 체크 카드에 모델 드롭다운만 더한다.
2. **추론 선택** — 2026-10-26 전 재관측에 추론 옵션을 넣어 함께 관측한 뒤.
3. **역할판** — 격리 칸, 오케스트레이터 칸(= 지금의 합성자). 슈퍼바이저 칸은 "나"로 표시해 시작한다.
4. **홈·작업·문서함** — 작업 묶음, 타임라인, 공개 뒤 다시 보기, 내보내기.
5. **일반 칸** — 읽기 전용 조사·검토 팀원, 문서함 공유, P7 규칙, 캐시 측정.
6. **슈퍼바이저 모델** — 제안만, 기본 끔, 사용자가 확인한 뒤 진행.
7. **나중:** P8의 A·B, 파일을 고치는 팀원 한 명, 세션 복제(fork).

1–3은 지금 있는 기능(합성자 선택, 정족수 정책, 원본 앱 참여)을 다시 배치하는 쪽에 가깝다. 새 개념은 4의 "작업", 5의 일반 칸, 6의 슈퍼바이저다.

### G7. 조심할 결과와 못 쓰는 것

- **Rethinking the Evaluation of Efficiency Methods for Multi-Agent Systems**([arXiv:2609.05933](https://arxiv.org/abs/2609.05933), [요약만]): AgentPrune·AgentDropout 등이 "barely beat random pruning"이었다고 봤다. 무엇을 넣든 무작위로 줄이기와 팀원 한 명을 기준으로 재야 한다.
- **Why Do Multi-Agent LLM Systems Fail?**(MAST, [arXiv:2503.13657](https://arxiv.org/abs/2503.13657), [요약만]+README): 여러 에이전트의 이득이 "often minimal". 실패 분류로 쓸 수 있다.
- **못 쓰는 것:** 모델 내부 기억(KV 캐시)을 에이전트끼리 나누는 KVCOMM([arXiv:2510.12872](https://arxiv.org/abs/2510.12872))·DroidSpeak([arXiv:2411.02820](https://arxiv.org/abs/2411.02820))·Cache-to-Cache([arXiv:2510.03215](https://arxiv.org/abs/2510.03215)), 모델을 다시 학습하는 Optima([arXiv:2410.08115](https://arxiv.org/abs/2410.08115)). 구독 CLI로는 모델 내부를 건드릴 수 없다.
