승인은 앱 재시작이나 새 원장 생성으로 새로 생겨서는 안 되고, 이미 사용한 몫도 복원돼야 합니다. 계정 한도가 초기화됐더라도 사용자가 정한 승인 상한까지 자동 초기화되는 것은 아닙니다.

이는 A7의 승인·예산·만료 요구를 실제 실행 규칙으로 구체화한 제안입니다.

3-3. [모순] 부재 모드를 넣는다고 “템플릿에 과거 승인을 옮기지 않는다”는 원칙을 바꿀 필요는 없습니다.

확신도: 높음

A7의 결정 B 설명은 부재 모드를 넣으면 템플릿이 과거 승인을 옮기지 않는 원칙도 바뀐다고 적습니다. 이 부분은 불필요하게 넓은 해석입니다.

템플릿과 승인은 계속 분리할 수 있습니다.

템플릿은 작업 방식과 설정을 재사용합니다.
승인은 특정 범위·기간·상한 안에서 그 작업을 실행할 권한입니다.

저녁에 승인한 작업 묶음에 속한 동작은 그 승인 ID를 참조하면 됩니다. 템플릿을 다음 날 다시 불러왔다고 어제 승인까지 복사할 이유는 없습니다. 이렇게 하면 반복 승인을 줄이면서도 오래된 허락의 재사용을 막을 수 있습니다.

또한 다른 AI가 “사용자가 허락했다”고 보낸 메시지는 승인 기록의 근거가 되어서는 안 됩니다. AI는 승인안을 작성할 수 있지만, 실제 실행 권한은 사용자가 확인한 기록에서 나와야 합니다.

근거: A7 §2 P6·§7 결정 B; A4의 템플릿 설명; A6의 템플릿 복원 규칙.

3. 결정 C: 다른 작업의 상태 읽기
3-4. [조언] 네 결정 중 실제 작업에 가장 빨리 도움이 될 수 있습니다. 처음에는 대화 기록보다 작업 프로그램이 내보내는 작은 상태 파일을 우선하십시오.

확신도: 높음

C가 없으면 앱은 계속 자기 호출만 압니다. GPU 학습·이미지 생성·기존 세션의 상태가 들어와야 실제 운영 도구가 됩니다.

첫 화면에서 꼭 필요한 것은 많지 않습니다.

무엇이 실행 중인지, 무엇이 끝났거나 실패했는지, 무엇이 사용자를 기다리는지, GPU를 누가 쓰고 있는지면 됩니다. 세션 캐시 상태·압축 횟수·CPU 온도·모든 회사의 한도 예측을 한 번에 완성할 필요는 없습니다.

A7은 출처·관측 시각·유효 시각을 붙이고, 수집 실패를 “모름”으로 표시하며, 수집기 하나의 실패가 다른 칸을 막지 않게 제안합니다. 이 설계는 유지할 만합니다.

근거: A7 §3.1–§3.4.

다만 두 가지 구현 함정이 있습니다.

“대화 본문을 읽지 않는다”와 “읽은 뒤 화면에서 숨긴다”는 다릅니다.
본문과 사용량이 같은 JSON 기록에 들어 있는데 파일 전체를 읽고 사용량만 추출한다면, 대화 본문을 읽지 않았다고 할 수 없습니다. C의 승인 범위를 지키려면 상태 줄이나 훅이 필요한 숫자만 별도 파일로 내보내게 하고, 상황판은 그 파일만 읽는 경로를 우선하는 것이 맞습니다. 그런 통로가 없는 세션은 당분간 미관측으로 둬야 합니다.

경로 허용 목록은 폴더 이름만 검사하는 것으로 끝내면 안 됩니다.
설정에 등록한 파일이 링크를 통해 다른 위치를 가리키는 경우, 파일 크기가 비정상적으로 커진 경우, 수집 중 기록이 바뀌는 경우를 처리해야 합니다. 인증 파일 이름을 몇 개 금지하는 방식보다, 읽어도 되는 파일과 필드만 좁게 정하는 방식이 낫습니다.

이것들은 현재 구현에서 발견한 버그가 아니라, C를 구현할 때 지켜야 할 조건입니다. 근거가 되는 승인 범위는 A7 §3.1·§7 결정 C입니다.

Windows와 WSL의 경계도 초기에 확인해야 합니다. A7은 Windows의 HTTP 서버와 데스크톱 세션 정보를 WSL에서 읽는 경로를 미확인으로 남겼습니다. 가장 먼저 실제 PC에서 학습 상태 하나와 이미지 생성 대기열 하나를 읽어 보는 것이, 수집기 인터페이스를 여러 개 설계하는 것보다 중요합니다. Windows 쪽에서 작은 상태 파일을 내보내고 WSL이 읽는 구조도 후보입니다.

3-5. [조언] GPU가 낮게 사용된다는 이유만으로 “빈 자원”이라고 판단하거나 새 실험을 만들면 안 됩니다.

확신도: 높음

A7·A8은 GPU 빈 시간을 채우는 쪽을 강조합니다. 그러나 사용자 목표는 GPU 사용률을 최대화하는 것이 아니라 필요한 작업을 낭비 없이 끝내는 것입니다.

따라서 자동 실행 조건은 다음처럼 잡는 편이 맞습니다.

승인된 대기 작업이 있고, 선행 조건이 충족됐으며, 자원을 맡은 작업이 없다고 확인됐고, 사용자 우선 작업을 방해하지 않을 때 시작한다.

GPU 사용률만 낮아도 메모리를 잡고 있는 작업이나 다른 대기 조건이 있을 수 있습니다. 수집에 실패해서 상태를 모르는 경우도 빈 것으로 처리하면 안 됩니다. 승인된 대기 작업이 없다면 쉬는 것이 정상입니다. 이를 실패로 세면 AI가 필요 없는 실험을 만들어 GPU를 채우려는 방향으로 흐를 수 있습니다.

측정할 것도 “GPU가 쉰 시간”보다 “승인되고 준비된 일이 있었는데 시작되지 못한 시간”이 적절합니다. 이것이 사용자가 겪은 운영 손실에 더 가깝습니다.

근거: A7 §2 P3·P20·P21, §3.1의 미관측 처리, §8의 사용자 우선순위 미해결 항목. 위 실행 조건과 측정 기준은 이 요구에 대한 설계 제안입니다.

4. 결정 D: 일상 모드
3-6. [조언] 채택이 맞습니다. “비교 증거 부족” 때문에 일상 작업을 막는 조건만 풀고, 권한·과금·종료 확인은 유지해야 합니다.

확신도: 높음

D는 세 목표에 부합합니다. 매번 관측 기록을 준비하는 비용을 줄이고, CLI 업데이트나 관측 만료로 일상 작업 전체가 막히는 것을 줄일 수 있습니다. 다만 D만으로 장기 세션 관리나 GPU 작업 실행이 생기는 것은 아닙니다.

중요한 구분은 다음입니다.

| 일상 모드에서 없어져도 되는 실행 조건 | 그대로 남겨야 하는 조건 |
|---|---|
| 같은 기기의 과거 관측 기록이 존재할 것 | 현재 사용할 실행 파일·설정·권한이 명확할 것 |
| 관측 후 30일 이내일 것 | 구독 경로가 확인되고 금지된 과금 경로가 없을 것 |
| 과거 관측 버전과 정확히 같을 것 | 실행에 필요한 명령과 결과 해석이 호환될 것 |
| 독립성이 관측으로 확인됐을 것 | 입력 고정·호출 상한·종료 확인·실패 기록이 유지될 것 |

버전이 바뀌었다는 이유만으로 일상 실행을 거절하지는 않되, 필요한 옵션이 작동하지 않거나 과금·권한 상태를 확인할 수 없으면 막는 것입니다. 과거 관측 기록이 없다는 문제와 현재 안전 조건을 충족하지 못한다는 문제를 분리해야 합니다.

근거: A8 §2 K1·§6 결정 D; core/eligibility.py의 eligibility(); app/cli_executor.py의 _check_eligible(), plan().

구현에서는 다음 부분을 빠뜨리기 쉽습니다.

기존 allow_context_unverified를 켜는 것만으로는 부족합니다.
현재 실행기 생성자는 관측 기록이 없으면 거절합니다. _check_eligible()도 기록의 적격성과 로컬 기기 등록을 확인합니다. 기존 옵션은 문맥 적합성 항목만 느슨하게 할 뿐입니다. 화면·설정 파서·실행기 생성·실행 직전 검사까지 일상 정책이 이어져야 합니다. 관측 도구용 unchecked=True를 제품의 일상 모드로 노출하는 방식은 피해야 합니다.

표시도 일반 실행까지 이어져야 합니다.
현재 공개 조회 코드는 문맥 미확인 경고를 일반 실행이 아닌 경우에 붙입니다. D를 넣을 때는 일상 실행의 화면·내보내기·후속 기억에서 “문맥 미확인”이라는 출처 상태가 사라지지 않게 해야 합니다. 일반 팀원이 독립 비교 대상이 아니라는 설명과, 이번 실행의 문맥을 확인하지 않았다는 설명은 서로 다릅니다.

일상 모드는 곧 쓰기 모드나 자율 모드가 아닙니다.
독립성 확인을 요구하지 않는다고 파일 수정·임의 명령·다른 세션 접근을 허용할 이유는 없습니다. 첫 D는 현재 읽기 전용 실행의 사용 가능성부터 개선하고, 실제 작업 수행 권한은 B와 작업별 승인에서 별도로 다루는 것이 낫습니다.

로그인 확인 역시 종료 코드만 봐서는 부족합니다. 현재 Claude 공식 문서는 auth status에서 로그인 방식이 여러 종류로 구분된다고 설명합니다. 따라서 현재 실행에 사용할 환경과 설정으로 확인하고, 허용한 로그인 방식만 받아야 합니다. 인증 파일을 직접 읽어 토큰을 꺼내는 구현은 필요하지 않습니다.

A8이 우려한 --bare도 주의 대상은 맞습니다. 현재 공식 문서에서 bare가 구독 로그인을 사용하지 않는다는 점은 확인됩니다. 다만 미래 기본값 전환 시점을 단정해 일정을 짜기보다는, 실제로 설치할 판에서 구독 경로와 필요한 옵션을 확인하는 절차로 대응하는 편이 낫습니다.

5. A8 §5의 순서는 맞는가
3-7. [모순] 상황판을 D와 SDK 시험 뒤에 두는 것은, 앞서 제안한 모델 없는 상황판 설계와 맞지 않습니다.

확신도: 높음

A8 §5는 D 다음에 Codex SDK 시험, 승인 수신함, 훅 기반 상황판, 한도 정책을 차례로 둡니다. 반면 A7 §3의 첫 상황판은 모델 호출 없이 상태를 읽고 보여 주는 기능입니다.

상태를 읽는 데 독립 비교의 관측 기록이 왜 먼저 필요한가요? 필요한 것은 읽을 위치에 대한 C의 승인과 실제 데이터 연결입니다. 모델 없는 상태 수집이 D의 완료를 기다릴 이유는 없습니다.

현재 앱 입구가 실제 CLI 준비 조회와 결합돼 있다면 관측 전용으로 여는 경로를 추가하면 됩니다. 실제 상태를 보여 주는 관측 화면을 모의 화면으로 위장해서는 안 되고, 모델 실행이 막혀 있어도 관측은 사용할 수 있어야 합니다.

근거: A7 §3.3–§3.4; A8 §5; A6의 앱 시작 시 준비 조회.

다음 네 가지는 다른 작업을 기다리게 할 필요가 없습니다.

| 작업 | 먼저 필요한 것 | 기다릴 필요가 없는 것 |
|---|---|---|
| 실제 작업 상태 읽기 | C, 읽을 데이터와 출처 확인 | D, SDK 교체, 합성 비교 |
| 완료·실패 전달 | A, 실제 완료 사건, 중복 방지 | 모델 간 토론 기능 |
| 일상 CLI 실행 | D, 모델 없는 과금·권한·호환 점검 | GPU 관제 전체 완성 |
| 승인한 GPU 작업 자동 실행 | B, 자원 소유·종료·복구·승인 기록 | 범용 AI 세션 플랫폼 |

제가 바꾸는 핵심은 필요 없는 선행 조건을 없애는 것입니다. 기능을 같은 앱에 넣는다고 모두 한 줄로 기다리게 만들 필요는 없습니다.

3-8. [결함] A8이 “작은 것”으로 묶은 호출 관문 완화와 재시도는, 실제로는 중요한 정책 변경입니다.

확신도: 높음

A8 §5의 K3 제안은 독립 호출 병렬화, 실패 건너뛰기, 일시적 실패 한 번 재시도를 한 묶음으로 둡니다. 그러나 실패 종류마다 처리가 달라야 합니다.

현재 코드는 종료 미확인 호출이 있으면 다음 호출을 막는 보호를 가지고 있습니다. 이것을 “시간 초과니까 한 번 더”로 바꾸면, 앞 호출이 살아 있거나 이미 결과를 만들었는데 다시 실행할 수 있습니다.

근거: A8 §2 K3·§5; app/execution/invocations.py의 _upper_call_gate(), unsettled(); core/runner.py의 시간 초과·종료 확인 처리.

| 실패 종류 | 기본 처리 |

확신도: 높음

저라면 다음처럼 나눕니다.

그대로 사용하는 것: 작업 목록, 입력 확인, 실행 기록, 결과 위치, 사용량 표시, 필요한 템플릿과 검색.

선택형 실험 기능으로 남기는 것: 독립 초안, 정족수, 익명 교차검토, 합성, 수정·재검토의 여러 단계. 연구나 위험한 판단에는 사용할 수 있지만, 일상 작업의 시작 화면과 기본 절차에서는 뒤로 보냅니다.

당분간 확장하지 않는 것: 더 많은 상위 역할, 자동 팀 구성, 여러 단계의 자동 토론, 고급 기억 검색, 새 도구를 연결하기 위한 범용 규약과 프레임워크. 먼저 실제 사용에서 부족한 점이 반복돼야 합니다.

제거 대상으로 보는 것: 현재 사용하는 경로가 없고, 재사용 계획도 없으며, 보존할 기록으로서의 가치만 남은 실행 코드와 호환 분기. 다만 이번 검토에서는 저장소 전체의 사용처를 추적하지 않았으므로, 특정 파일을 곧바로 삭제하라고 지목하지는 않겠습니다.

현재 실제 합성과 상위 모델이 기본 꺼짐이라는 점은 이미 올바른 방향입니다. 제안은 그 기능을 처음으로 끄라는 것이 아니라, 기본값뿐 아니라 개발 우선순위에서도 선택 기능으로 취급하라는 것입니다.

근거: A1 §2 항목 20·25; A4의 기능·후속 우선순위; A10의 합성 이득 판단 보류.

시험도 같은 기준으로 정리하겠습니다. 시험 코드가 많다는 이유로 줄이지는 않습니다. 중복 시작, 승인 만료, 결과 저장 실패, 재시작 후 중복 실행, 종료 미확인, 봉인 정보 노출을 막는 시험은 남깁니다. 기능을 없앨 때 그 기능만을 위한 시험을 같이 정리하고, 불필요한 문서 형식을 유지시키는 검사부터 재검토합니다.

tests/test_accumulation.py도 자기 검사가 글자 수와 참조 관계를 볼 뿐 실제 유용성을 증명하지 못한다고 명시합니다. 검사에 통과했다는 이유로 기능을 유지할 필요는 없습니다.

4-3. [모순] “한 사실은 한 곳에”라는 규칙을 지키려면, 모든 세션이 같은 인계 문서를 고치는 구조부터 줄여야 합니다.

확신도: 높음

현재 협업 규칙은 중복 상태를 줄이려 하면서도 모든 PR에 인계 갱신을 요구합니다. 특히 같은 절의 같은 PR 줄을 바꾸게 하는 것은 병렬 작업과 충돌합니다. 그 결과 인계 문서를 짧게 유지하는 작업 자체가 반복 업무가 됩니다.

저라면 문서의 역할을 다음처럼 바꾸겠습니다.

상시 규칙에는 바뀌지 않는 경계만 둡니다. 구독 전용, 인증 값 취급, 다른 세션의 작업 보호, 완료를 주장할 근거 같은 것입니다.

현재 할 일은 기존 카드가 담당합니다. 누가 무엇을 하는지, 막힌 이유와 다음 행동을 카드에 둡니다. 인계는 필요한 카드와 적용된 결정을 찾는 짧은 입구로만 사용합니다.

과거 사고와 판단 근거는 날짜 기록으로 남깁니다. 삭제할 필요는 없지만 새 세션의 필수 읽기 목록에서는 제외합니다. 실제로 관련 작업을 할 때만 찾아 읽습니다.

이를 위해 새 문서를 여러 개 만들 필요는 없습니다. 기존 카드·규칙·인계의 중복 역할을 줄이는 작업입니다. 내용이 바뀌지 않은 인계 문서를 PR마다 의무적으로 고치지 않도록 규칙과 검사도 함께 수정하겠습니다.

근거: A3 §3의 작업 카드·§5의 인계 갱신·§7의 한 사실 한 곳 원칙; A2의 시작·종료 규칙.

여기서 중요한 것은 규칙을 잘 따르게 만드는 장치만 늘리지 않는 것입니다. 같은 목적을 더 적은 사람이 기억하고, 더 적은 AI가 읽고, 더 적은 파일을 고쳐도 달성할 수 있다면 그쪽이 낫습니다.

2. 구조는 어떻게 바꾸겠는가
4-4. [조언] 대화 실행·실제 작업·관제의 책임을 나누되, 별도 거대 시스템 세 개를 만들지는 않겠습니다.

확신도: 높음

저라면 책임을 세 층으로 나눕니다.

공식 CLI는 자기 대화를 맡습니다.
모델 호출, 대화 기록, 같은 세션 이어 하기, 도구 실행과 해당 CLI의 권한 요청을 담당합니다. 우리 앱은 세션 ID와 맡긴 작업, 관측한 상태를 연결합니다. 대화 저장과 재개 기능까지 다시 만들지 않습니다. Codex App Server에는 스레드·실행 이벤트·승인 연결이 있고, Claude CLI에는 특정 세션 ID로 이어 가는 공식 경로가 있습니다.

실제 작업 도구는 자기 작업의 결과를 맡습니다.
학습 스크립트·이미지 생성 서버·작업 큐는 시작 여부, 실행 ID, 진행 상태, 종료와 산출물을 알려 줍니다. 무엇을 만들어야 성공인지에 관한 구체적인 검사는 실제 작업 프로젝트에 두는 편이 맞습니다.

관제 앱은 사용자 의도와 실행을 연결합니다.
어떤 작업이 승인됐는지, 무엇을 기다리는지, 자원을 누가 맡았는지, 결과가 확인·전달됐는지, 사용량이 얼마나 관측됐는지를 관리합니다.

이 구분에서 특히 중요한 것은 “앱 원장이 정본”이라는 말의 범위입니다. 승인과 실행 요청은 앱 기록이 기준이 될 수 있지만, 실제 학습 프로세스가 살아 있는지까지 앱의 오래된 행이 결정해서는 안 됩니다. 요청한 상태와 실제로 관측한 상태를 대조해야 합니다. A7도 이 대조를 제안합니다.

예를 들어, Claude의 Stop 훅은 주 에이전트가 답변을 끝냈다는 사건이지, 그 세션이 시작한 외부 학습이 성공했다는 증명이 아닙니다. 공식 문서도 답변 종료와 백그라운드 작업을 구분합니다. 이 사건을 학습 완료로 번역하면 안 됩니다.

이렇게 나눠도 하나의 저장소, 작은 상주 프로그램, 기존 화면으로 시작할 수 있습니다. 마이크로서비스나 범용 이벤트 플랫폼을 새로 만드는 제안이 아닙니다.

현재 A5의 서비스·실행·조회 분리는 이 방향으로 바꾸기 위한 기반이 됩니다. 다만 엄격 비교의 수용·공개 규칙을 모든 외부 작업에 재사용하려 하지는 않겠습니다. 공통으로 쓸 것은 기록과 안전 원칙이지, 모든 작업의 완료 조건은 아닙니다.

근거: A5 「실행되는 뼈대」·「코드 위치와 변경 책임」; core/README.md의 실행 코어 범위.

장기적으로는 작업과 예산의 수명도 분리해야 합니다. 작업은 계속 같은 작업으로 남고, 승인·호출 한도는 기간과 범위가 다른 기록으로 연결하는 편이 낫습니다. 현재처럼 예산이 소진돼 새 원장을 열 때 작업·기억·템플릿까지 갈라지는 구조는 일상 운영에 불편합니다. 기존 소비 기록을 지우거나 상한을 소급 변경하자는 뜻은 아닙니다.

4-5. [조언] GitHub는 개발 협업의 공유 지점으로 남기고, 실시간 운영 상태와 비공개 작업 내용까지 모두 올리는 장소로 만들지 않겠습니다.

확신도: 높음

현재 “GitHub이 유일한 공유 지점”이라는 규칙은 웹 AI와 PC 세션이 코드를 함께 개발하는 상황에서는 이유가 있습니다. 그러나 그것을 그대로 실시간 작업 관제에 확대하면, 상태가 바뀔 때마다 문서·커밋·전달을 만들게 됩니다.

웹 AI가 로컬 상태를 직접 볼 수 없다면, 그 세션에 보이는 자료에는 생성 시각과 범위를 적습니다. 오래된 자료를 보고 “지금 실행 중”이라고 판단하지 않게 해야 합니다. 그렇다고 실시간 상태를 전달하려고 공개 decision-model_lab 저장소에 다른 프로젝트의 로그와 내용을 자동 업로드해서는 안 됩니다.

A7이 비공개 프로젝트 원문을 공개 저장소로 옮기지 않고 일반화한 것은 유지해야 할 경계입니다.

근거: A3 §1의 GitHub 공유 규칙; A7 머리말의 비공개 입력 취급; A6의 원문 보고 자동 공개 업로드 금지.

외부 도구의 아이디어만 가져와 기능을 다시 구현하면, 이후 버그 수정과 공급자 변경 대응은 계속 우리 책임입니다. 따라서 “코드에는 의존하지 않고 참고만 한다”는 선택도 유지 비용이 있습니다. 독립성이 필요한 부분과 이미 해결된 일반 기능을 나눠 판단해야 합니다.

근거: A8 결론 2·3, §1의 배선 재발명에 대한 자체 지적, §3의 참고·채택 기준.

그렇다고 공식 도구를 무조건 쓰자는 뜻도 아닙니다.

예를 들어 OpenAI의 Codex 플러그인은 Claude 안에서 읽기 전용 검토와 결과 조회를 제공하므로, 일상적인 Codex 두 번째 의견을 받는 왕복을 줄일 후보입니다. 하지만 이것이 웹 ChatGPT·Gemini의 검토를 같은 조건으로 대신하는 것은 아닙니다. 또한 이 프로젝트의 엄격한 독립 비교를 검증 없이 대체해서도 안 됩니다.

더 중요한 점은 그 플러그인의 공식 README조차 자동 검토 게이트가 Claude·Codex의 긴 반복을 만들고 한도를 빠르게 소진할 수 있다고 경고한다는 것입니다. 저는 수동으로 필요한 검토를 요청하는 경로만 먼저 쓰고, 자동 검토 게이트는 기본 꺼짐으로 유지하겠습니다.

즉, 선택 기준은 공식인지, 기능이 많은지, 우리 설계와 비슷한지가 아니라 필요한 범위만 안전하게 사용할 수 있는지와 전체 운영 부담이 줄어드는지입니다.

4. 이 앱을 계속 키울 것인가, 실제 작업 쪽에 힘을 쓸 것인가
4-8. [조언] 다음 개발의 대부분은 실제 작업 쪽 연결에 쓰고, 이 앱에는 그 연결에 꼭 필요한 변경만 하겠습니다.

확신도: 높음

둘 중 하나의 저장소를 버리라는 뜻은 아닙니다. 개발의 출발점을 바꾸자는 뜻입니다.

현재 흐름은 앱에 넣을 기능을 정한 뒤 그 기능의 구조·규칙·시험·문서를 완성하는 쪽에 가깝습니다. 다음에는 실제 불편 하나를 고르고, 그것을 없애는 데 필요한 최소한의 변경을 양쪽에 넣어야 합니다.

예를 들어 “학습이 끝났는데 전달되지 않는다”를 고쳤다면 필요한 결과는 다음 정도입니다.

학습 실행기가 정확한 작업 ID와 결과를 기록합니다. 관제는 실제 상태를 확인합니다. 완료가 확정되면 결과 위치와 함께 전달합니다. 재시작해도 같은 학습을 다시 돌리지 않습니다.

이 흐름이 실제로 작동하면 하나가 끝난 것입니다. 그 전에 범용 세션 플랫폼, 모든 회사의 승인 통합, 새로운 SDK 추상화를 완성할 필요는 없습니다.

A7도 실제 작업의 상태·전달·자원 문제를 핵심으로 분류합니다. 반면 기준 커밋의 A1은 사용자가 새 화면을 아직 써 보지 않았다고 기록하고, 다음 첫 작업으로 일반 팀원 비교 실험을 둡니다. 이 우선순위를 바꾸겠습니다.

근거: A7 결론·§1–§3; A1 §3·§4.

개발 관리에도 거창한 새 절차는 필요 없습니다. 기존 카드의 목표와 완료 조건에 다음 한 문장을 채울 수 있으면 됩니다.

이 변경은 사용자가 반복하던 어떤 행동을 없애며, 실제로 없어졌다는 것을 무엇으로 확인할 것인가?

여기에 답하지 못하는 신규 기능은 당장 만들지 않겠습니다. 기존 카드 양식에 이미 목표·범위·완료 조건·입력·호출 상한이 있으므로 새 양식을 추가할 필요도 없습니다.

4-9. [조언] 앱을 계속 키울지는 다음 기능 제안이 아니라, 실제로 사용한 결과를 보고 정하겠습니다.

그 절약보다 앱 개발·검토·수리 때문에 드는 일이 더 커지지는 않았는가.

이득이 확인되면 반복해서 나타나는 다음 불편을 해결합니다. 반대로 대부분의 작업은 여전히 기존 도구에서 끝나고, 이 앱은 유지해야 하는 화면 하나만 더 늘린다면 상황판과 필요한 연결부만 남기고 확대를 멈추는 것이 맞습니다.

이 판단에서 “지금까지 많이 만들었다”는 계속 개발할 근거가 아닙니다. 반대로 초기 개발비가 컸다는 이유만으로 당장 폐기하는 것도 맞지 않습니다. 앞으로 필요한 유지비와 앞으로 얻을 편의를 비교해야 합니다.

A10은 합성의 일반적 이득을 입증하지 못했고, A4는 여러 추가 기능의 실제 모델 효과를 미측정으로 남깁니다. 이 불확실성에 대응하는 방법은 또 다른 큰 플랫폼을 만드는 것이 아니라, 이미 만든 작은 흐름을 실제 업무에 써 보는 것입니다.

근거: A10 「결론」·「한계」; A4의 GR-1–GR-3와 실제 사용 흐름 관측 항목; A1 §4의 “효과가 없으면 자동화를 늘리지 않고 멈춘다”는 조건.
