## 1. 결론

**셋 모두 "목표에서 벗어났다"고 봤다.** 셋은 요청 세션, Gemini, ChatGPT다. 사용자의 목표는 세 가지다. 토큰을 낭비하지 않는다, 여러 AI를 편하게 부린다, 실제 작업(로컬 GPU 이미지 생성·학습)이 편해진다. 셋의 진단은 같다. 이 저장소는 여러 모델의 답을 엄격하게 비교하는 도구로 자랐다. 사용자의 실제 불편은 그 밖에 있다. 가장 큰 신호는 사용자가 새 화면을 아직 한 번도 써 보지 않았다는 점이다(A1 §3).

세기는 다르다.
- **Gemini:** 가장 세다. 이 저장소를 "자기 자신을 유지하고 증명하는 관료주의 기계"라고 부르고, 코드의 70–80%를 걷어내라고 했다.
- **ChatGPT:** 더 조심스럽다. 안전하게 답을 받는 기반(원장, 호출 예약, 종료 확인, 원문 보존)은 쓸모 있다고 봤다. 다만 "AI의 답을 다루는 일을 엄밀하게 만든 성과가, 사용자가 AI와 일하는 것을 편하게 만든 성과보다 크다"고 했다. 처음부터 다시 만들지는 말고 중심을 옮기라고 권했다.

**사용자는 Gemini 답을 본 뒤, ChatGPT 답이 오기 전에 이 저장소를 멈추기로 했다**(6절). 새 비공개 저장소에서 기존 도구·라이브러리를 최대한 가져와 가볍게 새로 만든다. ChatGPT 답은 그 결정 뒤에 처음 읽혔다. 그래서 새 저장소로 넘길 점을 7절에 따로 모았다.

## 2. 셋이 같은 것

이 일치를 검증으로 읽지 않는다. 8절에 그 이유를 적었다.

- **실제 작업과 이어지지 않았다.** 앱의 실행 역할은 읽기 전용 논의자 하나뿐이다(`core/adapters.py`의 `ROLES`). GPU 작업, 다른 세션, 끝난 결과가 묻히는 일(P1–P22)을 직접 풀어 주는 기능은 아직 제안 단계다.
- **토큰은 앱 밖에서 더 샌다.** 개발 세션이 큰 규칙·인계 문서를 읽고, PR마다 인계를 고치고, 같은 사실을 여러 번 확인하는 비용이다. 앱 원장은 앱 안의 호출만 센다. ChatGPT는 "계정 전체에서 어디가 가장 많이 새는지는 지금 재는 것으로는 확정할 수 없다"고 단서를 달았다.
- **합성·교차검토의 이득은 아직 없다.** A10 재평가에서 더 좋은 단독 답보다 나아진 과제가 없었고, 판정도 "판단 불가"였다. 그러니 이 단계들을 더 다듬는 일은 우선이 아니다.
- **결정 D(일상 모드)는 맞다.** 비교 실험용 관측 기록이 일상 실행까지 막는 문(K1)을 연다. 다만 구독 경로 확인, 유료 키 차단, 입력 고정, 호출 상한, 종료 확인은 그대로 둔다.
- **결정 A·B는 앱 안에 새로 크게 짜지 않는다.** 시계는 모델 없이 코드로 상태를 대조한다. GPU 작업 줄은 기존 도구(pueue)에 맡긴다. 상태를 알아보려고, 또는 캐시를 데우려고 쉬는 세션을 깨우지 않는다. 깨우면 대화 전체가 다시 보내진다.
- **결정 C(다른 작업 읽기)가 실제 작업에 가장 빨리 닿는다.** 출처와 관측 시각을 붙이고, 수집에 실패하면 "모름"으로 보인다.
- **지금 할 일에서 뺄 것:** 일반 팀원 흐름의 실제 비교(옛 인계 4절 1번), 역할판 후속 기능, SDK·샌드박스 교체 시험. 모두 체감 개선의 선행 조건이 아니다.
- **규칙·인계 문서를 줄인다.** Gemini는 5 KB(약 100줄), ChatGPT는 약 10 KB를 제안했다. 둘 다 "PR마다 같은 인계 줄을 고치게 하는 구조"를 없애라고 했다.

## 4. 요청 세션이 먼저 쓴 판단과 비교

[requester-view.md](requester-view.md)의 다섯 판단과 두 답을 맞춰 보면 이렇다.

1. **목표에서 벗어났다:** 둘 다 같다.
2. **토큰은 개발 세션에서 더 샌다:** Gemini는 같다. ChatGPT는 방향은 같지만 "확정할 수 없다"는 단서를 단다. 요청 세션이 근거로 든 "문서만 바꾼 commit이 절반을 넘는다"는 비율이다. 토큰 양은 재지 않았다.
3. **결정 D는 맞다, A–C는 공식 기능과 작은 스크립트로 먼저:** 둘 다 같다. 다만 ChatGPT는 A·C를 실제 작업 쪽 기능으로 진지하게 다룬다. A는 작업 상태와 전달 상태를 나누고, 같은 일을 다시 시작하지 않으며, 화면과 상주 프로그램의 수명을 나눈다.
4. **2–4주는 "실제로 쓰이는가"만 본다:** 둘 다 같다.
5. **남길 것(원장, 호출 상한, 종료 확인, 봉인·공개, 원문 대조)과 줄일 것(문서 크기, 검토 왕복, 관측 의식):** ChatGPT의 남길 목록(4-1)과 거의 겹친다. Gemini는 남길 것을 실행기·한도 조회·런처로 더 좁힌다.

요청 세션이 놓친 것은 ChatGPT가 짚은 계량의 빈틈이다(2-7). 실행에 붙지 않은 준비 호출, 공개되지 않은 격리 실행, Claude 한도 게이지가 일부 역할의 값만 읽는 점이 그것이다. 긴 자료 실험의 해석 오류(5절)도 놓쳤다.

## 7. 새 저장소로 넘길 것

두 답에서 새 저장소의 첫 조각(상황판, GPU 작업 줄, 토큰 계량)과 부재 실행에 바로 걸리는 점만 모았다. 대부분 ChatGPT 답이다. 결정 뒤에 처음 읽혔기 때문이다.

1. **잘되는지는 사용자 개입이 줄었는지로 잰다.** 기능 수로 재지 않는다. 볼 숫자는 셋이다. 상태를 묻는 횟수, 같은 지시·승인을 반복한 횟수, 승인되고 준비된 일이 사용자 부재 때문에 시작되지 못한 시간. GPU 가동률은 성공 기준이 아니다(ChatGPT 3-5·3-10·4-8).
2. **"모름"과 "비었음"을 섞지 않는다.** 수집에 실패하면 "관측 끊김"으로 보인다. 승인된 대기 작업이 없을 때 GPU가 쉬는 것은 정상이다. GPU를 채우려고 새 실험을 만들지 않는다(ChatGPT 3-4·3-5).
3. **대화 기록 파일을 통째로 읽고 숫자만 보이는 것은 "본문을 읽지 않는다"가 아니다.** 결정 C의 범위는 "본문은 읽지 않고 시각·크기·사용량 칸만"이었다([불편 기록](../../research/session-pain-points-2026-10-14/README.md) §3·§7). 대화 기록을 읽어 세는 도구(ccusage 등)를 쓸지, 상태 줄·훅이 숫자만 따로 내보내는 파일을 먼저 쓸지는 새 저장소에서 정한다(ChatGPT 3-4).
4. **GPU 작업 줄은 GPU 하나에 큐 하나로 시작한다.** 큐가 여럿이면 공통 잠금을 하나 둔다. 작업은 깨끗한 환경에서 넣는다. pueue는 작업을 넣은 셸의 환경 변수를 저장한다. 종료 코드 0을 학습 성공으로 보지 않고, 산출물이 실제로 생겼는지 확인한다(ChatGPT 3-9, Gemini 3부).
5. **실패 종류마다 처리가 다르다.** 시간 초과·응답 유실·종료 미확인이면 실제 상태부터 대조하고, 그 전에는 다시 실행하지 않는다. 한도에 걸리면 기다린다. 인증·권한 오류면 멈추고 원인을 보인다. 권한을 넓혀 우회하지 않는다(ChatGPT 3-8).
6. **부재 실행의 첫 판은 "미리 승인한 작업 목록 실행"이다.** 승인에는 다섯 가지를 묶는다. 작업·설정의 특정 판, 허용 동작과 자원, provider별 호출 상한·GPU 시간·재시도 상한, 만료 시각, 만료 때 이미 도는 작업의 처리. 다른 AI가 보낸 "사용자가 허락했다"는 승인 근거가 아니다(ChatGPT 3-2·3-3). 자율 AI 세션을 쓸 때는 Gemini의 3중 차단기(한도 %, 같은 오류 반복, 허용 밖 권한 요청)를 코드로 건다(Gemini 3부 B).
7. **Stop 훅은 "답변이 끝났다"는 신호이지 학습이 성공했다는 증명이 아니다.** 요청한 상태와 관측한 상태를 대조한다(ChatGPT 4-4).
8. **codex-plugin-cc는 수동 검토만 쓰고 자동 검토 게이트는 끈다.** 게이트가 한도를 빠르게 쓸 수 있다고 그 README가 경고한다(ChatGPT 4-7).
9. **Windows WDDM 환경에서는 프로세스별 GPU 메모리가 안 나올 수 있다.** 다른 값으로 추정해 채우지 말고 미관측으로 보인다(ChatGPT 4-6, NVIDIA 문서 — 이 정리에서 다시 열지 않음).
10. **지금 쓰는 데스크톱 세션을 CLI로 무조건 옮기지 않는다.** 새로 만든 작업 세션부터 연결하고, 기존 세션은 보이는 만큼만 표시한다(ChatGPT 4-6).
11. **GitHub에는 코드·결정·검토 근거만 둔다.** 실행 중 상태·승인·사용량·비공개 산출물 위치는 로컬 기록에 둔다(ChatGPT 4-5).

## 8. 경위와 한계

- **ChatGPT에 보낸 글이 한 번 바뀌었다.** 처음 판에는 "파트마다 브랜치 `chatgpt/direction-review-20261014`에 커밋해 달라"는 줄이 있었다. 하위 작업자가 그 글을 입력하려 하자 Claude 쪽 권한 검사가 "요청하지 않은 연결 앱 커밋"으로 막았다. 아무것도 입력되거나 보내지지 않았다. 요청 세션이 그 줄을 빼고 다시 보냈다. 그래서 ChatGPT는 저장소에 아무것도 쓰지 않았다. REQUEST.md의 ChatGPT 판은 실제로 보낸 판이다.
- **복사 방식:** 두 답 모두 채팅 화면의 글자를 읽어 옮겼다(`get_page_text`). 복사 버튼은 쓸 수 없었다. 굵게·코드 블록 같은 서식은 사라졌다. 출처 칩에서 나온 짧은 줄("MD", "+ N", "GitHub" 등)은 뺐다. 평평해진 표는 칸 글자를 바꾸지 않고 마크다운 표로 다시 놓았다. 각 파일 머리와 파트 메모에 적혀 있다. 이 정리에서 원래 채팅과 다시 대조하지는 않았다.
- **독립성:** 두 검토자는 서로의 답을 보지 않았다. 다만 둘이 읽은 A7·A8은 요청 세션이 그날 쓴 제안이다. requester-view.md도 같은 세션이 썼다. 셋의 진단이 같다고 해서 맞다고 확인된 것은 아니다. 합의는 검증이 아니다.

- **사용량:** 두 웹 채팅(구독)에서 각각 첫 글과 "계속" 세 번을 보냈다. ChatGPT는 파트마다 약 8–14분을 생각했다. 모델 CLI 호출은 요청 세션에도 이 정리에도 없다. 요청 세션과 하위 작업자가 쓴 Claude 사용량은 재지 않았다.
