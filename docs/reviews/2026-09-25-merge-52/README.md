### 실제 서버 종료 — 전후 비교

WSL에서 모의 서버를 띄워 끝나지 않는 가짜 참여자(`behavior: hang`)를 bubblewrap 안에서 실제로 실행시킨 뒤 2초 기다려 **서버 프로세스에만** SIGINT(Ctrl+C와 같은 신호)를 보냈다. 그다음 같은 데이터 폴더로 다시 띄워 원장을 읽었다. 모델 호출 없음. 원장은 `/tmp`에 두고 끝나고 지웠다.

| | PR 전 main(`6cd1363`) | PR 뒤(`797c4d3`) |
|---|---|---|
| 서버 종료 코드·포트 | 0, 닫힘 | 0, 닫힘 |
| 원장의 마지막 사건 | `attempt_unknown` | `attempt_rejected` — `cancelled`, 종료 코드 -15, 자손 종료 확인, 입력 전달 완료 |
| 재시작 뒤 미종료 수 | 1(자리 하나를 계속 차지, 사용자가 풀어야 함) | 0 |
| 남은 `bwrap`·`app.server` 프로세스 | 없음 | 없음 |

즉 PR 전에는 서버를 끄면 돌던 시도가 "결과 모름"으로 남았고, PR 뒤에는 서버가 먼저 취소를 알리고 자손 종료까지 기록한 뒤 원장을 닫는다. 빈 서버 종료와 재시작(원장 잠금 해제)도 두 판 모두 정상이었다.

곁들여 본 것: 참여자가 `running`으로 표시된 직후(0.1초 안) 끄면 가짜 CLI가 실제로 뜨기 전이라 `failed_to_start`로 끝났다. 취소가 시작보다 먼저 닿은 경우이고 자손 종료 확인도 참이었다. 이전 실험 드라이버([strict](../2026-09-25-strict-live-run/drive.py))처럼 **프로세스 그룹 전체**에 SIGINT를 보내는 경우도 병합한 판에서 같은 조건(가짜 CLI가 뜬 뒤 2초)으로 봤다. 결과는 서버에만 보낸 경우와 같았다(`cancelled`·-15·자손 종료 확인, 종료 코드 0, 남은 프로세스 없음).

## 발견

| # | 내용 | 조치 |
|---|---|---|
| N1 | `test_app_shutdown`의 첫 시험은 종료 뒤 `resume`·새 실행·합성이 **어떤 이유로든** 거절되면 통과했다. 그 실행은 아직 공개 전이라 합성은 종료 관문이 없어도 "공개 전" 이유로 거절된다. 실제로 합성의 종료 관문을 지운 변이가 원래 시험을 통과했다 | 세 거절 모두 "shutting down" 이유를 보게 했다. 같은 변이가 이제 실패한다 |
| N2 | R1(인용 공백)은 결함 수정이라기보다 **규칙을 엄격하게 한 것**이다. 이전 판도 앞뒤 공백을 벗긴 인용의 위치를 정확히 기록했다. 이제는 합성자가 인용 앞뒤에 초안에 없는 공백·줄바꿈을 붙이면 `not_found`가 된다 | 유지한다 — "글자 그대로"라는 계약에 맞다. 다만 다음 실제 합성에서 원문 일치율이 떨어지면 이 변경을 먼저 의심한다 |
| N3 | `app/synthesis.py`가 파일 끝 줄바꿈 없이 끝났다(마지막 줄 내용은 같음) | 줄바꿈을 더했다 |
| N4 | [검토 기록](../2026-09-25-deep-review/README.md)의 "최종 CI를 아직 확인하지 않았다"는 그 커밋 시점의 문장이다. 최종 head `797c4d3`의 CI는 성공했다 | 날짜 붙은 기록은 고치지 않고 [검토 색인](../README.md)에 적었다 |

코드가 한 번에 한 가지씩 확인한 것: `_Server.daemon_threads = False`는 끄는 동안 HTTP 처리 스레드를 기다리게 한다. 처리기에는 5초 유휴 제한이 있어 열린 연결이 종료를 오래 막지는 않는다. 시작하지 못한 스레드를 목록에서 걸러내는 `reap()`은 CPython 3.12/3.13의 `socketserver._Threads`에 있는 메서드다.
