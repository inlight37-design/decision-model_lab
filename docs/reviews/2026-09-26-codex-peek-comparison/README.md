# codex-peek 두 리뷰 비교와 통합 판단

2026-09-26 · Codex · 사용자 제공 독립 리뷰와 기존 PR #102를 함께 읽은 후속 비교. **기존 리뷰의 방향은 타당하다. 독립 리뷰는 그 방향을 뒤집기보다, 실제로 어디까지 강제되는지를 반례로 보강한다. 실행 순서는 기존 리뷰 쪽이 현재 프로젝트에 더 잘 맞는다.**

제가 권하는 결합은 **기존 리뷰의 작은 적용 순서 + 독립 리뷰의 구체적인 반례와 완료 조건**이다. 역할판 작업을 이어가면서, 이미 있는 질문·자료·결과 기록을 연결해 검토 범위를 보여 준다. 별도 작업 계약 확장을 선행 과제로 삼을지, 교차검토와 기억 자동화를 붙일지는 그 뒤에 판단한다. 이번 변경은 비교 문서와 검증 자료 보존이며 제품 기능을 구현하거나 채택 결정을 바꾸지 않는다.

## 3. 새 반례가 기존 판단을 얼마나 바꾸는가

### 실행 성공과 검토 통과

B의 전체 경로 재현은 가짜 Claude 검토자가 blocker와 `Verdict: fail`을 반환해도 job은 `succeeded`, `ask-wait`는 exit 0, 해당 Codex Stop은 차단 응답 없이 끝났음을 보여 준다. **job이 '호출을 마쳤다'는 뜻으로 성공한 것은 모순이 아니다. 그 상태를 '검토에 통과했다' 또는 '미해결 지적이 없다'로 읽을 때 문제가 된다.** 후처리 응답 자체에는 수정·재검증 의무가 남아 있다.

적용 범위는 Codex 구현 훅, core 프로필, 승인 envelope 없는 설정, 가짜 Claude provider의 그 경로다. 별도 판단 대기·상한 마감·다른 프로필까지 모두 우회됐다는 실험이 아니다. A도 이미 토론 종료·결과 승인·프로세스 종료를 구분했다. B는 이 원칙을 선택사항이 아닌 **완료 판정의 명시적인 조건**으로 다룰 근거를 더했다.

우리 표시에서는 다음을 섞지 않는 편이 맞다: 호출 완료 여부, 검토자의 판정, 지적의 처분, 검토한 대상이 아직 같은지, 현재 단계에서 결과를 수용할 수 있는지. 다섯 개 DB 테이블을 새로 만들라는 뜻은 아니다. 기존 상태와 빠진 의미를 먼저 대응시킨다.

### 검토 뒤 변경 탐지

미추적 디렉터리가 `?? newcode/`로 축약되면, 그 안 파일 내용만 바뀌었을 때 디렉터리 mtime이 그대로여서 최신성 검사가 놓칠 수 있었다. 같은 재현에서 추적 파일 변경은 `proof-stale`로 차단됐다. 그러므로 **'Git 저장소 안이니 모든 변경을 잡는다'는 해석은 반박됐지만, '변경 감지가 전혀 없다'는 해석도 틀리다.**

`--untracked-files=all`만 붙이는 수정은 한 사례를 줄일 뿐 최종 내용 결속 전체를 해결하지 않는다. 우리에게는 이미 있는 입력·source·draft 해시를 검토 대상 참조에 쓰고, 검토 결과를 사용할 때 대상이 달라졌는지 표시하는 접근이 적합하다. 외부 가변 파일을 읽는 동안의 바꿔치기까지 해결됐다는 주장도 피한다. 그 문제는 별도 경계다.

### 기억 승인과 자동 처리

A의 '자동 수칙 후보 스캔 폐지'와 B의 '관찰/MAP에는 자동 추론이 있다'는 모순이 아니다. 정확한 결론은 **관찰 수집, 관계 추론, 수칙 후보 제안, 사용자 승인, 실제 전달을 나눠 확인해야 한다**는 것이다. 과거 교훈을 짧게 재사용하는 것은 시도할 가치가 있지만, 같은 오류를 모두에게 주입할 위험도 있다. 동일 자료를 받았다는 사실만으로 오류가 서로 독립이라는 보장은 생기지 않는다.

## 4. 제 의견: 적용 순서는 이렇게 합치는 것이 맞다

### 먼저, 역할판의 정해진 흐름을 유지한다

독립 리뷰 B의 TaskSpec 지적은 설계 계약과 runtime 사이의 간극을 잘 짚었다. B도 전체 계약 이식이 아니라 **필요한 필드만 연결**하자고 제안했다. 차이는 이를 첫 작업 묶음/P0으로 앞세운 점이다. 사용자가 다음 역할판 A 단계를 맡겼다는 결정과 그 뒤의 구현 순서는 B가 본 main 인계에도 이미 있었다. 전체 단계가 모두 별도로 승인됐다는 뜻은 아니며, 현재는 요청받은 역할판을 우선하고 기존 인계의 순서를 유지하는 편이 적합하다. 또 #101에는 `prepare_run`의 확인 manifest, `confirmation`, `tasks/task_id`, 고정 `role_config`가 추가됐다. **작업의 입력·역할을 고정하는 부분은 이미 진행 중이므로, 계약 확장 전에 중복과 남은 요구부터 확인해야 한다.**

그렇다고 기존 TaskSpec의 `goal`·`acceptance_ids`나 B가 제안한 명시적 제외 범위가 모두 runtime에 구현됐다는 뜻은 아니다. 먼저 다음 검토 기능이 실제로 요구하는 빠진 필드만 식별한다. 목표·범위는 문서상의 요청 형식으로 시험할 수 있고, 저장과 재사용이 필요한 시점에 기존 schema/Store에 최소한으로 연결하면 된다. 근거: [#101의 controller](https://github.com/inlight37-design/decision-model_lab/blob/8fc945d410bec31d7f104199a684e9aab4f5b9a3/app/controller.py), [roles](https://github.com/inlight37-design/decision-model_lab/blob/8fc945d410bec31d7f104199a684e9aab4f5b9a3/app/roles.py), [원래 TaskSpec](https://github.com/inlight37-design/decision-model_lab/blob/435ba02f50d287f62dce7512a0ceae9b9c2f164b/contracts/v0.1.schema.json).

### 첫 보완은 기존 기록의 연결과 정확한 표시다

결과 화면에서 질문·자료 판, 대상 초안, 검토 응답, 인용 대조, 남은 쟁점을 이어 보여 주는 제안에 우선 동의한다. 실제 검토자가 없었던 실행은 '검토 미실시'로 보여야 한다. 기존 실행 기록을 연결했다는 이유로 새로운 검토가 수행된 것처럼 표시하면 안 된다.

현재 합성에도 claim id, 참여자와 초안 해시, 인용 위치, `disposition: unresolved`, `factual_check: not_performed`가 있다. 따라서 '지적별 처분이 아예 없다'고 설명하면 과장이다. 추가 후보는 **처분을 바꾸는 절차, 반박 근거, 재검토와 대상 변경의 수명 관리**다. [현재 합성 구현](https://github.com/inlight37-design/decision-model_lab/blob/435ba02f50d287f62dce7512a0ceae9b9c2f164b/app/synthesis.py#L203-L272).

표시할 근거도 구분해야 한다. source가 읽기 전용 폴더에 제공됨, 요청에 포함됨, 응답이 실제로 인용함, 인용이 원문과 일치함, 모델이 내용을 이해하고 판단에 썼음은 같은 사실이 아니다. 관측할 수 없는 마지막 항목을 '실제 사용 완료'로 꾸미지 않는다.

### 기억은 사람이 선택한 공통 자료부터 시험한다

A의 수동 선택을 첫 단계로 택한다. B의 작은 규칙 기반 검색은 그다음 후보로 둔다. 둘 다 자동 모델 검색보다 단순하지만, 수동 시범은 새 저장소나 검색기를 만들지 않고 **좋은 관련 기억 자체가 이 과제에 도움이 되는지**부터 확인할 수 있다. 이는 작은 효용 실험의 통제 방식이며, 사용자가 매번 기술적 기억을 찾아 승인해야 하는 영구 제품 흐름을 권하는 것은 아니다. 관찰 기록마다 새 승인을 요구할 필요도 없다.

실행 전 선택된 짧은 자료만 같은 비교 참여자에게 고정해 전달한다. 봉인 중 동료 답·검토자의 의견을 전달하지 않는다. 공개 뒤 얻은 교훈은 현재 독립 초안에 소급 주입하지 않고 다음 실행용 후보로 둔다. 같은 총예산에서 기억 없음·확인된 관련 기억·오래되거나 반박된 기억을 비교하고, 개선이 없으면 자동화는 보류한다. 수동 선택의 시간이 실제 병목이고 선택 품질이 확인될 때 결정론적 검색을 검토한다.

### 추가 교차검토는 효과를 확인할 후속 기능으로 둔다

B가 제안한 공개 뒤 교차검토는 구조상 적합하다. 다만 '적합하다'와 '지금 추가 호출 비용을 쓸 만큼 유리하다'는 별개다. 초기 초안은 그대로 보존하고, 동료 답을 본 검토 결과를 독립 정족수에 다시 세지 않는 조건이 필요하다.

원문 B의 '초안 2 + 교차검토 2 + 합성 1 = 5회'는 시험 예시이며 검증된 최적 설정이나 이번 호출 승인이 아니다. 비교는 현재 흐름과 같은 총예산의 강한 단독 모델을 포함해야 한다. 오류를 더 찾는지뿐 아니라 맞던 답을 망치는지, 미해결 반례를 지우는지, 호출·지연·사람의 검토 시간이 늘어나는지도 본다. 이득이 확인되기 전에는 자동 반복·상시 curator·외부 호출 facade를 필수 구성으로 삼지 않는 것이 제 판단이다.

## 5. 채택 여부를 정리한 처분표

이 표는 이번 비교자의 권고다. 사용자 결정·제품 정책·현재 구현으로 승격하지 않는다.

| 제안/주장 | 처분 | 이유와 다음 조건 |
|---|---|---|
| 기존 실행기·원장·독립 초안을 유지 | 수용 | 목적과 기존 경계에 맞음. 새 review도 기존 예약·봉인·종료 확인을 따라야 함 |
| proof를 버리지 말고 보장 범위를 명확히 표시 | 수용 | 실행 이력 결속은 유용함. 판정·미해결·대상 최신성을 따로 검사 |
| 실패 판정/내용 변경/인용 의미 반례를 완료 조건에 반영 | 보강 수용 | B의 재현을 새 기능의 음성 대조로 사용. 국소 반례를 전 제품 실패로 일반화하지 않음 |
| TaskSpec의 필요한 필드 연결을 다음 최우선으로 추진 | 순서 조정 | B도 필요한 필드만 제안했다. 기존 역할판과 중복을 확인하고 표시·문서 시범에 필요한 최소 필드부터 연결 |
| 지적별 처리 기능 | 부분 수용 | 문서에서 처분부터 사용. 기존 unresolved·인용 구조를 재사용하며 별도 DB는 필요 확인 뒤 |
| 사람 선택 기억 → 자동 검색 | 조건부 수용 | 수동 기억의 효용과 선택 비용부터 측정. 정책 승인과 사실 검증 분리 |
| 공개 뒤 교차검토 | 보류 후보 | 같은 비용에서 순이득이 확인돼야 우선순위를 올림. 원장 밖 호출·독립 정족수 재계산 금지 |
| 전체 Peek 설치·영속 세션을 격리 실행기에 연결 | 현재 채택하지 않음 | 격리 목적·공유 문맥·추가 호출·전역 설정 변경이 현재 범위와 맞지 않음 |
| CI·선택 시험·Warm 결과를 품질 보증으로 사용 | 반박 | 각각 저장소 회귀, 제한된 동작, 통제 벤치다. 우리 실제 과제의 효과는 미확인 |

## 6. 이 비교가 해결하지 않은 것

실제 모델 품질, 자동 기억이 정확한 기억을 생산하는 비율, 우리 과제의 비용 대비 개선, 모든 OS/provider/profile에서의 동작은 확인하지 않았다. 이번 비교에 붙은 오프라인 재현과 PR CI도 이를 대신하지 않는다. 선택 시험의 개수 차이로 A/B의 신뢰도를 점수화하지 않았다.

**제 최종 의견은 기존 리뷰의 도입 방향을 유지하되, 독립 리뷰가 찾은 반례를 '무엇을 확인해야 완료인가'에 반영하자는 것이다.** 기존 원장에 이미 있는 사실부터 정확히 보여 주는 변화가 지금 가장 실용적이다. 기억과 교차검토는 그 위에서 작게 측정해야 다음 투자가 타당해진다.
