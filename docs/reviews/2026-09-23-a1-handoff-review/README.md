### A1-02 · 높음 · A1이 stdin 전달 증거가 없는 답과 빈 답을 받는다

**위치:** `app/controller.py:203–234`, `core/adapters.py`의 `interpret`, `app/README.md`의 결과 수용 관문. **근거 종류: 재현 + 문서.**

문서는 `input_delivery == "complete"`를 요구하지만 코드는 `in (None, INPUT_COMPLETE)`다. 실제 bubblewrap으로 Python 가짜 CLI를 실행하면서 질문을 전혀 주지 않고 성공 JSON만 출력해도 `accepted`, `revealed`, `input_delivery=null`, `tree_confirmed_empty=true`가 됐다. 합성 출력의 빈 문자열과 공백만 있는 문자열도 수용되어 정족수에 기여했다. 결과 키: `real_bwrap.missing_stdin_accepted`, `acceptance_edges_synthetic`.

**한정:** 현재 MockExecutor가 질문을 누락한다는 발견은 아니다. 일반 `interpret()`가 stdin 없는 명령을 지원하는 것도 그 자체로 버그가 아니다. 문제는 **고정 질문을 stdin으로 전달하는 A1 경계에서 그 일반 호환성을 성공 증거로 쓰는 것**이다.

**최소 수정:** A1은 해당 시도의 저장된 실행 명세와 연결된 `complete`, 성공 판정, 전체 자손 종료, 비어 있지 않은 초안을 모두 요구한다. 향후 stdin 외 전송이 필요하면 명시적인 전송 계약·증거로 분기하고 `None`을 성공의 지름길로 쓰지 않는다. K01의 파이프 읽기 한계와는 별개의 결함이다.

### A1-03 · 높음 · 두 번째 서버 시작 실패가 첫 실행을 바꾸며, 옛 완료가 UNKNOWN을 덮는다

**위치:** `app/server.py`의 `serve`, `app/controller.py:193–235, 324–336`, `app/store.py`의 인스턴스별 잠금. **근거 종류: 재현.**

`serve()`는 포트를 bind하기 전에 Store·Controller를 만들고 복구를 수행하며 토큰 파일을 교체한다. 같은 데이터 폴더·같은 포트로 두 번째 시작을 시도하자 bind는 `OSError`로 실패했지만, 첫 실행의 RUNNING은 UNKNOWN이 되고 토큰 파일도 바뀌었다. 이후 첫 executor를 풀자 `_finish()`가 현재 상태·attempt 소유권을 검사하지 않아 UNKNOWN을 다시 ACCEPTED로 덮었다. 명단은 unknown을 남겨 전체 phase는 drafting인 불일치 상태였다. 결과 키: `failed_second_server_start`.

K20은 늦은 CLI 결과 처리가 없다는 사실을 이미 적고 있다. 그러나 이는 미래 분산 실행만의 문제가 아니라 **현재 두 번째 시작과 복구 경로에서 재현되는 결함**이다. UI에서 UNKNOWN을 확인한 뒤 늦은 결과가 오는 추가 조합은 별도 회귀 시험 대상으로 남긴다. 그 조합까지 실행했다고 주장하지 않는다.

**최소 수정:** 원장 단위 단일 controller 소유권을 복구·토큰 교체보다 먼저 확보한다. 포트만 먼저 잡는 것으로는 같은 원장·다른 포트의 이중 실행을 막지 못한다. 시도 ID와 controller 세대/소유권을 영속화하고, 완료는 기대한 RUNNING·attempt·세대에만 조건부 반영한다. 실패한 두 번째 시작은 원장과 현재 토큰을 전혀 바꾸지 않아야 한다. K20·필요한 K28 작업을 3단계에서 **실제 호출 전**으로 옮긴다.

### A1-04 · 높음 · RO 입력 하위 작업 폴더와 자동 시스템 마운트에 충돌 검사가 빠졌다

**위치:** `core/isolation.py:94–144`의 `_system_mounts()`·`plan()`. **근거 종류: 실제 bubblewrap 재현.**

첫째, RO 입력이 `/tmp/.../input`, 작업 폴더가 그 아래 `/tmp/.../input/work`이면 계획이 통과한다. 마지막 work RW bind가 RO의 일부를 다시 쓰기 가능하게 만들어 **호스트 임시 입력 폴더에 marker 파일이 쓰였다**. 현재 검사는 work가 다른 마운트를 품는 방향과 같은 경로만 막는다.

둘째, `never=("/etc/hostname",)`를 선언해도 자동 `/etc` 연결이 never 검사 대상에 없어 계획이 통과하고 해당 파일을 열 수 있었다. 파일 내용은 읽어 기록하지 않고 접근 가능 여부만 확인했다. 이는 `/etc/hostname` 자체가 비밀이라는 주장이 아니라 **명시적인 never 계약이 유효한 전체 마운트에 적용되지 않는 반례**다. 기본 controller 데이터 위치가 이 경로라는 주장도 아니다.

**최소 수정:** 명시적 연결뿐 아니라 자동 시스템 연결·별도 symlink 대상까지 포함한 유효 마운트 계획을 검증한다. work와 RO 입력의 양방향 겹침은 거절한다. 단, **Codex의 RW 설정 폴더 안에 RO 실행 버전을 덮는 의도된 조합은 보존**한다. 모든 겹침을 일괄 금지하거나 두 번째 백엔드를 도입할 문제가 아니다. K14의 검사-사용 경쟁과도 별개다. WM-04를 완전히 닫았다는 판정에는 반대한다.

### A1-05 · 중간 · 마지막 초안 저장과 공개 사이의 중단을 복구하지 못한다

**위치:** `app/controller.py:225–257, 278–285, 324–336`와 초기화 경로. **근거 종류: 실패 주입 재현 + 추론.**

마지막 초안을 저장하는 transaction과 `_maybe_reveal()`의 공개 transaction이 분리돼 있다. 마지막 수동 답 저장 직후 공개 함수만 실행되지 않게 한 뒤 새 Controller를 만들고 `pump()`까지 호출해도 **모두 accepted인데 phase=drafting, note=null**이었다. 복구는 RUNNING만 처리한다. 별도로 queued 항목이 있는 원장에 새 Controller를 만들었을 때도 새 시도는 시작되지 않았다. 결과 키: `restart_after_final_draft_commit`, `restart_queued_not_pumped`.

**최소 수정:** 원장 재시작 시 영속 상태를 재조정한다. 이미 저장된 수용 초안은 외부 모델을 다시 부르지 않고 공개 관문을 재평가한다. 미시작 queued는 명시적인 재개 정책으로 시작하거나 사용자에게 재개 대기로 표시한다. RUNNING/UNKNOWN은 자동 재호출하지 않는다. 완전한 이벤트 소싱 체계보다 작은 원자적 전이 또는 멱등적인 복구 함수가 먼저다.

### A1-06 · 중간 · 축소 승인이 특정 구성에 묶이지 않는다

**위치:** `app/controller.py:237–257, 301–306`. **근거 종류: 재현 + 문서.**

축소 승인 함수는 사유·구성·현재 phase와 무관하게 boolean을 1로 만든다. 두 수동 참여자가 있고 아직 이탈이 없을 때 먼저 승인한 뒤 한 사람의 답을 제출하고 다른 사람을 이탈시키면, **새 축소 확인 없이 공개**된다. 결과 키: `approval_before_membership_loss`.

현재 화면은 통상 이 조기 승인 버튼을 보여 주지 않는다. 따라서 일반 사용자가 반드시 겪는 클릭 흐름이나 인증 우회라고 부르지 않는다. 하지만 공개를 허가하는 최종 권위는 화면이 아니라 controller이고, API로는 호출 가능하다.

**최소 수정:** 승인 대기 상태에서만 현재 requested/active/dropped 구성과 입력·phase revision에 대한 승인을 받는다. 구성 변경 시 승인을 무효화한다. 단일 사용자·한 번의 축소만 지원하더라도 조기 승인을 거절하는 시험은 필요하다.

### A1-07 · 중간 · 보고 모델 불일치를 알아도 받으며 화면에서 드러내지 않는다

**위치:** `core/adapters.py`의 Claude 결과 해석, `app/controller.py:203–234`, `app/static/index.html`의 결과 카드. **근거 종류: 재현 + 문서/정적 확인.**

요청 모델 `m`, 보고 모델 `other-model`인 합성 결과는 `model_match=false`인데도 accepted/revealed가 됐다. 화면은 요청/보고 모델과 불일치를 표시하지 않는다. K32는 Codex·agy의 보고 모델 부재만 적고 있어, **이미 관측된 불일치를 사용하지 않는 경우**가 빠졌다.

**최소 수정:** 요청 모델·보고 모델·확인 불가·불일치를 구분한다. 확실한 불일치는 수용을 보류하고 명시적인 변경 판단을 받는다. 모델 별칭은 관측된 대응 관계로 처리하고, 보고 자체가 없는 경우를 불일치로 꾸며서는 안 된다. 실제 CLI가 조용히 강등된 사건을 관측한 것은 아니며, D18의 위반 가능성을 다루는 관문 시험이다.

### A1-08 · 중간 · 수동 답 SHA 설명은 여전히 붙여넣기 오류를 과대평가한다

**위치:** `NEXT-SESSION.md:196`의 K21, `app/README.md`의 원본 앱 참여 설명, `app/controller.py:260–285`, `app/static/index.html:203–275`. **근거 종류: 문서 + 코드/추론.**

화면은 선택한 카드의 **현재 run SHA를 자동 첨부**한다. 사용자가 다른 질문에 대한 답을 그 카드에 붙여넣어도 SHA는 맞는다. 따라서 K21의 "다른 실행에 잘못 넣는 것만 막는다"는 문구는 너무 넓다. 실제로 막는 것은 **요청에 포함된 digest가 대상 run과 불일치하는 제출**, 공개 후 제출, 중복 제출, 빈 답이다. 원본 앱에 어떤 입력을 주었는지와 clipboard의 출처는 검사하지 않는다.

**최소 수정:** 위 범위로 원문 설명을 바로잡고, 복사 패킷에 run·participant·입력 digest·질문 식별자를 넣으며 제출 시 사용자 확인을 별도 상태로 저장한다. 모델이 digest를 되말하거나 사용자가 확인 버튼을 눌렀다고 실제 입력·blind 검증으로 승격하지 않는다. 원본 앱의 메모리·도구를 쓰는 참여는 사용자 요구이므로 없애지 않는다. 정족수 정책은 아래 질문 6에서 구분한다.

### A1-09 · 낮음 · AGENTS의 현재 상태 안내가 앱 존재와 종료 보장을 잘못 설명한다

**위치:** `AGENTS.md`의 Project rules 중 core 설명. **근거 종류: 문서 + 코드.**

"There is no controller or app yet"는 현재 `app/`와 맞지 않는다. runner가 일반적으로 process tree 종료를 확인한다고만 쓴 문장도 `unit_confirmed_empty`와 `tree_confirmed_empty`, POSIX 한계를 지운다. 이번 PR에서는 이 **명백한 사실 문구만 원본에서 정정**한다. 제품 실행 코드와 과거 리뷰 원문은 바꾸지 않는다.

### 2. WM 반영의 정확성 — 부분 동의

| 발견 | 이번 판단 |

### 3. A1 수용 관문·공개 규칙 — 현재의 완전 충족 주장에는 반대

정상 흐름에서 성공/전체 자손 종료를 확인하고, UNKNOWN의 자리를 점유시키며 자동 재호출을 막고, 사용자 확인으로 자리만 풀어 이미 쓴 호출은 환급하지 않는 구현은 맞다. 구성 축소와 정족수 미달도 정상 시험에 있다. 그러나 A1-02·03·05·06 때문에 문서에 적힌 경계 전체가 성립하지 않는다.

D11은 A1-01과 수동 독립성 표시 문제, D18은 A1-06·07과 관련된다. D13의 호출 상한은 **현재 실행별 CLI 시작 횟수**로는 존재하지만 세션 전체 상한·CLI 내부 추가 호출·정확한 구독 소비량까지 보장하지 않는다(K23). 이 제한을 유지한 채 작은 관측을 할 수는 있어도, 일반 협업 엔진의 예산 집행이 완성됐다고 쓰면 안 된다.

### 4. 봉인 투영 — 반대

초안 본문·길이·초안 digest와 토큰·실행 시간은 직접 내보내지 않는다. 사건 목록도 현재는 kind 문자열뿐이며 payload와 사건 시각을 붙이지 않는다. 이 부분은 적절하다. 반면 자유 텍스트 진단은 실제 누출 경로다(A1-01).

상태 변화를 반복 조회하면 대략적인 완료 시각을 알 수 있다. 이는 정확한 duration 필드를 지웠다고 사라지지 않는다. Ledger가 허용하는 준비/완료 상태 표시와 엄격한 무정보 봉인은 같은 것이 아니다. 운영자용 거친 상태는 허용한다는 계약을 명시하고, **논의자에게 다른 참여자의 상태·진단 조회 권한을 주지 않는다**. 완료 시간을 맞추려고 모델을 추가 호출하거나 모든 동작을 인위적으로 지연시키는 방식은 우선하지 않는다.

### 5. 제어 API 보안 — 부분 동의

fragment로 초기 토큰을 받고 history에서 제거하며 sessionStorage에 저장하는 흐름, 허용 Host 확인, 읽기 API에도 Bearer 토큰 요구, HTML에 토큰을 넣지 않는 구성은 확인했다. 화면은 텍스트 노드를 써서 답을 표시한다. 기본 경로에서 토큰 없는 `/api/state`는 401이었다.

외부 Origin을 붙인 일반 HTTP 요청도 올바른 토큰이 있으면 200이었다. **이것만으로 CSRF 취약점이라고 판정하지 않는다.** 실제 브라우저의 교차 출처 요청, preflight, 토큰 탈취까지 재현하지 않았고 응답에는 CORS 허용 헤더가 없었다. 방어를 단순하게 유지하려면 쓰기 요청의 Origin 허용 목록·명시적 콘텐츠 타입·프레임 삽입 정책·요청 크기/읽기 시간 제한을 추가하고, 브라우저 음성 시험으로 확인한다. Origin은 인증 대체 수단이 아니다.

먼저 고칠 것은 A1-03의 시작 소유권이다. 추가로 데이터 폴더 0700, 토큰 파일의 생성 시점부터 0600, 원자적 교체, 비밀 원문이 없는 로그 정책을 권한다. 현재 chmod 뒤 최종 권한만으로 파일 생성 중간의 모든 노출을 증명하지 않는다. 실제 토큰 탈취 사건을 관측한 것은 아니다.

네트워크를 공유하므로 참여자는 controller 포트와 다른 localhost 서비스에 닿을 수 있다. controller 폴더·토큰을 마운트하지 않는 것과 모든 로컬 서비스를 보호하는 것은 다르다(K08). 같은 사용자·root·호스트 서비스까지 이 격리의 적대자로 간주하지 않는 신뢰 범위를 운영 전에 명시한다.

### 6. 수동 원본 앱 참여 — 부분 동의, Q6의 최종 정책은 사용자 결정

원본 앱 참여를 없애지 않는다. 수동 붙여넣기는 좁고 이해하기 쉬운 첫 경로이며 자동 재시도·자동 과금을 만들지 않는다. 입력 패킷·제출 확인·출처 기록을 보강하되, K21의 검증 범위를 정확히 낮춰야 한다.

**완료된 참여자 수와 독립성이 확인된 참여자 수를 분리**하는 것을 권한다. 엄격한 blind 비교는 독립성 조건을 충족한 집합으로 정족수를 계산하고, 원본 앱 결과는 별도 보조 근거로 함께 보여 준다. 미확인 참여까지 정족수에 넣는 모드도 사용자가 선택할 수 있지만, 그 결과를 "독립 정족수 충족"으로 표시하지 않고 해당 정책을 run에 고정한다. 특정 provider가 아니라 실행 방식·관측 상태가 기준이다. 사용자 확인만으로 verified를 부여하지 않는다.

Q5의 "당장은 화면 자동화 대신 공식 통로를 관측"하는 권고에는 동의한다. 다만 CLI/app-server를 연결한다고 원본 소비자 앱의 메모리·컴퓨터 사용·세션 기능을 그대로 가져온다고 가정해서는 안 된다. 기능·세션 연속성·로그인·허용 범위가 실제 요구를 충족하는지 별도 확인한다. 이 리뷰는 각 서비스의 최신 약관 허용 여부나 미관측 통로의 작동을 판정하지 않는다.

### 7. 다음 계획의 순서와 범위 — 부분 동의

N1–N6와 한 번씩 읽는 소수 관측은 방향이 맞다. 다만 다음 순서로 고친다.

1. **N0: 모델 없는 관문 보강.** A1-01–07의 실패 사례를 제품 회귀 시험으로 만들고, 단일 원장 소유권·시도 조건부 완료·재시작 재조정·유효 마운트 검사를 닫는다. K20과 필요한 스키마 버전 작업(K28)은 여기로 옮긴다. A1-08 문구와 수동 확인도 정리한다.
2. **N1–N4: 하나의 실제 실행 경로.** CliExecutor를 관측 도구가 재사용한다. 명세는 `ExecutionSpec.record()`로 저장하고 질문·원문 argv는 일반 실행 로그에 넣지 않는다. 새 profile에서 auth/transport/permission/context 관측을 분리하고 실행 직전 허가를 계산한다. 인증 폴더 범위와 `never`를 실제 호출 전에 확정한다.
3. **N5–N6: 해석 가능한 화면.** Q6 정책·수동 출처·모델 일치 상태를 구분하고 알려진 대비 오류를 고친다. 디자인 토큰 변경은 발행본과 함께 한다.
4. **2단계: 승인된 WSL 소수 관측.** "Claude 3회 안팎, Codex 2회 안팎"은 계획 추정치다. 승인 시에는 provider별 최대 시작 횟수·실패 포함 상한·timeout·중단 조건을 고정한다. tier 2/B1/B2를 같은 관측으로 함께 확인할 수 있으면 중복 호출을 피한다. 새 호출은 앞 결과를 읽은 후 결정하고, 막힌 경로를 우회하지 않는다.

그 뒤 합성·결정 카드·Q4·B3로 간다. B3는 직접 앱/single/cross_check를 비교하되 토큰을 구독 한도나 비용으로 등치하지 않는다. 모델·입력·기기·동시 사용·시간대·quota 관측 범위를 함께 기록한다. 이번 단계에서 전체 이벤트 플랫폼, 제2 격리 백엔드, MCP 자동화, 장기 기억을 동시에 도입할 이유는 없다.

### 8. 인계가 새 세션의 출발점으로 충분한가 — 부분 동의

현재 판은 보관본의 상충하는 "앱이 없다" 문장을 줄였고, 관측과 상태·계획·한계를 찾아가기 쉬워졌다. 보관본의 A2 결과 폴더·A6 공통 자료는 3단계에, A5 manifest는 N4에, stdin/거절 관측은 N1·B1·B2에, Codex 지시문·읽기 경계·agy 출력 함정은 K38–40에 남아 있다. 원본 앱 참여(사용자 확정 17), WSL·bubblewrap 선택도 보존돼 있다. 새 큰 인계 문서를 만들 필요는 없다.

다만 **코드를 수정하기에는 충분하지만 실제 호출 허가 체크리스트로는 부족**하다. K20의 순서, gate를 "그대로" 쓰라는 N1, 수동 SHA 표현, AGENTS 현재 상태를 고친다. 보관본 A1의 안전한 실행 명세 기록 규칙은 현재에도 있으나 N1의 완료 조건으로 구체화하고, 시도·입력·정책 binding 및 복구 시험과 연결한다. 각 관측의 종료 조건·남길 증거·실패 시 중단을 짧게 명시하면 된다. 과거 버전의 긴 경위를 다시 복사할 필요는 없다.

## 간결성·책임 분리 평가

**전체 재작성은 권하지 않는다.** runner는 한 프로세스 실행, adapters는 명세·해석, isolation은 경계, membership은 순수 구성 판단, controller는 최종 전이, store는 영속화, server는 전달을 맡는 구조가 적절하다. 작은 SQLite와 표준 라이브러리 기반 앱은 모의 단계에 맞는다. 지금 HTML/JS라는 사실 자체는 결함이 아니며 TypeScript 전환은 Q3로 남긴다.

현재의 위험은 파일 수보다 **관문의 조건과 상태의 중복 표현**이다. participant 상태·roster unknown·draft 존재·승인 boolean이 서로 다른 시점에 갱신되고, 화면의 숨김 필드와 API의 숨김 필드가 별도로 늘어날 수 있다. 이를 하나의 공개 투영 함수, 하나의 조건부 결과 전이, 하나의 재시작 재조정으로 모은다. 불투명한 범용 workflow 엔진이나 플러그인 계층을 추가하지 않는다.

`tools/review_boundary.py`의 연구용 순수 함수와 실제 controller를 같은 상태 권위로 쓰지 않는 현재 방향을 유지한다. 시험은 계속 보존하되 실제 핵심 경계 시험을 우선한다. N2가 N1을 복제하지 않고 호출하게 하고, 런타임 수치·기록을 여러 살아 있는 문서에 재기입하지 않는다. 이 리뷰의 재현 스크립트는 고정 커밋용 증거이므로 실행 제품이나 영구 CI 통과 조건으로 편입하지 않는다.
