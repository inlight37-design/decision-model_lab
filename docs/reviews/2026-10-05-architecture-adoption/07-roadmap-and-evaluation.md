## 2. GR-1에서 꼭 함께 완성할 연결

기존 설계는 주요 경계를 충분히 적었다. 다시 큰 설계 문서를 쓰는 것보다 다음의 사용 흐름을 실제로 연결하는 편이 가치가 크다.

1. 일반 결과가 모두 정리됐는지, 검토할 수용 CLI 작성자가 충분한지 판단한다.
2. 전체 목표와 각 팀원의 과제·답·자료 이름/hash·미검토 범위를 고정한다. 일반 분담을 같은 문제의 독립 답변으로 설명하지 않는다.
3. 화면 미리보기의 round ID·결과 판·입력 hash와 실제 생성 시점이 같은지 다시 검사한다. 재전송은 새 라운드를 만들지 않고 기존 요청을 찾게 한다.
4. 기존 REVIEW_SEAT·InvocationLedger·ExecutionCoordinator로 한 명씩 부른다. 앞 호출이 실패하면 나머지 미시작 이유를 남긴다.
5. 결과는 일반 `collected` 실행에 제공하되 독립 정족수·격리 합성 자격은 새로 주지 않는다.
6. GR-1은 일반 검토의 진행·unknown을 목록·상세·내 차례·선행 준비·사람 판단에 연결하고 기존 격리 수정/재검토를 유지한다. GR-2에서 일반 수정/재검토에 같은 계약을 적용한다.
7. 사람이 지적을 수용·반박·보류하고 현재 결과 판을 판단한다. 인용 일치와 판단 완료를 사실 검증으로 바꾸지 않는다.

수정은 그 다음의 별도 명령이다. 첫 라운드의 결과가 충분하면 거기서 끝낼 수 있어야 한다. 모든 팀원에게 최대 상한까지 수정/재검토를 자동 실행하는 루프는 기본값으로 넣지 않는다.

## 3. 검토 비용을 행동 단위로 보여 준다

기존 GR 설계의 정의를 그대로 쓴다. `n`은 검토 가능한 작성자 수, `r`은 수정할 작성자 수, `v`는 작성자당 수정 시도 상한, `c`는 수정 판당 재검토 상한, `k`는 선택적 취합 호출 수다.

**첫 답 작성 이후 추가 호출의 구조상 상한은 `n + r × v × (1 + c) + k`다.** 실패·거절된 실제 시작도 예산을 사용하며, preview의 예상량은 예산 예약이나 실행 보장이 아니다. [기존 비용 정의](../../architecture/general-team-review/README.md#5-호출-비용과-도입-판단)

| 두 작성자의 예 | 이번 단계 호출 | 첫 답부터의 누적 호출 | 사용자가 판단할 것 |
|---|---:|---:|---|
| 최초 분담 답 | 2 | 2 | 단독 답으로 충분한가 |
| 교차검토 한 라운드 | 2 | 4 | 지적이 실제 오류·누락인가 |
| 한 작성자 수정 | 1 | 5 | 바꿀 답과 반영할 지적을 골랐는가 |
| 다른 작성자 재검토 | 1 | 6 | 수정 근거가 맞고 중요한 반례가 남았는가 |
| 선택적 취합 | 1 | 7 | 이미 읽을 수 있는 결과를 다시 모을 가치가 있는가 |

이 표는 성공한 각 단계를 한 번씩 수행한 **예시 계산**이며 실제 측정 비용이 아니다. 다듬기·분담 제안·다음 단계·재시도·새 요약은 제외했다. 한 provider에 상위 역할이 몰리면 전체 합계보다 provider별 상한에 먼저 닿는다. 기본 런처의 각 provider 5회와 모든 수정/재검토 상한을 끝까지 쓰는 경로는 양립하지 않을 수 있다. 상한을 자동으로 올려 해결하지 않는다. [현재 기본 cap](https://github.com/inlight37-design/decision-model_lab/blob/48ab4bd6f0e297587707aecb83ebc0cd9968892f/app/launch.py#L58-L60)

또한 검토 호출은 작성자 수 `n`에 비례하지만 각자 다른 답을 읽는 입력량은 답 길이가 같을 때 대략 `n(n−1)`에 비례한다. 호출 수만 적다고 구독 사용량이 작아지는 것은 아니다. 화면에는 이번 동작의 추가 시작 수·입력 bytes·provider별 남은 횟수를 표시하고, 토큰/구독 차감량이 미확인인 부분은 미확인으로 남긴다.

## 4. 효과 평가는 세 가지로 나눈다

### 4.1 실행 계약의 정확성

이 단계는 모델 없이 한다. 같은 ID의 중복 요청, 마지막 예산 경쟁, cap 없는 REAL 통합, 입력/답/hash 변경, unknown, 결과 저장 실패, 새 결과 뒤 과거 판단, 원장 교체와 응답 유실을 재현한다. 기대 결과는 ‘거절해야 할 요청이 예약·호출되지 않음’, ‘불명확함을 성공으로 바꾸지 않음’, ‘기존 소비/초안/판을 잃지 않음’이다.

새 GR/취합 경로는 정상 fixture만 보지 말고 잘못된 대상·다른 자료 범위·빠진 작성자·자기 검토·새 판·동일 round 재전송을 함께 확인한다. 전체 suite의 녹색과 실제 결함을 겨냥한 재현은 다른 증거다. 이번에 일부 경계는 기존 회귀가 통과하는 상태에서도 재현됐다.

### 4.2 사용자 흐름과 성능

평가할 사용 장면을 구체적으로 정한다: 한도에 닿은 다음날 같은 작업을 다시 열기, 브라우저를 닫은 뒤 다듬기 재선택, 오래된 반례 찾기, 새 수정 뒤 판단 표시 확인, 늦은 검토 하나만 취소하기다. 사용자가 어디서 다시 모델을 부르게 되는지와 원래 결과를 찾는 데 걸린 시간을 본다.

기존 `benchmark_queries.py`와 `evaluate_memory.py`를 재사용한다. 차가운 조회와 반복 조회, 응답 bytes와 생성 시간, 조회 비용과 원문을 찾은 정확도를 구별한다. `/browse`의 큰 미연결 준비 payload는 이번 합성 재현으로 확인했으므로 목록/상세 분리의 구체적인 비교 대상이다. 실제 PC 지연을 합성 컨테이너 시간으로 대신하지 않는다. [WF-03 재현](04-workflow-and-ui.md#wf-03-목록-페이지를-작게-해도-미연결-준비-전문은-계속-전송된다)

### 4.3 모델 품질과 구독 효율

품질 비교는 다음 대조군을 둔다. 아래는 실험 설계이며 이번 세션에서 호출하지 않았다.

| 대조군 | 목적 | 비교에서 보존할 것 |
|---|---|---|
| 강한 단독 모델 1회 | 협업 없이 얻는 기준 품질·지연 | 같은 목표·자료·완료 기준 |
| 같은 호출 예산의 단독 모델 + 자기검토 | 추가 계산 자체의 효과와 여러 모델 효과 구분 | 총 시작 수와 입력/출력 사용량 기록 |
| 독립 초안만 비교 | 독립 해법과 반례의 기여 | 초안 봉인과 독립성 등급 |
| 일반 분담 + 취합 | 과제를 나누는 효용 | 작성자별 과제/자료 범위, 취합 손실 |
| 일반 분담 + 검토 | 충돌/누락 발견의 효용 | 올바른 지적과 틀린 지적, 범위 차이의 오인 |
| 검토 + 선택 수정/재검토 | 최종 오류 감소와 추가 비용 | 원래 정답 훼손·반례 소실·판 선택 이력 |

과제군은 서로 섞어 평균 하나로 만들지 않는다. 예를 들어 정답/근거가 있는 코드 경계 문제, 자료 간 요구사항 충돌, 개방형 설계 비교를 나눈다. 이미 본 fixture만 반복해 ‘일반 품질’을 주장하지 않고, 고정한 평가 기준과 아직 보지 않은 과제를 구분한다.

측정할 핵심은 정답/완료 기준 충족, 근거 없는 주장, 올바른 지적/오지적, 수정 후 새 오류, 미해결 반례 보존, 사람 검토 시간, 시작/실패 수, 실제 보고 usage, 전체 지연이다. 모델 간 일치율이나 지적 개수를 단독 품질 점수로 쓰지 않는다. 비용 분모는 객관적인 기준을 충족한 결과로 정하고, 단순히 사람이 버튼을 눌렀다는 이유만으로 성공한 결과라고 세지 않는다.

추가 검토가 새로운 유효 정보를 주지 않거나, 원래 옳은 답을 나쁘게 바꾸거나, 사람이 읽는 부담을 줄이지 못하면 그 과제군에서는 단독/독립 초안까지만 쓰도록 한다. 성공률 몇 퍼센트 개선 같은 기대치를 사전에 발명하지 않는다.

## 6. 개발 세션의 작업 방식

현재 GitHub 카드·작은 브랜치·중간 커밋·PR CI·인계 규칙을 유지한다. 이 검토 때문에 새 외부 작업 서버나 매번 모델이 요약하는 상태 봇을 추가하지 않는다. 한 구현 PR은 한 사용자 흐름이나 한 무결성 수정으로 끝내고, 다음 세션은 이번 분석 전체 대신 해당 항목과 실제 함수부터 읽는다.

구현 보고는 ‘무엇을 바꾸었나, 어떤 기존 의미가 유지되나, 어떤 반례를 확인했나, 무엇이 아직 관측되지 않았나’를 담으면 된다. 검토 대상 SHA·원본 답/자료 판·요청 모델과 실제 보고 모델의 차이를 기록한다. 다른 AI의 찬성 수를 승인 근거로 삼지 않는다.

이번 분석에서 전체 로컬 시험 수집은 bubblewrap 환경 probe가 반환하지 않아 중단된 경로가 있었다. probe 자체에도 timeout과 실패/skip 사유를 두는 작은 시험 도구 개선은 실제로 관측된 불편에 근거한다. 해당 실패를 피하려고 제품 수용 조건이나 CI 격리 gate를 약화하지 않는다. 최종 검증 기록은 이 검토의 검증 문서와 PR에 별도로 남긴다.
