# 아키텍처·파이프라인·워크플로우와 외부 기능 이식 심층 검토

## 1. 결론

**현재 Python·SQLite 중심 구조와 공식 구독 CLI 실행 경계를 유지한다. 다음 투자 대상은 새 오케스트레이터가 아니라, 이미 있는 실행·검토·기억·작업 흐름 사이에서 의미가 끊기는 경계다.** 현재는 controller의 서비스를 분리했고, HTTP와 헤드리스 배선을 공유하며, 입력 고정·일회 승인·호출 예약·종료 미확인 보유·공개 조회·검색·페이지화·계획·수정 판을 갖췄다. 모듈 분리나 예산 원장이 없는 초기 프로젝트로 보고 설계를 다시 시작하면 중복 구현이 된다. [현재 구조 분석](01-architecture.md), [실행 근거](02-runtime.md), [기능별 코드 대조](08-capability-matrix.md)

가장 큰 구조적 불일치는 **작업과 지식은 오래 이어져야 하는데, 그것을 담은 저장소가 짧은 호출 예산 원장과 함께 교체된다는 점**이다. 가장 먼저 고칠 좁은 데이터 계약은 **저장한 답을 다시 쓸 때의 본문·hash 검증, 판단 메모가 적용된 결과 판, 최종 취합에 넣을 답 판 선택**이다. 사용자가 바로 느끼는 흐름에서는 **이미 완료한 다듬기·분담 결과로 돌아오는 입구**가 중요하다. 이들은 새 프레임워크 없이 현 서비스 안에서 단계적으로 풀 수 있다. [원장·복귀 분석](04-workflow-and-ui.md), [결과·기억 분석](03-context-and-results.md)

기존 다음 작업인 **GR-1 일반 팀원 검토 → GR-2 작성자 수정·다른 작성자 재검토 → GR-3 선택한 판 취합**은 유지한다. 작은 무결성·기억 의미 보완을 함께 처리하되 원장 전면 이전, 그래프 DB, 범용 스킬 런타임을 선행 조건으로 만들지 않는다. 외부 기능은 이 경로를 완성하는 데 필요한 부분부터 이식한다. [기존 GR 설계](../../architecture/general-team-review/README.md), [권고 구현 순서](07-roadmap-and-evaluation.md)

이 결과물은 **분석·설계 권고 문서**다. 제품 코드나 관측 정책을 바꾸지 않았고, 모든 권고에 대한 착수 결정이나 효과 검증을 대신하지 않는다. 기존 날짜 기록은 보존하고 현재 안내의 과도한 한도 설명만 정정한다. 실제 검증 범위는 [09-validation.md](09-validation.md)에 있다.

## 3. 현재 아키텍처의 평가

### 유지할 기반

| 현재 자산 | 평가와 유지 이유 | 다음 보완 경계 |
|---|---|---|
| controller façade와 입력·실행·계획·검토·합성·조회 서비스 | 현재 크기에서 책임을 추적할 수 있다. 새 distributed runtime의 필요가 확인되지 않았다. | 공유해야 할 무결성·관측 규칙을 한 계약으로 묶는다. |
| SQLite 원장과 소유 잠금, invocation·사건 이력 | 누가 무엇을 승인하고 얼마나 호출했는지 복구할 근거가 있다. | 장기 작업 식별자와 예산 원장의 수명을 구별한다. |
| 고정 입력·자료 hash·일회 승인·CAS | 준비 후 변경·중복 시작을 막는 방어가 있다. | 모든 답 소비 경로가 같은 무결성 검사를 사용해야 한다. |
| shell-free native runner와 별도 수용 판단 | exit 0이나 답 문자열만으로 완료를 인정하지 않는다. 입력 전달·전체 자손 종료·계획 관측을 함께 본다. | terminal 사건과 답의 관계, 직접 통합의 예산 결속, 원장 교체 시 unknown을 보완한다. |
| 공개 projection·검색·페이지·계산형 수신함 | 별도 검색 DB와 작업판 없이 현재 원장으로 흐름을 표현한다. | 목록에 계속 실리는 준비 전문을 상세 조회로 나누고 복귀 입구를 만든다. |
| 원본·수정 판·지적·재검토·사람 판단 | 과거 판을 덮어쓰지 않고 비교할 토대가 있다. | 선택한 답 판·판단 적용 판을 다음 기억과 최종 취합까지 연결한다. |

위 평가는 코드의 존재와 책임 구조에 대한 것이다. 실제 모델 품질, 현재 계정 사용 가능성, 사용자 PC 성능이 검증됐다는 뜻은 아니다. 각 행의 고정 SHA 근거와 실제 호출 흐름은 [01](01-architecture.md)·[02](02-runtime.md)·[03](03-context-and-results.md)·[04](04-workflow-and-ui.md)에 연결했다.

### 가장 중요한 세 경계

**작업 수명과 예산 수명.** launcher는 기본 provider별 예산에 여유가 있는 원장을 이어 쓰며, 한 provider가 소진되면 다음 앱 시작 때 새 원장을 고른다. 작업·계획·템플릿·기억·검색이 현재 Store에 묶여 있어 이전 작업이 기본 화면에서 이어지지 않는다. 이전 DB 삭제나 원장 상한 초과를 확인한 것이 아니다. 먼저 이전 원장의 읽기 전용 선택·명시적 인계 입력·미해결 실행 확인을 제공하고, 반복 사용에서 필요가 확인되면 장기 작업과 예산 구간을 분리한다. [WF-01·RT-02](04-workflow-and-ui.md)

**결과의 판과 판단의 판.** 원래 답, 수정 답, 검토 대상, 사람의 판단, 합성 입력은 서로 다른 객체다. 최신 수정이 생겼다는 이유만으로 그것이 승인된 최종 답은 아니다. 작성자별로 사용할 원본/수정 판과 hash, 관련 지적·재검토·미해결을 명시한 선택 묶음을 두고, GR-3을 시작으로 합성·다음 단계·보고에서 같은 의미를 사용한다. 자동으로 최신 답을 고르는 정책은 피한다. [CR-02·03](03-context-and-results.md)

**기억의 검색과 실제 전달.** 관련 이력을 찾는 것, 그중 어떤 구간을 발췌하는 것, 프롬프트에 고정하는 것, 원자료가 현재도 같은지 확인하는 것은 별개다. 현재 구현은 출처·선택 이유·고정 사본을 갖고 있다. 후속은 수정/재검토까지 검색 대상에 포함하고, 질의에 맞은 구간이 입력에 실리는지, 과거 판단이 어느 판에 적용됐는지 명료하게 하는 것이다. [CR-04](03-context-and-results.md), [M01–M05](05-memory-adoption.md)

## 4. 확인한 문제와 우선순위

P1은 확장 전에 맞추거나 일상 사용의 연속성에 우선 대응할 항목, P2는 그다음의 정확성·사용성 보완, P3는 추가 측정 후 결정할 항목이다. 외부 공격 가능성이나 실제 장애 빈도의 등급이 아니다. 아래는 서로 관련된 상세 지적을 묶은 목록이다.

| 우선 | 항목 | 확인한 사실과 적용 범위 | 최소 개선안 |
|---|---|---|---|
| P1 | 답 소비의 hash 검사 — CR-01 | 임시 DB에서 저장된 답 본문만 바꾸자 보고서는 거절했지만 교차검토·취합은 그 본문을 사용했다. 정상 UI의 변조 경로를 주장하는 것이 아니라 저장 무결성 경계의 재현이다. | 호출 예약 전에 원본 답을 읽는 공통 검사기를 적용하고 기존 보고서 검사와 일치시킨다. |
| P1 | 기억 속 과거 판단 — CR-02 | 새 수정 판 뒤 공개 화면은 미검토로 돌아가지만, 새 기억에는 과거 판단 메모의 적용 판이 구분되지 않은 채 남는다. | 판단 당시 결과 판·현재 판·과거 판단 표지를 기억 항목에 함께 보존한다. |
| P1 | 원장 교체와 작업 복귀 — WF-01·RT-02 | 한 provider의 예산 소진 뒤 다음 앱 시작 때 새 Store를 선택한다. 이전 작업과 unknown 점유는 자동으로 이어지지 않는다. 기존 파일 삭제나 실제 고아 프로세스 생존은 확인하지 않았다. | 이전 원장 조회·인계 입력·알려진 미해결 원장 확인을 연결한다. 상한 증가로 문제를 가리지 않는다. |
| P1 | 완료한 준비 결과로 돌아가기 — WF-02 | 다듬기·분담 결과는 저장돼도 폼 상태를 잃은 뒤 완료 결과를 다시 고를 입구가 부족하다. | 기존 ID로 고르는 준비 목록·상세와 재개 경로를 만들고 이전 승인을 재사용하지 않는다. |
| P1, 직접 통합 시 | REAL 호출 예산 결속 — RT-01 | 정상 HTTP/헤드리스 배선은 상한을 검증한다. 그러나 빈 신규 원장의 직접 Controller 생성·호환 setter는 합성 REAL-tag 재현에서 저장 cap과 runtime cap을 어긋나게 한다. | native 호출의 최종 예약 경계에 불변 예산 결속을 둔다. 기존 cap 미지정 재개는 저장된 cap 상속을 유지한다. |
| P2 | 수정 내용 검색 — CR-04·M01 | 수정 답에만 있는 용어는 기억 순위 계산에서 누락돼 무관한 최근 이력이 선택될 수 있다. 공개 UI 검색에는 수정/재검토가 이미 포함된다. | 두 검색 경로의 범위를 맞추고 수정 내용 질의와 발췌를 기존 평가셋에 더한다. |
| P2 | 상위 역할의 Claude 한도 관측 — RT-03 | parser가 읽은 한도 정보가 공통 상위 호출 정착 단계에서 저장되지 않고 계정 조회도 해당 사건을 읽지 않는다. | 허용된 한도 필드만 정규화해 저장·공개한다. 상태 표시용 추가 모델 호출은 필요 없다. |
| P2 | Codex terminal 스트림 — RT-04 | 합성 사건열에서 완료 뒤 새 답이 와도 앞 완료가 뒤 답까지 수용시킨다. 실제 native 스트림의 발생 여부는 미확인이다. | 답과 terminal의 순서 계약을 작은 fixture로 고정한다. 정상 확장 사건은 별도로 구별한다. |
| P2 | 준비 전문의 목록 포함 — WF-03 | limit 1 조회에도 미연결 준비 전문이 모두 실린다. 합성 5건은 약 243 KB, 20건은 약 971 KB였다. 반복 조회 cache는 작동하지만 응답 크기는 같다. | 준비 요약 목록과 선택 상세를 분리한다. 20건은 기본 상한을 넘는 부하 fixture임을 유지한다. |
| P2/P3 | 합성 수명·역할별 취소·lock — RT-05/06/07 | 합성은 이미 회계에 포함된다. 저장 형태·개별 취소·관측에는 다른 호출과 차이가 있고 큰 이력의 lock 영향은 미측정이다. | 공통 관측/복구 계약부터 맞추고 lock 변경은 측정 후 결정한다. |

각 재현의 입력·출력·코드 줄·과장하면 안 되는 범위는 [02](02-runtime.md)·[03](03-context-and-results.md)·[04](04-workflow-and-ui.md)에 있다. 일반 팀원 검토/수정/선택 판 취합의 미구현은 이미 알려진 다음 범위이므로 새로 발견한 버그로 세지 않았다.

## 5. 외부 프로젝트 기능은 어디까지 이식할 것인가

## 6. 구현 순서와 비용 판단

**첫 흐름은 작은 계약 보완과 GR-1을 병행하는 것이다.** 답 소비 hash 검사와 기억의 판단 판 표시는 담당 범위가 좁다. GR-1은 미리보기→입력 고정→호출 예약→교차검토→일반 공개 조회→상태→사람 판단까지 연결한다. 이후 GR-2에서 자기 배정 자료로 수정하고, GR-3에서 어떤 판을 취합할지 고른다. 이 흐름의 완료 조건과 후속 파일은 [07](07-roadmap-and-evaluation.md)에 정리했다.

**두 번째 흐름은 일상 사용의 연속성을 회복하는 것이다.** 원장 선택/복귀와 준비 결과 목록을 연결하고, 목록 전문을 상세 조회로 분리한다. 이후 실제 사용 기록에서 검색 실패를 모아 기억 평가를 확장한다. 수정 용어 검색처럼 이미 재현한 누락은 좁은 회귀로 보완하고, 벡터·그래프·광범위한 ranking 변경은 측정이 필요한 선택지로 남긴다.

검토는 호출 비용을 늘린다. 작성자 2명이라면 초안 2회, 서로 검토 2회, 한 명 수정 1회, 다른 작성자 재검토 1회, 취합 1회로 **합계 7회**가 된다. 준비·실패·추가 검토는 별도이며 provider별 배정에 따라 한 provider의 기본 5회 상한에 먼저 닿을 수 있다. 단순 호출 수와 실제 token·대기·계정 창 사용량을 따로 표시해야 한다. 예산 부족을 자동 상향으로 해결하지 않는다. 기존 GR 공식과 여러 단계의 비용·중단 조건은 [07 §3](07-roadmap-and-evaluation.md#3-검토-비용을-행동-단위로-보여-준다)에 있다.

효과는 동일 과제에서 강한 단독 모델, 같은 호출 예산의 자기 검토, 독립 초안, 일반 검토, 수정/재검토/선택 판 취합을 비교해야 한다. 정답·근거 보존·잘못된 지적·새 오류·사람의 수정 시간·실패를 포함한 전체 소비를 함께 본다. 다수결, 답 길이, 합성자의 자신감만으로 품질 향상을 판정하지 않는다. 이번 세션은 이 평가 설계까지만 했으며 실제 모델 품질 실험은 수행하지 않았다. [07 §4](07-roadmap-and-evaluation.md#4-효과-평가는-세-가지로-나눈다)

## 7. 검증과 보존

웹 컨테이너에서 임시 SQLite와 합성 executor로 핵심 반례를 재현했고, 관련 기존 회귀와 문서·설계·근거 원장 검사를 실행했다. 전체 로컬 suite는 수집 단계 대기로 완료하지 못했고, 별도의 부분 실행에서 bubblewrap capability probe 대기 stack을 확인했다. 완료한 검사와 미완료 검사를 섞어 전부 녹색으로 표시하지 않았다. 최종 원격 CI 결과는 [PR #184 Checks](https://github.com/inlight37-design/decision-model_lab/pull/184/checks)가 기준이다. [검증 상세](09-validation.md)

실제 구독 CLI 호출, 사용자 PC·계정·브라우저 접근, 실사용 원장의 성능 관측, 외부 runtime 설치/실행은 하지 않았다. 과거 사용자 PC 관측은 각 날짜의 증거로 남긴다. 중간 결과는 같은 검토 브랜치에 여러 차례 원격 커밋했으며, PR은 main과 분리해 남긴다. 다음 구현의 기준은 현재 인계와 기존 GR 설계이며 이 보고서는 그 판단 근거로 사용한다.
