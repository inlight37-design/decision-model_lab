## 관측과 변경

클라우드 Linux, Python 3.12.14, 임시 SQLite, 수동 참여자의 합성 공개 답·자료·작업을 사용했다. 모델/실제 CLI 호출은 없고 사용자 PC는 접근하지 않았다. `python tools/benchmark_queries.py --runs 100 1000`을 변경 전후에 각각 실행했다. 시간은 응답 JSON 직렬화 포함 3회 중앙값, 메모리는 별도 tracemalloc 측정(SQL trace 목록 포함)의 Python peak다. OS RSS나 실사용 PC 부하가 아니다. [이전 값](before.json)과 [변경 후 값](after.json)을 보존한다.

| 1,000 실행 | 이전 | 변경 후 |
|---|---:|---:|
| 화면 목록/상세 갱신 | 전체 255.50 ms / 25,656,621 bytes | 선택 없음 91.29 ms / 519,752 bytes |
| 특정 작업 검색 | 151.52 ms / SQL 12,031 | 2.13 ms / SQL 142 |

이전 화면은 매번 모든 답·보낸 입력·자료 메타데이터를 읽고 보냈다. 새 overview는 상태·호출·사용량으로 작업 목록을 만들고 선택한 실행만 상세로 싣는다. 상세와 목록은 같은 lock 안에서 읽는다. 사용량/상태 계산은 기존 gate·task projection을 사용하며 목록 역할 구성에서 기억 본문을 뺀다. 기존 `/api/state`와 보고서 형식은 유지한다.

검색은 작업 필터를 먼저 적용하고 공개 실행 projection을 하나씩 읽는다. 질문/자료 검색은 답을 읽지 않는다. 기존 catalog가 건수·발췌·순서를 계산하므로 봉인 결과를 별도 색인에 복사하지 않는다. 실행별 표의 조회 index는 기존 column 이전이 끝난 뒤 추가한다. schema 의미나 호출 기록을 바꾸지 않는다.

## 검증

- 기존 전체 projection과 목록의 상태·호출·usage, 선택한 상세가 일치함을 검증했다. 봉인/공개, 미확정 합성, 교차검토, 수정·재검토, 판단 완료를 포함한다.
- 검색 종류별로 기존 전체 snapshot 검색과 결과/건수/발췌를 대조했다. 작업 필터의 조기 적용과 목록에서 답·자료 본문 미조회를 확인했다.
- HTTP 인증·매개변수, 실제 JS의 응답 순서·선택 이동, Chromium의 홈→상세→빠른 이동→새 실행→모바일을 확인했다. page error와 가로 넘침이 없었다.
- 로컬 전체 suite에서 새 index를 제거하지 않고 구형 원장을 만들던 fixture와 측정 도구의 문서 연결 누락을 발견해 고쳤고 해당 검사를 재실행했다. 컨테이너의 기존 `test_children_left_behind_are_counted_and_ended` 실패(`unknown != exited`)는 그대로이며 이를 합격으로 바꾸지 않았다. PR 최신 head의 CI는 PR Checks를 기준으로 한다.

## 남은 한계와 결정

전체 본문 검색 시간은 거의 같고 여전히 선형이다. 목록도 모든 작업의 타임라인·상태를 읽으므로 아주 큰 원장에서는 페이지화/상태 집계를 추가 평가해야 한다. 사용 중인 원장을 가져오지 않았고 실제 대형 수정 이력·합성 이력 분포를 재현하지 않았다. 이번 측정으로 FTS·벡터 DB의 이익을 주장하지 않는다. 먼저 부담이 큰 전체 상세 전송과 불필요한 작업 검색을 줄였고, 다음에는 기억의 선택 누락을 별도 평가한다.
