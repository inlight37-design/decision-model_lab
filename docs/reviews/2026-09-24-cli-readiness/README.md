# 실행 계약 재검토·연결 준비 — 2026-09-24

codex 세션이 사용자 PC `aux-pc`의 Windows와 WSL2 `Ubuntu-24.04`에서 작업했다. 시작 main은 `56bf5afcce385b8bec33f118421428af99944534`(PR #30 병합)이다. **이번 작업의 모델 호출은 없다.** 이전에 소진한 호출 예산을 초기화하지 않았고 manifest·C3 정책·Q4 선택도 바꾸지 않았다.

## 결과

Claude의 순서 5 구현은 계획을 한 번 만들어 기록·실행하는 구조와 시도별 실행 종류 저장을 해결했다. 정확한 head의 push CI도 확인했다. 그러나 실행 직전 허가와 지문 정규화에서 재현되는 문제를 고쳤다. 실제 모델 서버 연결(순서 6)은 아직 완료하지 않았다. 현재 관측으로 허가된 CLI가 없기 때문이다.

| 재현한 문제 | 수정과 검증 |
|---|---|
| 계획 뒤 관측 기록을 철회해도 실행 시작 가능 | `run()`에서 같은 계획의 현재 허가를 다시 확인. 새 계획을 만들지 않음. 실제 합성 inventory 파일을 바꿔 프로세스 시작이 차단됨을 확인 |
| Codex 자료 폴더 개수가 달라도 같은 계약 판 | mount 역할 목록의 중복을 보존. 자료 하나의 기존 K46 판은 유지하고 여러 자료는 구별 |
| stdin 질문이 옵션과 같으면 실제 옵션이 질문으로 가려짐 | argv 전송에서만 질문 마스킹. 계약 지문과 `ExecutionSpec.record()`를 함께 수정; agy argv 질문 가림은 유지 |
| 저장된 실제/합성 시도도 화면 행에 “CLI 모의” 표시 | 행의 `execution`으로 종류 표시. 대기 중은 실행 전, 과거 근거 없음은 미기록으로 표시 |

재현·검토 범위와 남는 한계는 [CONTRACT.md](CONTRACT.md)에 있다. deep freeze, 동적 환경 정책 전체의 지문화, 검사와 시작 사이 OS 경로 변경 문제까지 해결했다고 주장하지 않는다.

## main 보호 — 완료

이전 Claude 세션의 권한 분류기 거절은 이번 도구에는 없었다. 사용자의 기존 권한 위임 범위에서 GitHub API로 설정한 뒤 독립 재조회했다.

- `main`은 PR을 거쳐야 하고 승인 인원은 0이다.
- `checks (3.12)`, `checks (3.13)` 필수; GitHub Actions app ID 15368에 묶었다.
- 관리자에게도 적용한다. 최신 main 재반영 강제는 끄고, force push·삭제는 허용하지 않는다.

GitHub [branch protection API](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection)의 현재 필드와 응답을 대조했다. 설정 확인이며 의도적으로 실패 PR의 병합을 시도한 것은 아니다. 사용자가 직접 설정하거나 이 권한을 다시 줄 필요는 없다.

## 모델 호출 없이 한 준비

- **서버 연결 전 조회:** `python -m app.server --check-cli <adapter> --model <전체-이름> --inventory <기록>`은 현재 계획·설치 버전·허가 거절 이유만 출력한다. 서버·원장·CLI·모델은 시작하지 않는다. bwrap 바이너리 신뢰도 파일 정보로 검사한다. 실제 namespace 가용성과 구독/모델 가용성을 이 명령이 확인하는 것은 아니다. 실제 WSL 결과는 [Claude](readiness-claude.json)·[Codex](readiness-codex.json) 모두 거절이며 판과 이유를 남겼다.
- **Claude 재관측 준비:** [계획·실측](../../experiments/w2-isolation/2026-09-24-claude-preflight/README.md). 합성 HOME에서 설치 CLI의 version/help, 기존 승인 범위에서 구독 로그인 상태만 확인했다. 현재 json 참여자 계획과 stream-json 진단은 서로 다른 판이다. `claude_preflight.py assess`는 성공한 plain 결과도 전송만 뒷받침한다고 표시한다.
- **Codex C3:** [GitHub·C3 검토](GITHUB-C3.md). 합성 HOME과 외부 통신 차단 상태에서 실제 `debug prompt-input`을 실행해 AGENTS와 skill metadata 표식을 확인했다. 추가로 app-server의 읽기 전용 목록에서 합성 MCP 도구·입력 schema와 skill metadata를 대조했다. MCP 지시문과 exec 옵션 동등성은 확인되지 않아 최종 요청 전체의 증거로 합치지 않는다. failed를 유지한다.

**Claude를 곧바로 반복 호출하면 순서 6이 풀린다는 전제는 성립하지 않았다.** 정확한 판의 1회·300초는 전송 확인에 쓸 수 있으나 현재 JSON에는 문맥·권한을 모두 판정할 증거가 없다. 별도 stream init도 전체 문맥 부재의 증거가 아니다. 지금은 무모델 증거 대조 및 관측 가능한 실행 명세 검토가 우선이고, 그런 명세가 정해진 뒤 필요한 호출 예산만 받는 것이 권고다.

## 사용자에게 남는 선택

- Q4 첫 화면은 A(결정·미해결 조건 먼저)를 권고한다. B 전환은 유지한다. 답을 받기 전에는 사용자 결정으로 기록하지 않는다.
- 독립성 기준을 완화할지는 별도 제품 결정이다. 현재는 완화하지 않고 추가 관측 경로를 조사했다. “더 돌렸으니 독립적”으로 판정하지 않는다.
- 실제 호출을 원하면 정확한 목적·명세·provider·실패 포함 횟수·timeout·중단 조건으로 정한다. 이번 준비는 그 승인을 대신하지 않는다. 유료 API로 대체하지 않는다.

원격 설정 권한이나 브라우저 연결을 새로 받을 필요는 없었다. 옛 codex 작업 폴더는 main에 포함된 clean 상태를 확인한 뒤 이번 독립 브랜치로 재사용했다. 다른 세션 작업 폴더를 지우지 않았다.

## 검증

관련 회귀는 수정 전 재현과 수정 후 성공을 확인했다. 최종 전체 검사 및 정확한 head CI 결과는 같은 폴더의 `VALIDATION.md`에 기록한다. 새 조회 명령도 현재 WSL 설치에서 직접 실행해 두 provider가 거절되는 것을 확인했다. 원래 허가가 없다는 사실을 오류를 감추거나 우회해서 바꾸지 않았다.

모의 화면의 행 표시 변경은 aux-pc의 Codex 내장 Chromium으로 임시 원장에서 직접 확인했다. 모의 CLI의 실행→공개→합성과 A/B 전환도 성공했다. AX 클릭 한 번은 도구의 shadow-root 확인 오류로 실패했고, 현재 DOM을 다시 읽은 뒤 의미 기반 버튼 클릭으로 완료했다. 시험 탭과 서버는 정리했다. 이전 Edge 취소 확인창·실제 JSON 다운로드 결과는 [Claude 기록](../2026-09-24-execution-contract/README.md)의 증거이고, 이번에 같은 끝단을 재시험했다고 쓰지 않는다. 기존 인계의 사용자 결정(2절)·금지 사항(5절)은 그대로 보존했다.
