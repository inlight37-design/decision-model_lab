# Ledger

여러 상급 모델의 독립 답변을 주장·근거 단위로 대조하고 **미해결 반례를 지우지 않는** 데스크톱 앱을 위한 디자인 시스템.

`decision-model_lab`의 제어 평면 위에 올라가는 1층(셸)을 만든다. 병렬 실행기가 아니라 판단 구조를 다루는 화면이므로, 여기의 색과 밀도는 장식이 아니라 **의미론**이다.

> 이름 `Ledger`는 자리표시자다. 제품명이 정해지면 index의 `title`만 바꾸면 된다.

---

## 하나의 규칙

**미검증이 검증처럼 보이면 안 된다.**

이 한 줄이 나머지 전부를 결정한다. 모델이 자신 있게 답했다는 사실, 세 모델이 동의했다는 사실, 프로세스가 `exit 0`으로 끝났다는 사실 — 셋 다 화면에서 검증과 같은 시각적 무게를 가지면 안 된다.

구체적으로:

- **투표는 근거가 아니다.** 동의한 모델 수는 관측값이므로 회색 캡션으로 쓴다. 배지나 초록색을 주지 않는다.
- **`unknown`은 `0`이 아니다.** 사용량을 관측하지 못했으면 `0`이나 `—`가 아니라 파선 테두리의 `unknown`을 쓴다. 빈 칸은 "없음"으로 읽힌다.
- **취소 버튼은 종료를 선언하지 않는다.** 취소를 *요청*하고, 종료가 확인되지 않으면 화면도 `UNKNOWN`으로 남는다.
- **정족수가 깨진 결과를 정상 완료로 보이게 하지 않는다.** 3인 구성에서 1인이 실패했으면 남은 2인의 답으로 채우지 말고 "요청한 구성이 완료되지 않음"을 표시한다.

## 두 번째 규칙 — 전부 보여주지 않는다

claim × evidence 전체를 한 화면에 펼치고 싶은 유혹이 크다. 그러면 안 된다는 근거가 있다.

PaperTrail(CHI 2026)은 LLM 답변과 원문을 각각 주장으로 쪼개 대조하는 인터페이스를 만들고 사용자 실험을 했다. 결과는 둘로 갈렸다 — **신뢰는 유의하게 낮아졌지만(p=.015) 사용성 평가도 유의하게 나빠졌고(p=.026), 정작 사용자가 LLM 텍스트를 고치는 양은 달라지지 않았다(p=.313).** 저자들은 이를 "정보 복잡도와 사용성의 맞교환"이라 부르고, 시간 압박 아래에서 인터페이스가 "어수선해진다"고 적었다.

그래서 이 시스템은 **단계적 공개**를 기본값으로 한다.

| 층 | 무엇을 보여주는가 | 언제 |
|---|---|---|
| 1 | 검토 중인 결정, 현재 권고, **이 결정을 뒤집을 조건** | 항상 |
| 2 | 미해결 항목과 다음으로 가치 있는 검사 | 항상, 단 접힌 상태 |
| 3 | 주장별 대조표, 근거, 참여자별 원문 | 눌렀을 때만 |

1층에 결론만 두고 근거를 숨기는 것이 아니다. **결정을 바꿀 수 있는 것**을 1층에 두고, 바꾸지 않는 것을 3층에 둔다. 중요한 소수 반례는 1층으로 올라온다.

## 세 번째 규칙 — 채움이 아니라 괘선

상태를 알약 배지로 칠하면 네 disposition이 전부 같은 크기의 색 덩어리가 되고 **무게 차이가 사라진다.** 게다가 그 모양은 어느 제품에나 있다.

이 시스템은 대신 **모노 라벨 + 밑줄**을 쓴다. 글자는 읽히고 색은 잉크로만 남는다. 무게는 괘선의 두께가 나른다 — `unresolved`는 3px, 나머지는 2px, `unknown`은 1px 파선.

같은 이유로 모서리는 2–3px이고, 카드는 그림자 대신 선으로 구분한다. 이 앱의 조상은 웹 카드가 아니라 **괘선 친 장부와 교정지**다. 반경 6px에 부드러운 그림자를 두르면 도구가 아니라 마케팅 페이지로 읽힌다.

## 상태는 어떻게 정해지는가

화면을 만들 사람이 가장 먼저 물을 질문이다. **색을 칠하기 위해 모델을 더 부르지 않는다.** 신호의 출처는 셋뿐이다.

| 층 | 무엇이 정하는가 | 추가 비용 |
|---|---|---|
| **A. 코드가 계산** | `disposition`, 호출 수, 정족수, blind 상태 | **0** |
| **B. 실행 결과** | `check.kind`, `check.status` | 그 검사 자체의 비용뿐 |
| **C. 모델** | 초안 → claim 추출, 의미 병합 | 기존 호출에 구조화 출력을 얹어 처리 |

**A는 이미 구현돼 있다.** `tools/check_frontier_protocol.py`의 `validate()`가 순수 함수로 계산한다 — `supported`는 `test`/`source`/`calculation` 중 `passed`가 있고 `failed`가 없을 때만. 화면은 그 결과를 표시할 뿐 스스로 승격하지 않는다.

**B는 모델의 자기 보고가 아니다.** `kind`는 *어느 검사기가 돌았는지*로 정해진다 — 테스트 러너가 돌면 `test`, source resolver가 URL을 열고 해당 위치를 찾으면 `source`. 모델이 "검증했습니다"라고 쓴 것은 `self_report`이고 승격에 쓰이지 않는다.

**C만 모델이 필요하고, 호출을 추가하지 않는다.** 초안을 받을 때 구조화 출력으로 함께 받는다(`--output-format json --json-schema` 류). 별도 extractor를 부르면 그것도 예산에서 차감되므로(`D13`) 그렇게 하지 않는다.

남는 위험은 C의 **추출 손실** 하나다 — 초안에 있던 조건이 claim으로 등록되지 않으면 원장이 완벽해도 결과가 틀린다. 그래서 `Extraction loss`가 별도 지표로 있다.

## 색의 의미

색은 여기서 상태를 나른다. 브랜드 표현이 아니다. **`accent`만 상호작용용이고 나머지 의미색은 절대 장식에 쓰지 않는다.**

### disposition — checker가 정의한 네 가지

| 토큰 | 뜻 | 왜 이 색인가 |
|---|---|---|
| `supported` (teal) | 외부 검사가 통과했다 | 유일하게 "확인됨"을 뜻하므로 유일하게 긍정색 |
| `qualified` (amber) | 조건부로 성립한다 | 주의를 요구하되 실패는 아니다 |
| `rejected` (slate) | 근거로 반박됐다 | **경보색을 쓰지 않는다.** 반박은 해결된 상태이고, 검증이 제 일을 한 결과다 |
| `unresolved` (crimson) | 근거로 해결되지 않았다 | **화면에서 가장 큰 목소리.** 이 시스템이 존재하는 이유가 이것을 지우지 않는 것이다 |

`rejected`를 빨강으로, `unresolved`를 회색으로 칠하는 것이 흔한 반사다. 정확히 거꾸로다. 반박된 주장은 끝난 일이고, **미해결 주장은 사람이 봐야 하는 일**이다.

### 상태

| 토큰 | 쓰임 |
|---|---|
| `unknown` | 관측하지 못함. **항상 `1px dashed` 테두리와 함께.** 채운 배경을 주지 않는다 |
| `sealed` (violet) | blind barrier가 닫혀 있음. 제출됐지만 열람 불가. 내용을 흐리게 처리하지 말고 아예 그리지 않는다 |
| `danger` | 예산 초과, 권한 거절, 인증 실패. 진행을 막는 것에만 |
| `accent` | 링크, 선택, 포커스. **의미색이 아니다** |

### 대비

모든 본문은 자신이 놓인 면에서 4.5:1 이상이어야 한다. `ink-200`은 12px 이상에서만 쓴다. **의미색은 글자색과 괘선으로만 쓰고 배경으로 채우지 않는다** — 채우면 그 위의 글자 대비를 두 테마에서 각각 다시 맞춰야 하고, 보통 한쪽이 무너진다. 예외는 선택된 행의 `accent-soft` 하나뿐이다.

## 타이포그래피

`IBM Plex Sans` + `IBM Plex Mono`. 모노는 장식이 아니라 **내용**이다 — 이 앱 화면의 상당 부분이 `claim-c1`, `sha256:…`, `D15`, `4/7` 같은 식별자와 수치다.

| 스타일 | 어디에 |
|---|---|
| `title` | 검토 중인 결정 한 줄 |
| `heading` | 섹션, 카드 머리 |
| `body` / `body-strong` | 주장 문장. 강조는 **색이 아니라 굵기**로 |
| `caption` | 한계 문구, 관측 범위 |
| `label` (mono) | 배지 글자, 대문자 라벨 |
| `code` (mono) | claim ID, digest, 경로, 명령 |
| `metric` (mono) | 호출 수, 시간. 자릿수를 맞춰야 하므로 `font-variant-numeric: tabular-nums`를 함께 |

## 밀도와 레이아웃

작업용 화면이므로 읽는 문서보다 조밀하다. 기본 행 높이 32–36px, 카드 안쪽 `space-4`, 섹션 사이 `space-6`.

- 카드는 **괘선으로 구분**한다(`rule-100`, 구역 경계는 `rule-200`). 그림자는 팝오버에만. 모든 블록에 그림자와 둥근 모서리를 주면 위계가 사라진다.
- 표는 자체 `overflow-x: auto` 컨테이너 안에. 페이지 본문이 가로로 스크롤되면 안 된다.
- 좌우 최소 여백 `space-4`를 모든 폭에서 유지한다.
- 한 줄에 담기지 못하는 주장 문장은 줄바꿈한다. **잘린 글자는 버그다** — 이 앱에서 잘린 조건절은 사라진 조건절이다.

## 하지 않는 것

- 파랑→보라 그라데이션, 이모지 섹션 표시, 모든 카드에 좌측 강조 바, 알약 모양 상태 배지
- 모든 블록에 같은 반경과 같은 그림자. 그러면 무엇이 중요한지가 사라진다
- 채팅 말풍선. 이것은 대화 기록이 아니라 판단 기록이다
- 진행률 막대로 "완료 임박"을 암시하기. 호출 예산은 **소진량**이지 진척도가 아니다
- 자신감 수치를 눈금이나 별점으로 표시하기. calibration이 검증되기 전에는 숫자 그대로, 출처를 붙여서만
